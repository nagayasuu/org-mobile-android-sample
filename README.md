# org-mobile-android-sample

Emacs で利用する org ファイルを Android で読むための、小さな閲覧アプリです。

Dropbox から端末へ保存した UTF-8 の `.org` ファイルを「ファイルを開く」で選択すると、見出し・本文・箇条書きを表示します。文書全体を縦にスクロールして閲覧できます。端末に保存したコピーを読むため、PC 側の更新後は再度保存してください。

最初の版は閲覧専用です。対応外の org 構文はテキストとして表示します。操作確認には [公開サンプル](examples/smoke.org) を使えます。

## ビルドと検証

JDK 17、Android SDK Platform 37.0、Build Tools 37.0.0 を準備し、SDK の場所を `ANDROID_HOME` またはローカル専用の `local.properties` に設定します。

```sh
./gradlew check assembleDebug
```

APK は `app/build/outputs/apk/debug/app-debug.apk` に出力します。詳しくは [環境の準備と検証コマンド](docs/android-build.md)、[USB 接続した端末での確認](docs/device-testing.md) を参照してください。初回の検証結果は [検証記録](docs/verification/2026-11-01-initial-implementation.md) に残しています。

## 開発の仕組みと今後の決定事項

以下は導入・検討の方針と残る課題です。方針の決定と実装・検証の完了を区別し、具体的な手順は各項目の参照先へ集約します。番号は項目を識別するためのもので、実装順序を定めるものではありません。

### 1. カバレッジ計測（方針決定済み・未導入）

JaCoCo を使い、Debug の JVM テストによるアプリ実装の行・分岐カバレッジ計測、HTML／XML レポート、CI 判定を導入します。合格条件は行・分岐それぞれ80%以上と、変更対象のカバレッジを低下させないことです。具体的な設定・タスク・互換性は導入時に検証します。

詳細：[開発手順のカバレッジ計測](docs/development-workflow.md#カバレッジ計測を導入する)。

### 2. プロパティベーステスト（方針決定済み・未導入）

Kotest Property を既存の JUnit 4 と併用し、`OrgParser`・`DocumentDecoder` を多様な生成入力で検証します。開発中は関連する性質を各1,000例、PR 作成・更新時は対象の性質を各1,000例検証し、最終受け入れでは対象コミットの CI 成功を確認します。週次・任意の探索専用の実行枠は設けません。失敗時は seed を記録して再現します。

1,000例は実測前の初期値であり、検証の十分性を保証する数値ではありません。採用バージョン・入力サイズ上限・互換性を導入時に確認し、実行時間と検出効果を評価します。

詳細：[開発手順のプロパティベーステスト](docs/development-workflow.md#プロパティベーステストとミューテーションテストを段階的に導入する)。

### 3. ミューテーションテスト（試験導入方針あり・未導入）

`OrgParser`・`DocumentDecoder` を対象に、PIT などの候補ツールの互換性を確認して試験導入します。意図的に加えた誤りをテストが検出できるか評価し、検出効果・実行時間・保守負担から、継続利用と CI への組み込みを判断します。最低 mutation score は試験結果を確認してから決めます。

詳細：[開発手順のミューテーションテスト](docs/development-workflow.md#ミューテーションテストの構成と評価)。

### 4. 依存構造の自動検査（方針決定済み・未導入）

ArchUnit を既存の JUnit 4 の JVM テストへ追加し、クラス間の参照・呼び出し関係を検査します。解析・デコードの Android 非依存と、ViewModel が画面や具体的な読み込み実装へ依存しないことを確認します。通常のローカル検証と CI に含め、規則違反があれば失敗させます。採用バージョン・互換性と、実際に違反を検出できることは導入時に確認します。

詳細：[開発手順の依存構造検査](docs/development-workflow.md#依存構造を自動検査する)。

### 5. 自動 E2E テスト（方針決定済み・未導入）

UI Automator と Espresso を使い、標準ファイル選択から表示まで、取り消し・画面回転後の保持、読み込みエラーからの復帰を自動検証します。API 37 のエミュレーターを Gradle Managed Devices で管理し、採用バージョンと実行環境の互換性を導入時に確認します。PR の必須検証にするかは、実行時間と安定性を確認して判断します。

詳細：[開発手順の自動 E2E テスト](docs/development-workflow.md#自動-e2e-テストを導入する)。

### 6. 性能計測（計測環境未整備・基準値未確定）

対象端末と合成文書、計測条件をそろえ、読み込み開始から最初の内容表示までの時間、解析時間、メモリ使用量を測定します。実測結果と利用目的から基準値・許容値を決め、性能に影響する変更で再計測します。自動計測は、手順と基準を整えてから必要性を判断します。

詳細：[開発手順の性能計測](docs/development-workflow.md#性能計測の対象と方法)。

### 7. 必須 CI とブランチ保護（設定・保護条件の動作確認済み）

2026-11-01 に GitHub 側へ設定を適用しました。`main` への統合は PR 経由とし、GitHub Actions の `verify` の成功と最新の `main` の反映を必須にしています。管理者にも適用し、直接 push・強制 push・削除を禁止し、レビュー指摘の解決を求めます。API で設定の保存と適用対象を確認し、同じ保護設定の一時ブランチで、管理者による条件未達の更新・マージの拒否と、条件を満たす PR の Squash merge を検証済みです。

詳細：[Git 運用規約の必須 CI と main の保護](docs/git-workflow.md#必須-ci-と-main-の保護)、[設定・検証記録](docs/verification/2026-11-01-branch-protection.md)。

### 8. 設計判断の記録（運用方針決定済み・個別記録未作成）

ファイルアクセス方式、状態の永続化、同期、モジュール境界など、影響が広く戻しにくい判断を ADR として記録します。必要な判断が生じた時点で `docs/decisions/` に作成し、比較した選択肢、採用理由、制約、検証方法、再検討する条件を残します。

詳細：[開発手順の ADR](docs/development-workflow.md#設計判断を-adr-に記録する)。

### 9. 今後の機能（未実装・仕様未決定）

見出しの折りたたみ、編集、新規保存、既存ファイルの更新、Dropbox との自動同期を追加候補とします。各機能は、利用目的と受け入れ条件を決めてから着手します。保存・同期では、保存先と方式、元データの保護、競合解決、失敗時の復旧、データ移行の方法を具体化し、主要な判断を ADR に残します。

### 12. 依存・開発環境の更新確認（開発着手前に確認する方針・自動化未導入）

開発着手前に実施記録を確認し、同日（日本時間）の正常完了記録がなければ、依存ライブラリ・JDK・Android SDK・Gradle・AGP・GitHub Actions の更新情報確認と結果の記録を自動実行します。月次 Issue 内へ日付別に、更新の要否、延期理由、後続作業を記録し、失敗・未完了は実施済みとして扱いません。依存バージョンの変更は、確認結果に基づく別の変更として検証します。自動実行を起動する仕組みは導入時に具体化します。

詳細：[開発手順](docs/development-workflow.md)の「依存・開発環境の着手前更新確認」。

### 13. コミットメッセージ検証と Git フック（実装・CI の動作確認済み）

Python 3 の標準ライブラリでコミットメッセージの形式と50/72ルールを検証します。`sh scripts/install-git-hooks.sh` で、この clone のメッセージ検証とステージ済み差分の空白確認を有効にできます。CI の必須ジョブ `verify` にも検証を組み込み、PR 内のコミットと PR タイトル、`main` への push で追加されたコミットを確認します。2026-11-02 にローカルの12テストとフックの動作、GitHub CI の成功、不正コミット・タイトルの拒否、タイトル修正後の再実行と正常復帰を確認しました。

マージキューと、複数バージョンの並行保守用のブランチ運用は保留します。現行の `main` と短命な作業ブランチによる運用を継続します。

詳細：[Git 運用規約の自動検証と Git フック](docs/git-workflow.md#自動検証と-git-フック)、[検証記録と未確認の範囲](docs/verification/2026-11-02-git-hooks.md)。

## 現在の制約と未確認の検証範囲

### 14. 読み込み処理の制約（追加調査・対策検討が必要）

現在は文書全体をメモリ上へ読み込むため、大容量文書の時間・メモリ性能を実測する必要があります。また、同期的なプロバイダーの読み込みは、キャンセルしても即時中断やタイムアウトを保証しません。長時間待機・停止時の動作を確認し、必要な制限や中断方法を検討します。

詳細：[検証記録のリスクと保証の限界](docs/verification/2026-11-01-code-review.md#リスクと保証の限界)。

### 15. 未確認の検証範囲（2026-11-01のコード見直し時点）

今回の変更に対する Dropbox 保存操作の再確認、最大表示サイズ、TalkBack の読み込み中・空文書・エラー時の音声と見出し移動の詳細、支援技術に慣れた利用者による評価は未確認です。確認済みの範囲と区別し、結果を検証記録へ残します。

詳細：[コード見直しと実機検証の記録](docs/verification/2026-11-01-code-review.md)。
