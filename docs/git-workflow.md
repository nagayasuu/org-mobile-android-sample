# Git 運用規約

この文書は、このリポジトリで人と Codex が共通して使う Git 運用の基準である。ブランチ、コミット、レビュー、履歴の取り扱いを定める。

今後の運用に合わせて、この文書を変更して育てる。

## 1. 基本方針

- 編集差分とステージ済み差分をそれぞれ確認する。
- コミットは意味の一貫した単位とし、無関係な変更を分ける。
- 履歴には変更の背景、判断理由、制約を残す。
- 短命な作業ブランチと小さな Pull Request（PR）を使い、頻繁に統合する。
- 未完成機能は既存の動作を保ちながら段階的に統合し、公開のタイミングを別に制御できるようにする。
- 最新の統合先と組み合わせた状態で必要な検証を行う。
- 未公開履歴の整理と、共有済み変更の取り消しを使い分ける。
- ビルド、CI、設定定義もレビュー対象にし、秘密情報の実体は含めない。
- 作業完了時に差分、検証、履歴への影響を簡潔なチェックリストで確認する。

短い変更サイクルを優先し、GitHub Flow を採用する。

## 2. ブランチと開発フロー

- 統合先は `main` とし、検証済みでリリース可能な状態を維持する。
- 通常の変更は `main` から作業ブランチを作り、PR を通じて `main` に統合する。
- 作業ブランチは一つの目的に絞り、長期間分岐させない。変更が大きくなる場合は、既存動作を保てる単位に分割する。
- 未完成機能を統合する場合は、フィーチャーフラグなどで公開を制御し、既存機能の失敗を隠さない。
- 緊急修正も短い作業ブランチと PR を使う。
- 継続的な開発用の `develop` や、常設の `release/*`、`hotfix/*` ブランチは初期運用には設けない。複数バージョンの並行保守が必要になった時点で見直す。

基本の流れは次のとおり。

```text
main → 作業ブランチ → 実装・検証・コミット → PR・レビュー → main に統合 → ブランチ整理
```

### ブランチ名

`<type>/<short-description>` とし、説明は英小文字・数字・ハイフンで表す。課題番号がある場合は説明の先頭に付けられる。

| type | 用途 | 例 |
| --- | --- | --- |
| `feat` | 機能追加 | `feat/task-filter` |
| `fix` | 不具合修正 | `fix/123-empty-task-title` |
| `docs` | 文書の追加・更新 | `docs/git-workflow` |
| `refactor` | 振る舞いを保つ構造変更 | `refactor/task-repository` |
| `test` | テストの追加・整理 | `test/task-filter` |
| `build` | ビルド・依存関係の変更 | `build/update-gradle` |
| `ci` | CI の変更 | `ci/android-checks` |
| `chore` | その他の保守作業 | `chore/ignore-local-files` |

既存の作業ブランチで依頼された場合は、その作業文脈を尊重する。規約に合わせるためだけに、無断でブランチを改名したり作業途中の変更を移したりしない。

## 3. コミット規約

### 変更の単位

- 1 コミットは、目的を一文で説明できる論理的なまとまりにする。
- 機能追加や不具合修正には、その振る舞いを確認する関連テストを含める。無関係な整形やリファクタリングは別のコミットにする。
- テスト自体の構造を整理する場合は、可能な限り本番コードの変更とコミットを分け、既存の検証能力を維持する。
- レビューに出すコミットは、適用した時点で必要なビルド・検証が通る状態を目指す。
- 認証情報、秘密鍵、ローカル環境固有の設定、生成物を意図せず含めない。`.gitignore` に追加しても、既に追跡済みのファイルは管理対象から外れないことに注意する。

### メッセージ形式

このリポジトリでは、次の形式を採用する。特定の外部仕様への完全準拠や、自動バージョン更新の導入を意味するものではない。

```text
<type>(<scope>): <変更の要約>

変更が必要になった背景と理由。
必要に応じて、選択した方法、影響、制約、検証内容を記載する。

Refs: #123
```

- `type` は前節のブランチ種別と同じ一覧から選ぶ。
- `scope` は任意とし、`tasks`、`build`、`docs` など対象領域を短く示す。不要なら括弧ごと省略する。
- 要約と本文は日本語を基本とし、コード識別子や一般的な技術用語は英語でよい。
- 要約は、何を変更したかが具体的に分かる一行にする。`修正` や `update` だけのメッセージは使わない。
- 自明でない変更には本文を付け、差分から読み取れる内容に加えて「なぜ」を残す。単純な誤字修正などは要約のみでよい。
- 課題への参照は、実在する番号がある場合だけ付ける。
- 破壊的変更では `type(scope)!: 要約` または `type!: 要約` とし、本文の `BREAKING CHANGE:` に影響と移行方法を記載する。

#### 50/72ルール

コミットメッセージには次の50/72ルールを適用する。

- 要約は命令形で書き、50文字以内にする。
- 日本語では現在形（例：`追加する`、`修正する`）で表現し、要約は25文字程度を目安にする。
- 本文を付ける場合は、要約の次に空行を置く。
- 本文は各行が72文字以内になるように整える。
- 本文では、差分から分かる変更内容よりも、なぜ変更するのかを中心に説明する。

例：

```text
docs(git): Git 運用規約を追加する

ブランチとコミットの運用を明文化し、作業時の判断基準を統一する。
AGENTS.md から参照させ、今後の作業にも適用する。
```

## 4. PR・レビュー・統合

ビルド、テスト、CI、端末での動作確認の具体的な手順は [開発手順](development-workflow.md) に従う。

- PR は一つの目的に絞り、問題、変更後の振る舞い、変更理由、検証結果を説明する。必要に応じて影響や復旧方法を添える。
- 最新の `main` と変更を組み合わせた状態を検証する。競合が解消できたことと、正しく動作することは別に確認する。
- 変更に応じて、ビルド、静的解析、単体・結合テストなど必要な検証を選ぶ。文書のみの変更では内容、リンク、差分の確認を行う。
- 必須の検証が失敗している状態で統合しない。実行できない検証は理由と未確認事項を明記し、成功したと報告しない。
- レビューでは正しさに加えて、作者以外が保守できるか、変更が十分小さいかを確認する。
- 統合方式は **Squash merge を既定**とし、一つの PR の目的が分かるコミットを `main` に残す。最終メッセージにも第3節の形式と変更理由を反映する。
- 統合後は `main` の検証結果を確認する。失敗した場合は修正または取り消しを優先し、問題を重ねない。
- 作業ブランチは、統合済みで残す作業がないことを確認して整理する。Squash merge 後は通常のマージ祖先判定だけでは統合を確認できないため、PR の状態と差分も確認する。

### 必須 CI と main の保護

個人開発での統合条件として、次の方針を採用する。[GitHub のブランチ保護](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches)を設定して維持する。GitHub 側の現設定は未確認であり、設定の適用・動作確認は未実施である。方針の確定と保護の有効化を区別する。

| 項目 | 採用する方針 |
| --- | --- |
| 保護対象 | `main`。管理者にも保護条件を適用する |
| 統合経路 | PR を必須にし、`main` への直接 push を禁止する |
| 必須 CI | `Android checks` の `verify` ジョブを必須化する。GitHub 上の実際のチェック名と実行元を確認して設定する |
| 最新状態の検証 | マージ前に最新の `main` を取り込み、CI を成功させる。ブランチ保護でも最新状態を要求する |
| レビュー | 人による必須承認は当面0人とし、セルフレビューを実施する。レビュー指摘は解決してから統合する |
| 履歴保護 | `main` の強制 push・削除を禁止する |
| 統合方式 | Squash merge を既定とする |
| マージキュー | 初期は導入せず、並行する PR が増えたら再検討する |

CI の実行範囲と拡張時の扱いは[開発手順](development-workflow.md)に従う。必須ジョブを分割・改名する場合は、ワークフローと GitHub 側の必須チェックを合わせて更新し、ジョブ名の重複による曖昧な判定を避ける。

設定時には、実際のチェック名、設定内容、適用日と確認結果を記録する。管理者にも保護が適用されること、CI 失敗・実行待ち、最新の `main` 未反映、未解決のレビュー指摘など、条件を満たさない PR がマージできないことと、条件を満たした PR を統合できることを確認する。本書やワークフローの更新だけで、ホスティングサービス側に制約が設定されたとはみなさない。

## 5. 履歴の整理・取り消し・調査

| 場面 | 方針 |
| --- | --- |
| 自分だけが持つ未公開コミットの整理 | `commit --amend` や対話的 rebase を使える。作業中の変更と対象範囲を先に確認する |
| `main` の更新を作業ブランチへ取り込む | 未公開の自分の履歴では rebase を使える。共有済みブランチでは履歴を保つ merge を基本とし、更新後に再検証する |
| `main` や共有済み変更の取り消し | 原則として `git revert` で取り消しを新しいコミットとして残す |
| push が非 fast-forward で拒否された | fetch で相手の更新を取得し、分岐と差分を確認して統合する。拒否の解消だけを目的に強制 push しない |
| 特定の修正を別の開発ラインへ適用 | 必要な場合に `cherry-pick` を使い、元コミットと適用先の関係を記録する |
| 変更理由・原因を調べる | `git log`、`git show`、`git blame`、`git log -S` / `-G` を使う。再現条件がある不具合は `git bisect` も検討する |
| コミットを見失った | `git reflog` で以前の参照先を調べ、必要なコミットをブランチなどで保持する。reflog はローカルの記録であり、恒久的なバックアップにはしない |

共有済み履歴の書き換えが必要な例外では、対象、理由、共同作業者への影響を確認し、合意してから行う。`--force-with-lease` も履歴を書き換える操作であり、合意の代わりにはならない。

## 6. Codex が作業するときの手順

ユーザーの明示的な指示を優先し、指定がない部分に本書を適用する。判断に迷う場合は、既存の作業と履歴を保つ方法を選ぶ。

1. 作業前に `git status --short`、`git branch --show-current`、必要な差分と履歴を確認する。未追跡ファイルも含め、既存の作業を把握する。
2. 依頼の範囲内で変更し、既存の未コミット変更を維持する。同じファイルを編集する場合も、既存の変更を巻き戻さない。
3. 変更内容に合った検証を行い、実行コマンド、結果、未実行項目を説明できるようにする。実際のプロジェクト構成を確認し、存在しないビルド手順や CI を前提にしない。
4. コミットする場合は、対象を明示して `git add <path>` または `git add -p` で選ぶ。`git diff --staged` を確認し、無関係な既存変更が混ざっていないことを確かめる。
5. 作業後に差分と状態を確認し、変更点、検証結果、残っている課題を報告する。

コミット、push、PR 作成、マージはそれぞれ別の操作として扱い、依頼の範囲に従って実行する。本書を読むこと自体を、それらすべての実行依頼とはみなさない。既に明示された指示について、重ねて確認を求める必要はない。

`reset --hard`、変更を捨てる `restore` / `checkout`、`clean`、強制 push、未統合ブランチの強制削除は、整形や作業準備の代わりに使わない。必要な場合は、依頼で許可された範囲と失われる変更を確認する。

### 完了時のチェックリスト

- [ ] 差分は依頼の目的に沿い、既存の作業を損なっていない。
- [ ] 必要な検証を行い、失敗・未実行・未確認の項目を明記した。
- [ ] コミットする場合、対象とステージ済み差分を確認し、規約に沿ったメッセージを用意した。
- [ ] 共有履歴やリモートへの操作は依頼の範囲内である。

Git の運用ルールはこの文書へ集約し、`AGENTS.md` には参照先を維持する。方針の変更時は、変更理由と影響する手順を合わせて更新する。

- リリースタグの命名、バージョン付与、並行保守が必要になった場合の分岐方法。
- コミットメッセージ検証やフックの導入。ローカルフックは通常の clone だけでは配布されないため、導入する場合は配布・更新手順も定める。
