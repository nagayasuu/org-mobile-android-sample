# Git 運用規約

この文書は、このリポジトリで人と Codex が共通して使う Git 運用の基準である。ブランチ、コミット、レビュー、履歴の取り扱いを定める。

今後の運用に合わせて、この文書を変更して育てる。

## 1. 基本方針

- 編集差分とステージ済み差分をそれぞれ確認する。
- コミットは意味の一貫した単位とし、無関係な変更を分ける。
- 履歴には変更の背景、判断理由、制約を残す。
- 短命な作業ブランチと小さな Pull Request（PR）を使い、頻繁に統合する。
- 未完成機能は既存の動作を保ちながら段階的に統合し、公開のタイミングを別に制御できるようにする。
- 最新の統合先と組み合わせた状態で必要な検証を行う。
- 未公開履歴の整理と、共有済み変更の取り消しを使い分ける。
- ビルド、CI、設定定義もレビュー対象にし、秘密情報の実体は含めない。
- 作業完了時に差分、検証、履歴への影響を簡潔なチェックリストで確認する。

短い変更サイクルを優先し、GitHub Flow を採用する。

## 2. ブランチと開発フロー

- 統合先は `main` とし、検証済みでリリース可能な状態を維持する。
- 通常の変更は `main` から作業ブランチを作り、PR を通じて `main` に統合する。
- 作業ブランチは一つの目的に絞り、長期間分岐させない。変更が大きくなる場合は、既存動作を保てる単位に分割する。
- 未完成機能を統合する場合は、フィーチャーフラグなどで公開を制御し、既存機能の失敗を隠さない。
- 緊急修正も短い作業ブランチと PR を使う。
- 継続的な開発用の `develop` や、常設の `release/*`、`hotfix/*` ブランチは設けない。並行保守用のブランチ運用の導入は保留する。複数バージョンの保守が必要になった場合に再検討する。

基本の流れは次のとおり。

```text
main → 作業ブランチ → 実装・検証・コミット → PR・レビュー → main に統合 → ブランチ整理
```

### ブランチ名

`<type>/<short-description>` とし、説明は英小文字・数字・ハイフンで表す。課題番号がある場合は説明の先頭に付けられる。

| type | 用途 | 例 |
| --- | --- | --- |
| `feat` | 機能追加 | `feat/task-filter` |
| `fix` | 不具合修正 | `fix/123-empty-task-title` |
| `docs` | 文書の追加・更新 | `docs/git-workflow` |
| `refactor` | 振る舞いを保つ構造変更 | `refactor/task-repository` |
| `test` | テストの追加・整理 | `test/task-filter` |
| `build` | ビルド・依存関係の変更 | `build/update-gradle` |
| `ci` | CI の変更 | `ci/android-checks` |
| `chore` | その他の保守作業 | `chore/ignore-local-files` |

既存の作業ブランチで依頼された場合は、その作業文脈を尊重する。規約に合わせるためだけに、無断でブランチを改名したり作業途中の変更を移したりしない。

## 3. コミット規約

### 変更の単位

- 1 コミットは、目的を一文で説明できる論理的なまとまりにする。
- 機能追加や不具合修正には、その振る舞いを確認する関連テストを含める。無関係な整形やリファクタリングは別のコミットにする。
- テスト自体の構造を整理する場合は、可能な限り本番コードの変更とコミットを分け、既存の検証能力を維持する。
- レビューに出すコミットは、適用した時点で必要なビルド・検証が通る状態を目指す。
- 認証情報、秘密鍵、ローカル環境固有の設定、生成物を意図せず含めない。`.gitignore` に追加しても、既に追跡済みのファイルは管理対象から外れないことに注意する。

### メッセージ形式

このリポジトリでは、次の形式を採用する。特定の外部仕様への完全準拠や、自動バージョン更新の導入を意味するものではない。

```text
<type>(<scope>): <変更の要約>

変更が必要になった背景と理由。
必要に応じて、選択した方法、影響、制約、検証内容を記載する。

Refs: #123
```

- `type` は前節のブランチ種別と同じ一覧から選ぶ。
- `scope` は任意とし、`tasks`、`build`、`docs` など対象領域を短く示す。不要なら括弧ごと省略する。
- 要約と本文は日本語を基本とし、コード識別子や一般的な技術用語は英語でよい。
- 要約は、何を変更したかが具体的に分かる一行にする。`修正` や `update` だけのメッセージは使わない。
- 自明でない変更には本文を付け、差分から読み取れる内容に加えて「なぜ」を残す。単純な誤字修正などは要約のみでよい。
- 課題への参照は、実在する番号がある場合だけ付ける。
- 破壊的変更では `type(scope)!: 要約` または `type!: 要約` とし、本文の `BREAKING CHANGE:` に影響と移行方法を記載する。

#### 50/72ルール

コミットメッセージには次の50/72ルールを適用する。

- 要約は命令形で書き、`type`・任意の `scope`・区切りを含む1行目全体を50文字以内にする。
- 日本語では現在形（例：`追加する`、`修正する`）で表現し、要約は25文字程度を目安にする。
- 本文を付ける場合は、要約の次に空行を置く。
- 本文とフッターは各行が72文字以内になるように整える。URL を含む行も例外にしない。
- 本文では、差分から分かる変更内容よりも、なぜ変更するのかを中心に説明する。

文字数は Unicode コードポイント数で数える。UTF-8 のバイト数や画面上の表示幅では数えない。日本語も通常の1文字は1と数え、結合文字や複数コードポイントからなる絵文字は構成要素をそれぞれ数える。

例：

```text
docs(git): Git 運用規約を追加する

ブランチとコミットの運用を明文化し、作業時の判断基準を統一する。
AGENTS.md から参照させ、今後の作業にも適用する。
```

### 自動検証と Git フック

検証処理は [`scripts/check_commit_message.py`](../scripts/check_commit_message.py) に集約する。Python 3 の標準ライブラリと Git を使い、Node.js や外部 Python パッケージは不要である。UTF-8 のメッセージについて、以下を失敗条件として扱う。

- 規定外の `type`、`type(scope): 要約` / `type: 要約` と異なる形式、空の要約、1行目末尾の空白。`scope` を付ける場合は空白・括弧を含まない値にする。
- `修正` / `update` だけの要約、1行目が50文字を超える、本文前の空行がない、本文・フッターの行が72文字を超える。
- 破壊的変更の `!` と、空でない説明を伴う `BREAKING CHANGE:` の片方だけがある。

日本語・命令形の適切さ、理由・移行方法の十分性、Issue 番号の実在はセルフレビューで確認する。自動検証は意味の正しさを保証しない。

#### clone ごとの導入・更新・解除

リポジトリのルートで、初回に次を実行する。

```sh
sh scripts/install-git-hooks.sh
git config --local --get core.hooksPath
```

設定値が `.githooks` なら有効である。導入スクリプトはこの clone の `core.hooksPath` だけを設定し、グローバル設定は変更しない。既に同じ設定なら再実行できる。別の `core.hooksPath` や、既定の hooks ディレクトリに有効な独自フックがある場合は、既存の検証を無効にしないよう中止する。既存フックとの併用が必要なら、その処理を保持する呼び出し方を別途決めてから導入する。

フック本体は [`.githooks/`](../.githooks/) で版管理し、通常の clone でファイルを取得する。有効化の設定は clone ごとに必要である。更新は通常の PR・統合・取得を通じて配布し、変更内容を確認してから導入スクリプトを再実行する。Git・Python 3・POSIX シェルが必要であり、Windows では Git Bash と `python3` を使える環境を用意する。GUI 経由でも Python 3 が PATH 上に必要である。Windows・GUI 上での動作は未確認である。

解除は、この clone の設定が `.githooks` であることを上記コマンドで確かめてから行う。他の値に変更されていた場合は削除しない。

```sh
git config --local --unset core.hooksPath
```

#### 実行する検証

| 実行箇所 | 検証内容 |
| --- | --- |
| `pre-commit` | `git diff --cached --check` でステージ済み差分の末尾空白などを検出する。未ステージの内容は対象にしない |
| `commit-msg` | 共通スクリプトでメッセージを検証する。通常の commit と amend が対象。Git の編集用コメントと scissors 行以降の差分は除いて判定する |
| CI の `verify` | フック・検証処理のテストと共通スクリプトを実行する。PR ではタイトルと `base.sha..head.sha`、`main` の push では `before..after` に追加された通常コミットを対象にする |

共有ブランチへ `main` の更新を取り込む運用を維持するため、ローカルでは `MERGE_HEAD` が存在するマージ操作、CI では親が複数あるマージコミットのメッセージを対象外とする。マージで取り込む通常コミットは CI の対象範囲に含める。`git revert` の既定の見出しは規約に合わないので、`git revert --edit <commit>` で `fix: ...を取り消す` などに編集し、取り消す理由と元コミットへの参照を残す。

CI は履歴を全取得して対象範囲を検証し、既存の全履歴へ遡って規約を適用しない。新規ブランチの push で `before` がゼロの場合は先端コミットだけを確認する。取得不足・不正 UTF-8・入力の読み取り失敗は失敗にする。メッセージの実体をエラーへ転記せず、コミット SHA・行番号・違反内容を報告する。

PR タイトルの変更でも再実行するため、`pull_request` の `edited` イベントを指定する。検証は既存の必須ジョブ `verify` 内で行い、チェック名を増やさない。ローカルフックは未導入や `--no-verify` で回避できるため、CI の検証も必須とする。

Squash merge の最終メッセージは統合時に編集でき、PR タイトルの CI 成功だけでは保証されない。統合前に最終メッセージの形式・理由・文字数を確認する。`main` の push CI でも実際のメッセージを検証するが、その時点では統合済みである。失敗時は共有履歴を書き換えず、原因を確認して対応する。

手動確認とフック・CI のテストは次を使う。

```sh
python3 scripts/check_commit_message.py --message-file /tmp/commit-message.txt
python3 scripts/check_commit_message.py --revision HEAD
python3 -m unittest discover -s scripts/tests -v
```

メッセージファイルは UTF-8 で用意する。既存コミットの確認は導入前のメッセージでも規約を適用するため、過去の違反が見つかっても履歴を修正しない。

2026-11-02 にローカルの12テストと、この clone の有効なフックを確認した。GitHub CI でも正常系、不正コミット・タイトルの拒否、同じ先端コミットでのタイトル修正による再実行と正常復帰を確認済みである。対象コミット・run・未確認の範囲は[検証記録](verification/2026-11-02-git-hooks.md)を参照する。

## 4. PR・レビュー・統合

ビルド、テスト、CI、E2E による利用経路の検証の具体的な手順は [開発手順](development-workflow.md) に従う。

PR 作成前のセルフレビューと統合前のレビューでは、[開発手順のレビューチェックリスト](development-workflow.md#review-checklist)を使い、[PR テンプレート](../.github/pull_request_template.md)へ結果と根拠を記録する。修正や対象コミットの更新後は、影響する項目を再確認する。確認内容と判定基準は開発手順に集約し、人による必須承認数と必須 CI は本節の保護条件に従う。

agent による確認は[agent によるレビュー手順](development-workflow.md#agent-review)に従い、作成者と別の agent か、同じ agent のセルフレビューかを記録する。agent の確認結果を GitHub の承認や必須 CI の代わりにせず、コメント投稿・承認・マージは依頼された範囲で行う。

依頼時の情報、確認根拠の再利用、修正後の再確認、繰り返す指摘の自動化は、[レビューの負担と待ち時間を減らす手順](development-workflow.md#review-efficiency)に従う。結果と根拠は PR 内の検証・レビュー記録から参照できる形にし、同じ説明の転記を減らす。

- PR は一つの目的に絞り、問題、変更後の振る舞い、変更理由、検証結果を説明する。必要に応じて影響や復旧方法を添える。
- 最新の `main` と変更を組み合わせた状態を検証する。競合が解消できたことと、正しく動作することは別に確認する。
- 変更に応じて、ビルド、静的解析、単体・結合テストなど必要な検証を選ぶ。文書のみの変更では内容、リンク、差分の確認を行う。
- 必須の検証が失敗している状態で統合しない。実行できない検証は理由と未確認事項を明記し、成功したと報告しない。
- レビューでは正しさに加えて、作者以外が保守できるか、変更が十分小さいかを確認する。
- 統合方式は **Squash merge を既定**とし、一つの PR の目的が分かるコミットを `main` に残す。最終メッセージにも第3節の形式と変更理由を反映する。
- 統合後は `main` の検証結果を確認する。失敗した場合は修正または取り消しを優先し、問題を重ねない。
- 作業ブランチは、統合済みで残す作業がないことを確認して整理する。Squash merge 後は通常のマージ祖先判定だけでは統合を確認できないため、PR の状態と差分も確認する。

### 必須 CI と main の保護

個人開発での統合条件として、次の方針を採用する。[GitHub のブランチ保護](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches)を設定して維持する。2026-11-01 に GitHub 側へ設定を適用し、API で保存内容と `main` への適用を確認した。同じ保護設定の一時ブランチで、管理者による条件未達の更新・マージの拒否と、条件を満たす PR の Squash merge を確認済みである。設定内容と確認範囲は[検証記録](verification/2026-11-01-branch-protection.md)を参照する。

| 項目 | 採用する方針 |
| --- | --- |
| 保護対象 | `main`。管理者にも保護条件を適用する |
| 統合経路 | PR を必須にし、`main` への直接 push を禁止する |
| 必須 CI | `Android checks` の `verify` ジョブ。チェック名 `verify`、実行元 GitHub Actions（App ID `15368`）を指定済み |
| 最新状態の検証 | マージ前に最新の `main` を取り込み、CI を成功させる。ブランチ保護でも最新状態を要求する |
| レビュー | 人による必須承認は当面0人とし、セルフレビューを実施する。レビュー指摘は解決してから統合する |
| 履歴保護 | `main` の強制 push・削除を禁止する |
| 統合方式 | Squash merge を既定とする |
| マージキュー | 導入は保留。並行する PR の増加と GitHub の利用条件を確認して再検討する |

CI の実行範囲と拡張時の扱いは[開発手順](development-workflow.md)に従う。必須ジョブを分割・改名する場合は、ワークフローと GitHub 側の必須チェックを合わせて更新し、ジョブ名の重複による曖昧な判定を避ける。

設定時には、実際のチェック名、設定内容、適用日と確認結果を記録する。管理者にも保護が適用されること、CI 失敗・実行待ち、最新の `main` 未反映、未解決のレビュー指摘など、条件を満たさない PR がマージできないことと、条件を満たした PR を統合できることを確認する。本書やワークフローの更新だけで、ホスティングサービス側に制約が設定されたとはみなさない。

#### 設定の維持と動作確認

GitHub のリポジトリの **Settings → Branches → Branch protection rules** で `main` のルールを確認・更新する。GitHub の画面または API を利用でき、`gh` は必須にしない。

1. **Require a pull request before merging** を有効にする。**Require approvals**、Code Owner の承認、最後の push に対する承認は要求せず、必須承認は0人とする。
2. **Require status checks to pass before merging** と **Require branches to be up to date before merging** を有効にする。チェック名 `verify` を選び、期待する実行元を GitHub Actions にする。他の実行元による同名チェックを許可しない。
3. **Require conversation resolution before merging** と **Do not allow bypassing the above settings** を有効にする。PR 要件を回避できるユーザー・チーム・アプリは追加しない。**Allow force pushes** と **Allow deletions** は無効のまま維持する。
4. 保存後に設定を再取得し、対象が `main`、管理者への適用が有効、必須チェックが `verify` / App ID `15368`、最新状態の要求が有効であることを確認する。REST API を使う場合は `GET /repos/{owner}/{repo}/branches/main/protection` で確認できる。
5. PR の Checks とマージ欄で、CI が実行待ち・失敗のときに統合できず、最新の `main` 未反映や未解決のレビュー指摘がある場合も統合できないことを確認する。管理者のアカウントでも確認し、検証のために保護を解除しない。
6. 条件を満たした PR で `verify` の成功と統合可能な状態を確認し、統合を行う際は Squash merge を選ぶ。統合後の `main` の CI も確認する。設定確認と実際の拒否・統合は別の結果として、対象 PR・コミット・run の URL と未確認事項を記録する。

CI 待ちによる拒否と PR 要件による拒否を区別するため、PR を持たないコミットの直接更新は CI 成功後にも確認する。保護条件を満たした既存 PR の先端への参照更新が許可され、その PR が統合済みになる場合がある。これは PR 要件の無効化とは区別し、通常の統合操作には Squash merge を使う。

## 5. 履歴の整理・取り消し・調査

| 場面 | 方針 |
| --- | --- |
| 自分だけが持つ未公開コミットの整理 | `commit --amend` や対話的 rebase を使える。作業中の変更と対象範囲を先に確認する |
| `main` の更新を作業ブランチへ取り込む | 未公開の自分の履歴では rebase を使える。共有済みブランチでは履歴を保つ merge を基本とし、更新後に再検証する |
| `main` や共有済み変更の取り消し | 原則として `git revert` で取り消しを新しいコミットとして残す |
| push が非 fast-forward で拒否された | fetch で相手の更新を取得し、分岐と差分を確認して統合する。拒否の解消だけを目的に強制 push しない |
| 特定の修正を別の開発ラインへ適用 | 必要な場合に `cherry-pick` を使い、元コミットと適用先の関係を記録する |
| 変更理由・原因を調べる | `git log`、`git show`、`git blame`、`git log -S` / `-G` を使う。再現条件がある不具合は `git bisect` も検討する |
| コミットを見失った | `git reflog` で以前の参照先を調べ、必要なコミットをブランチなどで保持する。reflog はローカルの記録であり、恒久的なバックアップにはしない |

共有済み履歴の書き換えが必要な例外では、対象、理由、共同作業者への影響を確認し、合意してから行う。`--force-with-lease` も履歴を書き換える操作であり、合意の代わりにはならない。

## 6. Codex が作業するときの手順

ユーザーの明示的な指示を優先し、指定がない部分に本書を適用する。判断に迷う場合は、既存の作業と履歴を保つ方法を選ぶ。

1. 作業前に `git status --short`、`git branch --show-current`、必要な差分と履歴を確認する。未追跡ファイルも含め、既存の作業を把握する。
2. 依頼の範囲内で変更し、既存の未コミット変更を維持する。同じファイルを編集する場合も、既存の変更を巻き戻さない。
3. 変更内容に合った検証を行い、実行コマンド、結果、未実行項目を説明できるようにする。実際のプロジェクト構成を確認し、存在しないビルド手順や CI を前提にしない。
4. コミットする場合は、対象を明示して `git add <path>` または `git add -p` で選ぶ。`git diff --staged` を確認し、無関係な既存変更が混ざっていないことを確かめる。
5. 作業後に差分と状態を確認し、変更点、検証結果、残っている課題を報告する。

コミット、push、PR 作成、マージはそれぞれ別の操作として扱い、依頼の範囲に従って実行する。本書を読むこと自体を、それらすべての実行依頼とはみなさない。既に明示された指示について、重ねて確認を求める必要はない。

`reset --hard`、変更を捨てる `restore` / `checkout`、`clean`、強制 push、未統合ブランチの強制削除は、整形や作業準備の代わりに使わない。必要な場合は、依頼で許可された範囲と失われる変更を確認する。

### 完了時のチェックリスト

- [ ] 差分は依頼の目的に沿い、既存の作業を損なっていない。
- [ ] 必要な検証を行い、失敗・未実行・未確認の項目を明記した。
- [ ] コミットする場合、対象とステージ済み差分を確認し、規約に沿ったメッセージを用意した。
- [ ] 共有履歴やリモートへの操作は依頼の範囲内である。
