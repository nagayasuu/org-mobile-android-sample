# 開発手順

このリポジトリでは、動いている org 閲覧アプリへ小さな変更を加え、テスト・CI・E2E の結果から次の変更を決める。人と agent は同じ検証手順を使い、既存の閲覧機能を維持しながら、入力から表示、必要なら保存までを一つの機能として通す。GitHub 上の操作は[GitHub CLI の手順](../guides/github-cli.md#github-cli)に従って `gh` を使う。

| アプリ・テスト・ビルド設定 | [アプリ仕様](../project/app-spec.md)、[現在の構造](../project/architecture.md)、[設計の判断基準](design.md)と[検証の基準](verification.md)の関係する節、[Android の手引き](../guides/android.md)の必要な実行方法 |

<a id="change-steps"></a>

## 変更の共通手順

1. [Git 運用規約の Codex の手順](git.md#6-codex-が作業するときの手順)に従い、状態、現在のブランチ、差分、関連する履歴を確認する。既存の未コミット変更を保つ。
2. 目的・変更範囲・受け入れ条件を定め、対象と参照先を読む。アプリの変更では README、対象コード、関連テストと履歴から一つの操作を入口から結果まで追い、既存実装や Android の標準機能を使えるか調べる。
3. アプリ・テスト・ビルド設定を変更する場合は関係する既存テストを実行し、着手前の状態を把握する。保証が不足する箇所は必要な範囲で現在の振る舞いをテストにする。文書のみの場合は対象の内容・参照先と既存の定義を確認する。
4. ビルドや E2E が必要な場合は、利用できる JDK・SDK、CI、エミュレーターと、実行できない検証を確認する。環境構築は[ビルド・検証の手引き](../guides/android.md)の該当する節に従う。
5. 小さく変更し、[共通の検証](verification.md#共通の検証)、[agent レビュー](review.md#agent-review)、[完了条件と報告](#completion)に従って結果と未確認事項を残す。

文書の配置と正本の一覧は [開発文書の案内](../README.md)を参照する。

## 次の小さな機能と受け入れ条件を決める

利用者の一つの目的を、実装・レビュー・E2E で検証できる大きさに絞る。画面だけ、保存層だけを先に大量に作らず、利用者の操作と結果がつながる単位で進める。不具合修正、依存更新、構造整理も一つの目的に絞る。

### 利用者の目的と利用環境を確かめる

機能や利用経路を決める際は、利用者への短い聞き取りや実際の操作から、次の点を確認する。このアプリでは「PC の Emacs で使う org ファイルを Android でも読む」という目的を起点にし、開発者自身の知識や操作の慣れを利用者全体の前提にしない。

- 達成したい作業と、現在の方法で困っている点。例えば、移動中に必要な見出しや本文を見つけたいのか、文書全体を読みたいのかを区別する。
- 利用頻度、org や Android のファイル操作への慣れ、Dropbox から保存する手順をどこまで理解しているか。
- 利用する端末・OS、文書の長さや言語、通信の有無、文字サイズ・読み上げ・入力方法など、操作に影響する環境。

確認した事実と未確認の想定を分け、今回優先する使いやすさを受け入れ条件へつなげる。例えば、たまに使う場合は操作を見つけやすいこと、繰り返し使う場合は少ない手間で目的の本文へ戻れることを重視する。小さな修正では既存の確認記録を参照し、影響する点だけを見直す。公開記録には個人を特定する情報や私的な文書内容を含めない。

### 受け入れ条件へ落とし込む

着手前に、Issue・PR の草案や作業メモへ以下を記載する。小さな変更では短い箇条書きでよく、専用ファイルは必須にしない。

- 目的、変更前と変更後の振る舞い、今回扱わない範囲。
- 入力・操作・期待結果で表した受け入れ条件。正常系に加え、関係する空入力、取り消し、アクセス権の喪失、失敗と再試行などを選ぶ。
- 影響する画面、解析処理、状態保持、ファイルアクセス、設定・依存先と、互換性への影響。
- E2E で確かめる条件、自動化の未対応範囲、使用する公開サンプルや合成データ。

例えば見出しの折りたたみなら、「見出しを押す → 配下が隠れる → 再度押すと戻る」という一本から始め、入れ子や画面再作成時の状態は別の具体例で確認する。

品質の条件も変更の範囲に合わせて具体化する。

| 観点 | 条件と確認方法の例 |
| --- | --- |
| 読みやすさ・操作性 | 日本語、長い文書、文字サイズ、明暗設定、回転時に操作と内容を判別できるかに加え、利用者が操作を見つけて目的を達成できるかを確認する |
| アクセシビリティ | 読み上げ、文字拡大、色に依存しない情報、操作対象とフォーカスについて、変更対象の画面・主要操作で確認する |
| データと失敗時の動作 | 対応外構文の保持、読み込み失敗後の再選択をE2E で確認する。保存機能を追加する場合は元ファイルの保護と再起動後の保持も条件にする |
| 応答性 | 対象端末・OS、文書量、計測区間、許容時間を決めて測る。1 万項目の末尾表示の確認と、読み込み時間・メモリの測定を区別する |
| プライバシー | 文書内容・個人のファイル名・URI・認証情報をログや成果物へ含めず、必要なアクセス権だけを使うことを差分と出力で確認する |

数値の目標は、現在の実測と利用目的から決める。未計測の性能を達成済みとせず、カバレッジやコード量だけを完了条件にしない。

<a id="agent-planning"></a>

### 実装計画を主担当とレビュー担当で共有する

受け入れ条件を、対象ファイル・小さな実装手順・各手順の検証へ結び付ける。小さな変更は Issue・PR の草案や作業メモに短く記載し、複数の責務にまたがる変更や方針が不明な変更は、[実装計画の様式](../templates/implementation-plan.md)を使って整理する。専用ファイルや新しい agent 設定の作成を全作業の前提にしない。

| 担当 | 行うこと | 引き継ぐ内容 |
| --- | --- | --- |
| 主担当 | 要求と現状を調べ、計画、実装、テスト実行、指摘への対応を進める | 受け入れ条件、対象版・差分、判断理由、実行結果と未確認事項 |
| レビュー担当 | 要求・計画と、実際の差分・検証結果を照合する。対象ファイルは変更しない | [agent レビュー手順](review.md#agent-review)による判定、根拠、指摘と残るリスク |

主担当は次の順で進める。

1. **計画する。** 目的、対象と維持する動作、変更するファイル、手順ごとの期待結果・検証、未決事項を記す。確認できた事実と仮定を分け、広い影響のある判断は関係者と確認する。既に依頼・許可された作業はその範囲で進める。
2. **基準を確かめる。** 関係する既存テストを実行し、着手前の失敗と新しい変更による失敗を区別する。
3. **小さく実装・検証する。** [実装のサイクル](#implementation)を使い、各手順の結果を計画から参照できる形で残す。共有する依存や対象範囲が変わったら、計画・検証範囲・既存の許可との整合を見直す。
4. **レビューへ渡す。** 対象版と更新済みの計画、差分、実行結果の参照先をそろえ、[agent レビュー手順](review.md#agent-review)に従って確認者を選ぶ。指摘への対応後は、更新差分と影響する項目を再確認する。

担当を増やす場合は、既存の[入力・出力を絞る手順](../guides/agent-tools.md#agent-context)に従う。独立した調査を追加で委譲するときも、目的・関連ファイル・許可された操作・返す成果を依頼単体で分かるようにする。複数担当が編集する必要がある場合は、担当範囲と必要な作業場所の分離を決め、統合した状態を検証する。

計画は作業の基準であり、完了の根拠は実際の差分と実行結果である。手順の効果は、同種作業の手戻り、再読、レビューの待ち時間、取得できる場合の全担当の使用量で比較する。今回の計画・記録の追加だけで改善を実証したとは扱わない。

<a id="implementation"></a>

## 小さく実装し、理解できる構造を保つ

振る舞いを変える場合は、次のサイクルを基本にする。

1. 利用者の操作に近い境界で、受け入れ条件を示す少数のテストを用意する。画面や ViewModel から必要な振る舞いを定め、細かな解析条件は内部の単体テストで補う。
2. テストを実行し、期待した振る舞いが未実装であるためにアサーションで失敗することを確認する（Red）。環境不備やテストの誤りによる失敗は先に切り分ける。
3. 成功に必要な小さな変更を実装する。
4. 関連テストの成功を確認し（Green）、成功を保って構造を整理する（Refactoring）。
5. 別の結果になる具体例や境界条件を追加し、受け入れ条件を満たすまで繰り返す。完了前に共通のビルド・検証を実行する。

一つの例を通す仮実装から始め、異なる例を追加して実装を一般化する（三角測量）。例えば見出しの判定なら、見出しになる行に加え、インデントした `*` の箇条書きやソースブロック内の行を確認する。新しい振る舞いを加える段階と、振る舞いを保って構造を整理する段階を区別し、コンパイルできない大きな変更を長く抱えない。

文書や単純な設定の変更では、その変更に合う内容・リンク・構文の確認を選ぶ。実装を写しただけのテストや、意味のない失敗を作る作業は増やさない。

Red・Green・Refactoring の各段階では、実行コマンド、期待する結果、実際の成否・失敗理由を検証記録に残し、計画からその記録を参照する。共通の実行情報は[入力・出力を絞る手順](../guides/agent-tools.md#agent-context)の形式で一度記録する。環境不備やコンパイル失敗は、期待した振る舞いの欠落による Red と区別する。

既存動作を確かめる回帰テストが最初から成功した場合は、その結果を記録し、実装変更が必要かを判断する。既に満たしている条件を Red にするためだけに実装を壊さない。テストの検出能力を確かめる一時変更は、下記の[テスト自身の検証](verification.md#test-quality)として区別し、確認後に元へ戻す。

## 完了条件と報告

完了時には次の短いチェックリストを使う。

- [ ] 合意した受け入れ条件を満たし、変更範囲の既存動作を維持した。
- [ ] 変更に合う自動テスト・静的解析・ビルド、または文書の検証を実行し、結果を確認した。
- [ ] CI と E2E について、確認済みの結果、該当しない項目、未実行・未確認の項目を区別した。
- [ ] 利用経路や UI の変更では、対象となる利用者・環境、アクセシビリティと使いやすさに関する自動検証の範囲、残る問題・未対応事項を記録した。
- [ ] 責務・境界・依存先を変える場合は、品質を保証する範囲とリスクを見直し、必要な検証・設計説明・図を更新した。
- [ ] 必要な文書と設計判断を更新し、差分・成果物にローカル専用資料、個人のメモ、認証情報を含めていない。
- [ ] [レビューチェックリスト](review.md#review-checklist)の結果と根拠を記録し、修正必須の指摘を解消した。対象外と未確認を区別し、残るリスクの判断と後続対応を記録した。
- [ ] 残る課題と次の作業を明示し、Git の操作を依頼の範囲内で行った。

未実行・未確認の項目は理由と次の確認方法を残す。必須の検証が失敗している変更は統合しない。未確認を含む作業報告はできるが、検証済みとは報告しない。

agent へ依頼するときも、目的・受け入れ条件・変更範囲・検証手段を共有する。生成されたコードやコマンドも差分と実行結果で評価し、理解とレビューを省略しない。コミット・push・PR 作成・マージは[Git 運用規約](git.md)と依頼の実行範囲に従う。

完了報告は次の項目を基本にする。自動テスト、CI、E2E、ユーザーからの報告は、それぞれ確認した主体と範囲が分かるようにする。

```text
変更: 目的、変更後の振る舞い、主な設計判断
ローカル検証: 実行コマンド、結果、確認したレポート
CI: 対象コミット、run の URL、結果（未実行なら理由）
E2E: 対象 SHA・APK SHA-256、エミュレーター・OS、シナリオと期待結果・実際の結果
利用者からの報告（得られた場合）: 期待結果・実際の結果、公開可能な再現条件、残る問題
未確認・残る課題: 理由、影響、次の確認方法
Git 操作: コミット・push・PR・統合の実施範囲
```

長期に残す検証記録は `docs/records/verification/YYYY-MM-DD-short-description.md`（開発フローの比較は `docs/records/evaluations/`） に置く。日常の結果は PR へ記載してもよく、同じ記録を複数箇所へ転記しない。端末識別子、個人のファイル名・内容・URI、画面構造・画像などのローカル専用情報は公開記録へ含めない。

## 開発フローを小さく改善する

機能の区切りや不具合修正の後に、発見が遅かった問題、手作業、CI・レビューの待ち時間を振り返り、次の改善を一つ選ぶ。繰り返す確認は、リスクと保守コストに応じて自動化する。

- テストや CI が遅くなったら所要時間を測り、速い検証を先に得る。接続確認の役割を残したうえで、独立した処理の並列化やテストの配置を見直す。
- ビルド・CI・補助スクリプトも本体と同じくレビュー・検証する。入力・出力・失敗箇所を明確にし、ローカルと CI の処理を別々に複製しない。
- 依存と開発環境の更新は、[依存・開発環境の更新方針](../maintenance/dependencies.md)に従って判断する。更新を小さな変更として、設定・CI・環境手順を合わせ、共通検証と必要な E2Eを行う。
- 証明書・ドメインなど期限のある資産を利用する場合は、更新期限と担当を明確にし、期限前に確認する予定を設ける。バックアップを運用する場合は、実際に復元できることを定期的に確認する。
- 読みづらい箇所に加え、履歴で頻繁に変わる複雑な処理や、一緒に変更されるファイルを調べ、改善先を選ぶ。機能数やコード量の増加だけで開発の成果を判断しない。
- 集中作業と休憩、短い学習と知識共有の時間を確保する。繰り返し調べる手順や判断理由は、次の担当者が見つけられる場所へ残す。
- 例外・暫定対応を設ける前に、規則を守れる別案を検討する。
- 例外・暫定対応には、対象・理由・代替の確認方法・見直し条件・解消条件と、追跡先の Issue や文書を残す。警告の抑制や検証の緩和で失敗を隠さない。
