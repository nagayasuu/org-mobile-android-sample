# 検証の基準

変更種別ごとの検証範囲・実行条件・合否基準の正本。実行方法は [Android の手引き](../guides/android.md)、文書・補助ツールは [agent ツールの手引き](../guides/agent-tools.md)を参照する。

## 4. 必要な層でテストし、共通の検証を通す

自動テストは準備・実行・検証（Arrange-Act-Assert）が読み取れ、入力と期待結果から仕様が分かる形にする。内部の呼び出し順やクラスの配置へ過度に依存させず、同じ誤りを重複して検証するより結果を左右する条件を選ぶ。

| 検証の層 | このアプリでの役割 |
| --- | --- |
| 高速な JVM テスト | org 解析、UTF-8、空入力、不正入力、対応外構文などの変換と境界条件を確認する |
| Robolectric のテスト | ViewModel の状態、URI からの読み込み、画面表示・回転・取り消し・再読み込みなど、Android 部品との連携を確認する |
| E2E | API 37 の専用エミュレーターで標準ファイル選択から表示まで、取消・回転・読み込みエラーからの復帰を検証する |

利用経路の検証は下記の E2E に集約する。既存の JVM・Robolectric テストは、解析や Android 部品の境界条件を早く検出する共通検証として維持する。Robolectric の成功と、標準ファイル選択を通した E2E の成功は区別する。

## 自動 E2E テストを導入する

標準ファイル選択を含む主要操作を、次の方針で自動化する。`ReaderE2eTest`、API 37 の Gradle Managed Device、手動 CI `Android E2E` を導入した。採用バージョン、実行環境、コマンドと検証範囲は[自動 E2E の手引き](../guides/android.md#自動-e2e-テスト)と[導入記録](../records/verification/2026-11-05-e2e-tests.md)を参照する。

| 項目 | 採用する方針 |
| --- | --- |
| ツール | 標準ファイル選択の操作に [UI Automator](https://developer.android.com/training/testing/other-components/ui-automator)、アプリ内の操作・検証に [Espresso](https://developer.android.com/training/testing/espresso) を使う |
| 初期環境 | 標準ファイル選択を備えた API 37 のエミュレーターを使い、[Gradle Managed Devices](https://developer.android.com/studio/test/managed-devices) で構成を管理する |
| 入力 | テスト環境の端末へ配置した公開サンプルと合成文書を使う |
| 実行契機 | 初期はローカルと CI の手動実行。安定後に週次実行を追加し、PR の必須化は実行時間・安定性から判断する |
| 合否判定 | 期待する表示・状態と異なる場合と、タイムアウトした場合は失敗とする。成功するまでの再実行で済ませない |

初期シナリオは次の3つとし、現在は後述の5件を加えた8シナリオを実装している。

1. **ファイル選択から表示まで。** 標準ファイル選択でサンプルを選び、読み込み後の日本語・見出し・本文・リストの表示と、長文の末尾へのスクロールを確認する。
2. **取り消し・画面回転後の保持。** 文書の途中までスクロールしてから選択を取り消し、文書と閲覧位置が保持されることを確認する。画面回転後も同様に確認する。
3. **読み込みエラーからの復帰。** 不正 UTF-8 の合成ファイルを選んでエラー表示を確認し、正常な文書を再選択して読み込み・表示へ復帰できることを確認する。

追加シナリオは、空文書からの復帰、同じファイルの更新後の再読み込み、1万項目の末尾表示、文字・表示サイズと端末の夜間設定・回転、ATF と見出しノード属性の検査である。条件と保証範囲は[自動 E2E の手引き](../guides/android.md#入力初期化合否)に記す。

この E2E では実際の標準ファイル選択と端末上の文書へのアクセスを通す。テストごとのアプリ状態・文書・権限の初期化と後片付け、非同期の読み込み完了の条件待ち、各操作のタイムアウトは手引きに従う。固定時間の待機だけに頼らず、操作・表示のどの段階で失敗したかを追える結果を残す。個人のファイルやアカウントを含まない専用のテスト環境を使う。

実機での手動スモークテストは開発工程に含めない。Dropbox 保存・クラウド接続など、E2E で扱っていない条件は未対応として残す。確認が必要な利用経路は、公開可能な入力と再現条件を整え、E2E シナリオへ追加する。

導入する変更では、依存・テスト・端末構成・CI 定義をそろえ、採用バージョン、システムイメージ、入力の配置・初期化方法、実行コマンド、タイムアウト、レポートの場所を[ビルド・検証の手引き](../guides/android.md)へ記録する。対象コミット・APK・実行環境と各シナリオの成否を残し、エミュレーター上の結果を実機で確認済みとは扱わない。

### E2E の未対応条件と追加方針

現在の E2E は8シナリオであり、次の条件は未対応である。手動の実機確認を削除したことで検証済みにはならない。

空文書、更新後の再読み込み、1万項目の末尾、表示設定とノード属性の自動検査は対応済みである。過去の実機での確認結果は[コード見直しと実機検証の記録](../records/verification/2026-11-01-code-review.md)に残し、現在の E2E の保証範囲とは区別する。

| 未対応条件 | 追加方針 |
| --- | --- |
| Dropbox 保存・実際のクラウド接続 | 利用者の専用環境は未準備。[準備条件](../guides/android.md#dropbox-経路の準備未実装)を満たした段階で再検討する。接続 E2E は未実装 |
| 大容量の性能基準 | 1万項目の末尾検証と Debug の単発参考値は追加済み。Release 相当の反復計測、基準値・許容値、ピークメモリは未対応 |
| TalkBack・支援技術の音声・読み順・使いやすさ | ATF、見出し属性、文字200%・密度4/3倍・端末夜間設定の検査は追加済み。音声や主観的評価、全設定の組み合わせ、暗色テーマ対応は保証しない |
| Pixel 10a など実機固有の挙動 | API 37 エミュレーターの成功から一般化しない。必要な OS・環境の自動検証方法を追加検討する |

保守担当者は、該当する利用経路・表示・依存を変更するときにこの一覧を見直し、
対象条件とシナリオの追加方針を受け入れ条件へ記録する。追加した条件だけを一覧から外し、
実行した結果・環境を残す。手動スモークテストを再び完了条件にしない。

## テストの十分性と、テスト自身の変更

テストの十分性は、誤りの起こりやすさと影響から判断する。固定値を返す、末尾の項目を落とす、エラーを無視するなど、明らかに誤った実装でも成功できないかを検討する（悪魔の代弁者）。重要な保証やテストの変更では、必要に応じて実装を一時的に変え、意図したアサーションで失敗することを確認する。調査用の変更は取り除き、正しい実装で再実行してから確定する。

このアプリで検出能力を確かめる代表例は次のとおり。

| 一時的に加える誤り | 確認する保証 |
| --- | --- |
| 見出しレベルを常に1にする | 深さの異なる見出しを区別し、正しいレベルを返す |
| 文書の最後のブロックを落とす | 末尾の件数・内容を保持する |
| 不正 UTF-8 を置換文字として受け入れる | 内容を黙って変えず、文字コードの誤りとして拒否する |

テストオラクル（結果の正しさを判定する基準）も点検する。件数だけで内容の欠落を見逃したり、同じ実装を通した二つの結果の比較で共通の誤りを見逃したりしないよう、期待値は仕様に基づき、実装とは独立に定める。誤実装で成功してしまった場合は入力とアサーションを見直し、狙った保証の違反で失敗することを確かめる。コンパイル失敗や環境エラーは検出能力の確認に数えない。

テストのケース・アサーションは、既存の保証を保ちながら追加する。テストのヘルパー抽出などの構造整理では本番コードを固定し、本番コードの整理ではテストを固定する。可能な限り別のコミットに分け、同時変更が避けられない場合は、上記の検出能力の確認を行う。

## カバレッジ計測を導入する

カバレッジ計測は、検証が薄い箇所を探すために使う。以下の計測方法・対象・合否条件を採用する。JaCoCo の計測設定・HTML／XML 生成・CI 判定を実装し、ローカル検証に加えて GitHub Actions で正常系・閾値割れと低下の拒否・一時コード撤去後の復帰・統合後 main の成功を確認した。コマンドは[ビルド・検証の手引き](../guides/android.md#カバレッジ計測)、結果は[検証記録](../records/verification/2026-11-03-coverage.md)を参照する。

### 計測方法と対象範囲

[AGP 標準の JaCoCo 連携](https://developer.android.com/studio/test/coverage-report)を採用し、Debug ビルドの JVM テストから始める。`enableUnitTestCoverage` と `createDebugUnitTestCoverageReport` を使用する。Robolectric の動的クラスも計測するため、アプリの名前空間に限定して `includeNoLocationClasses` を有効にしている。AGP・Gradle・内蔵 Kotlin・Robolectric の更新時にも、既存テストの成功と、実際に対象コードの実行がレポートへ反映されることを確認する。Kotlin の表示・フィルターや設定の保守負担に問題がある場合は、[Kover](https://kotlin.github.io/kotlinx-kover/gradle-plugin/) を代替候補として比較し、採用方針を変更する理由と互換性を記録する。

| 項目 | 初期導入の範囲 |
| --- | --- |
| 実行するテスト | Debug の JVM テスト全体。通常の単体テストと Robolectric のテストを含み、プロパティテストの追加後はそれも含める |
| 計測するコード | `app/src/main` のアプリ実装。解析・デコードだけでなく、ViewModel・ファイルアクセス・画面と表示処理も対象にする |
| 指標 | 行カバレッジ・分岐カバレッジ。全体とクラス・ソース別の未実行箇所を確認する |
| レポート | 人が確認する HTML と、CI で集計できる XML。標準タスクで不足する形式や除外設定は、必要なレポートタスクで補う |
| 初期対象外 | 端末上の手動操作、instrumented test、Release のカバレッジ。既存の Release テスト・ビルド・E2E の役割は維持する |

Android の生成コード（`R`、生成される場合の `BuildConfig` など）、テストコード、依存ライブラリは集計対象から除外する。アプリ自身の判断を含むコードを達成率のために除外せず、除外パターンと理由を記録する。Kotlin の生成コードやインライン処理に由来する表示は実装と照合し、クラス名の広いパターンで実際の処理まで除外しない。

### レポートの使い方と他のテストとの関係

同じテスト範囲・variant・ツールの版・除外条件で、行・分岐のレポートを比較する。初期は `OrgParser`・`DocumentDecoder` の境界条件と、読み込み失敗・再試行・状態保持に関わる未実行箇所を優先する。入力と期待結果を説明できる不足ケースを追加し、実際に誤りを検出できるかを確かめる。

- カバレッジは実行された範囲を示す。アサーションの正しさや検出能力は、具体例・プロパティテストとミューテーションテストで補う。高い達成率だけを完了条件にしない。
- [JaCoCo の分岐カバレッジ](https://www.jacoco.org/jacoco/trunk/doc/counters.html)は例外処理を分岐として数えない。不正 UTF-8、権限喪失、読み込み例外などは、レポートに加えて対応するテストと期待結果を確認する。
- 部分的なテスト実行のレポートは調査用とし、全テストの基準値と区別する。instrumented E2E の結果は JVM カバレッジへ含めず、異なる variant の割合を単純に足し合わせない。
- ミューテーションテストは別の実行として扱い、変更された実装の計測結果を通常のカバレッジへ混ぜない。計測エージェントの併用が検証へ影響しないよう、導入時に実行設定を確認する。

### 合否判定

最低カバレッジと、変更によるカバレッジの低下を CI で判定する。次の両方を合格条件とし、満たさない場合はパイプラインを失敗させ、PR のマージを止める。

- **最低カバレッジは80%とする。** 上記の除外条件を適用した `:app` の Debug 全体について、行カバレッジ・分岐カバレッジのそれぞれが80%以上であることを求める。丸め前の値で判定し、クラスごとの一律80%は初期条件にしない。
- **変更対象のカバレッジを低下させない。** PR ではマージ先ブランチの最新コミット、`main` 更新時は更新前の `main` のコミットを基準にする。比較可能な変更対象の既存ソースファイル群について、変更前後の行・分岐カバレッジをそれぞれ比較し、いずれも低下していないことを求める。基準側と変更側は同じファイル群・variant・ツールの版・除外条件・テスト実行条件で計測する。新規ファイルも全体の80%判定の集計に含める。

初回など比較元がない場合は、低下の判定を未実施と明記し、80%の最低条件は適用する。分岐がないなど指標の分母が0の場合は対象外と明示し、実行データの欠落を対象外や合格として扱わない。閾値割れや低下が見つかったら、意味のある動作を検証するテストを追加する。除外の拡大や閾値の引き下げを改善の代わりにしない。

### CI と導入の順序

1. 既存テストによる初回の HTML・XML レポートをローカルで生成し、採用ツールの版、対象・除外条件、対象コミット、行・分岐の値、計測による実行時間の増加を記録する。実行済みの処理が未計測になっていないか、ソースとの対応を確認する。
2. ローカルでは専用コマンド、PR と `main` 更新時は CI で Debug の計測・レポート生成・合否判定を実行し、既存の検証レポートとともに成果物として保存する。同じテストを計測用・通常用に重複実行する必要がないかを確認し、共通のビルド・検証を維持した実行順序にする。PR の比較元コミットを記録し、マージ先が更新されたら比較し直す。
3. 当該実行で生成したデータだけを使い、古いレポートを今回の結果として公開しない。テスト失敗で生成されなかった場合は未生成と報告し、テスト結果と原因を確認する。テスト成功後の計測・レポート生成の失敗や成果物の欠落は CI で検出する。
4. 80%未満や変更対象の低下を検出して失敗することと、条件を満たす状態で成功することを確認する。初回計測が80%未満なら、必要なテストを追加してから合否判定を含む変更を統合する。PR では未実行行・分岐とアサーションの内容も確認する。マージを止めるための必須 CI チェックを GitHub 側でも設定し、ワークフローの追加だけで保護が有効になったとは扱わない。

計測設定・レポートタスク・CI を追加する変更で、採用バージョン、対象・除外範囲、実行コマンド、HTML・XML と実行データの場所、確認方法を[ビルド・検証の手引き](../guides/android.md)へ記録する。具体的なタスク名・出力先は現在のビルドで検証してから実行手順へ載せる。文書へ方針を追加したことだけで計測済みとは扱わない。

## プロパティベーステストとミューテーションテストを段階的に導入する

プロパティベーステスト（property based testing）は org 解析・UTF-8 デコードへ導入し、ミューテーションテスト（mutation testing）は同じ範囲で試験導入する。前者は多数の生成入力で仕様上の性質を確かめ、後者は実装へ小さな誤りを加えて既存テストが検出できるかを調べる。既存の具体例テストを維持し、両手法を補完的に使う。

プロパティベーステストは以下の対象・構成・実行回数・合否条件で導入済みであり、通常の JUnit 4 テストとして共通検証と PR の必須 CI に含める。採用バージョン、入力サイズ上限、seed の再現コマンドは[ビルド・検証の手引き](../guides/android.md#プロパティベーステスト)、実行結果と未確認事項は[導入記録](../records/verification/2026-11-04-property-tests.md)を参照する。ミューテーションテストはローカルの手動タスクとして試験導入済みで、改善後の31件すべてを検出できたため最低スコアを100%とした。構成・実行方法は[手引き](../guides/android.md#ミューテーションテスト)、比較結果・閾値の根拠・CI の判断は[導入記録](../records/verification/2026-11-04-mutation-tests.md)を参照する。

### 対象とプロパティの設計

最初は `:app` 内の `OrgParser` と `DocumentDecoder` を対象にし、端末や Android の画面を起動しないローカル JVM テストで実行する。画面、ファイル選択、状態復元、実際のプロバイダーとの連携は、Robolectric と E2E で確認する。モジュール分離は初期導入の前提にせず、Android のビルド設定との接続が保守負担になる場合に純 Kotlin/JVM モジュールへの分離を検討する。

この2つを初期対象にする理由は、多様な入力の組み合わせを生成しやすく、仕様から期待結果を定められ、Android の画面や外部 I/O を使わずに多数のケースを実行できるためである。`OrgParser` では構文・字下げ・改行などの組み合わせ、`DocumentDecoder` では正常な UTF-8 の内容保持と不正なバイト列の拒否を確かめる。これはコード構造と入力の性質に基づく優先順位であり、他の対象との検出効果・実行速度の比較測定による選定ではない。

適用範囲をこの2つへ固定しない。状態管理の検証不足や不具合が見つかった場合は、`ReaderViewModel` の状態遷移へ適用を広げる。成功・失敗・再試行・連続選択などの操作列に対し、表示文書と保存 URI の整合性を確かめる。その際は各ケースの状態初期化、coroutine の実行制御、期待する状態遷移のモデルを用意する。解析・デコードのプロパティテストだけでアプリ全体の入力・状態の組み合わせを十分に検証したとはみなさない。

プロパティベーステストには [Kotest Property](https://kotest.io/docs/proptest/property-based-testing.html) を使い、既存の JUnit 4 を維持する。テスト依存に `kotest-property` を追加し、既存の `@Test` 内で `runTest` と `checkAll` を使う構成から始める。採用バージョンと依存関係の互換性は導入時に検証する。

| 対象 | 生成する入力と前提 | 確認する性質 |
| --- | --- | --- |
| 見出し | 深さ、空でない改行なしのタイトル、日本語・絵文字 | `*` の数がレベルになり、タイトルが保持される |
| 箇条書き | マーカー、空白・タブによる字下げ、改行なしの本文。`*` の箇条書きには字下げを付ける | 種別・本文・インデントが仕様どおりになる |
| 改行・BOM | BOM と CR を含まない文書から CRLF 版、先頭 BOM 付き版を作る | 元の LF 版と解析結果が等しい |
| リテラルブロック | 見出し・リスト風の本文、ブロック名の大小文字。本文には対応する終了行を含めない | ブロック内を構文として解釈せず、終了後は通常解析へ戻る |
| UTF-8 | 孤立サロゲートを含まない Unicode 文字列、既知の不正バイト列を含む入力 | 正常時は UTF-8 経由の結果が直接解析と一致し、不正時は文字コードの例外になる |
| 解析の独立性 | 異なる文書 A・B を作り、A → B → A の順に解析する。未終了のリテラルブロックや空文書も含める | 各文書の仕様から定めた結果と一致し、前回の段落やブロック状態が混ざらない |

入力は仕様から構文を組み立て、完全なランダム文字列だけに偏らせない。空入力、境界値、対応外構文、不正入力も明示的に含め、生成する文字列長・文書量に上限を設ける。本番と同じ正規表現や判定処理で期待値を計算せず、深さとタイトルから `Heading` の期待値を作るなど、仕様から結果を定める。

改行・BOM の変換前後の一致と、UTF-8 経由・直接解析の一致は、既存の具体例テストを多様な入力へ広げる性質として使う。内容の保持については、見出しやリストと解釈されないよう固定の接頭辞を付けた改行なしの合成本文を UTF-8 で読み、元の本文を持つ `Paragraph` が返ることも確認する。両方の経路に共通する欠落を、経路間の一致だけで見逃さないためである。

失敗時は [shrinking](https://kotest.io/docs/proptest/property-test-shrinking.html) で簡単になった反例、[seed](https://kotest.io/docs/proptest/property-test-seeds.html)、生成回数、ツールの版を記録して再現する。見つかった反例は具体例の回帰テストへ追加する。入力は公開可能な合成データを使い、私的な文書を失敗ログや CI 成果物へ含めない。

合否判定は、定義した性質に反する入力が1件でも見つかったら失敗とする。成功するまで再実行して済ませず、記録した条件で原因を調べ、修正後に反例と関連テストを確認する。

### ミューテーションテストの構成と評価

[PIT 1.30.1](https://github.com/hcoles/pitest/releases/tag/1.30.1) を採用する。[pl.droidsonroids.pitest](https://github.com/koral--/gradle-pitest-plugin) 0.2.27 は AGP 9.2.1 で `applicationVariants` を参照して構成に失敗したため、専用の Gradle 初期化スクリプトから [PIT CLI](https://pitest.org/quickstart/commandline/) を起動する。通常のテストタスクのクラスパスを再利用し、JaCoCo の JVM 引数は引き継がない。Kotlin が生成するコードによるノイズを評価し、必要に応じて [Arcmutate Kotlin plugin](https://docs.arcmutate.com/docs/kotlin.html) の利用を検討する。今回の31件には未解決のノイズが残らず、追加の有償プラグインは導入しない。導入する場合は利用条件・ライセンスを確認し、ライセンスファイルなどの秘密情報はコミットや公開成果物へ含めない。

初回は変更対象を `OrgParser` と `DocumentDecoder`、実行テストを対応する具体例・プロパティテストへ絞り、PIT の既定の変更演算子から始める。Android・Kotlin の生成コードや単純なデータ保持を初期対象へ広げない。Robolectric を使うテストへの拡大は、[専用の Android 対応](https://docs.arcmutate.com/docs/android.html)とその利用条件・制約を確認してから判断する。

- 生き残った mutation は、仕様上の誤りを見逃しているもの、元と同じ振る舞いになるもの、生成コードなどによるノイズを区別する。意味のある不足からテストを改善し、除外には理由を残す。
- タイムアウト・実行エラー・未実行は、意図したアサーションによる検出と分けて記録する。変更前の正しい実装でテストが成功することも確認する。
- 現在の最低 mutation score は100%。PIT のスコア判定に加えて XML の全件が `KILLED` であることと、両対象クラスの mutation が存在することを確認する。対象・演算子・版を変更するときは、生き残った変更のレビューで重要な検証不足を修正し、実行時間、意味のある不足の発見数、ノイズ、調査・保守時間から閾値・継続利用・対象拡大を再判断する。
- [既定の変更演算子](https://pitest.org/quickstart/mutators/)が正規表現内の構文を網羅するとはみなさない。高い score だけで構文の検証が十分とは判断せず、「見出しレベルを固定する」「最後の段落を落とす」などの代表的な誤実装を検出できるかも導入時に確認する。一時的な変更は残さない。

### mutation score の閾値を決める手順

mutation score は、生成した変更のうちテストで検出できた変更の割合を示す。カバレッジで採用した80%をそのまま適用せず、次の手順で維持すべき検出能力を確認してから、固定閾値の数値を決定する。初回はこの手順で100%を採用済みであり、対象・条件を変更する際も同じ手順で見直す。

1. **計測条件を固定する。** 対象コード、変更演算子、ツール・プラグインの版、除外条件、プロパティテストの seed・生成回数・入力サイズ上限を記録する。採用ツールが score の分子・分母へどの状態を含めるかも確認し、異なる集計方法の値を混同しない。
2. **初回結果をレビューする。** score と変更の件数・内訳を確認し、生き残った変更をテスト不足、元と同じ振る舞い、生成コード由来のノイズに分ける。除外する場合は根拠を記録し、計測設定へ反映する。タイムアウト・実行エラーはアサーションによる検出と分け、原因を確認する。
3. **重要な見逃しを修正する。** 不正 UTF-8 を受け入れる、見出しレベルを誤る、文書の末尾を落とすなど、仕様上重要な誤りを見逃している場合は、期待する振る舞いを検証するテストを追加する。
4. **改善後の実測値から最低値を決める。** 同じ条件で再計測し、レビューした結果を維持できる下限を固定閾値にする。余裕を設ける場合も理由を記録する。対象・集計方法・閾値・決定理由を文書と実行設定へ反映し、閾値未満で失敗することを確認する。

閾値の導入後は「score が閾値以上」と「重要な振る舞いを壊す変更を見逃していない」の両方で判断する。score が高くても重要な見逃しは修正対象とし、実行エラーや計測の欠落を合格として扱わない。ツール・変更演算子・対象・除外条件を変える場合は、結果の比較可能性と閾値の根拠を見直し、合格させるためだけに閾値を引き下げない。

### 実行頻度と導入の順序

プロパティベーステストは早い段階で反例を発見するため、開発中の関連する性質と、PR 作成・更新時の対象の性質を、それぞれ各1,000例検証する。最終受け入れでは、受け入れ対象コミットの CI 成功を確認する。週次・任意の探索専用の実行枠は設けない。失敗調査では記録した seed による再現を行う。

1,000例は実測前の初期値であり、検証の十分性を保証する数値ではない。導入時に実行時間と検出効果を確認し、生成する入力とサイズ上限も評価する。回数や入力サイズ上限を見直す場合は、理由と検出能力への影響を記録する。

| 実行契機 | プロパティベーステスト |
| --- | --- |
| 開発中 | 関連する性質を各1,000例 |
| PR 作成・更新時 | 対象の性質を各1,000例、seed を記録 |
| 最終受け入れ | 受け入れ対象コミットの CI 成功を確認 |

ミューテーションテストの実行頻度は引き続き次の試験導入方針とする。

| 実行契機 | ミューテーションテスト |
| --- | --- |
| 開発中 | 必要なクラスだけ手動実行 |
| PR | 初期は任意。運用が安定したら対象変更時に実行 |
| 定期・手動 | 対象範囲を一通り実行し、レポートを保存 |

通常のプロパティベーステストは seed を変えて探索範囲を広げ、失敗時は記録した seed で再現する。ミューテーションテスト内では seed・生成回数・入力サイズの上限を固定し、mutation ごとに入力が変わって結果や実行時間の比較が難しくなることを避ける。

以下は初期導入時の手順である。1と3のプロパティベーステストの実装・ローカル検証は[導入記録](../records/verification/2026-11-04-property-tests.md)に残し、対象コミットの CI 確認は最終受け入れ時に行う。ミューテーションテストの比較・検出能力確認は[導入記録](../records/verification/2026-11-04-mutation-tests.md)に残した。ローカルの手動利用を継続し、CI の組み込みは継続実行の安定性と保守負担を確認して再判断する。

1. 解析・デコードへ4〜6個のプロパティテストを追加し、既存の具体例テストと共通のビルド・検証を通す。
2. 同じ対象でミューテーションテストを試し、対象コード・変更演算子・seed・生成回数などの条件をそろえて、既存テストだけの場合とプロパティテスト追加後の検出能力・実行時間を比較する。
3. プロパティベーステストは導入時に通常のローカル検証と PR 作成・更新時の CI に組み込み、1件の反例でも失敗することと、記録した seed で再現できることを確認する。最終受け入れでは対象コミットの成功結果と対応付ける。ミューテーションテストは試験導入の効果と保守負担が見合えば CI に組み込む。依存・専用タスク・CI 定義と同じ変更で、採用バージョン、対象・除外範囲、入力サイズ上限、生成回数と seed の指定方法、実行コマンド、レポートの場所を[ビルド・検証の手引き](../guides/android.md)へ記録する。文書に方針を書いたことだけで、実装・検証済みとは扱わない。

## 共通の検証

文書の機械的な検証には[文書検証の共通ツール](../guides/agent-tools.md#document-tools)、長い実行ログには[ログ保存と結果集約](../guides/agent-tools.md#check-output)を利用できる。内容の正しさや必要な検証範囲は、以下の基準と対象差分から判断する。

実装中は関連テストで早く結果を得て、アプリ・テスト・ビルド設定の変更は完了前に以下を実行する。

反復中は `git diff --stat` と対象差分から検証を選ぶ。解析なら `OrgParserTest`、状態管理なら `ReaderViewModelTest` を[個別実行](../guides/android.md#共通のビルド検証コマンド)し、Python 補助ツールなら `python3 -m unittest discover -s scripts/tests -p test_agent_tools.py -q` など関連ファイルを先に実行する。ログは `run_check.py` で保存する。対象を絞った成功を、完了前の共通検証や必要な CI・E2E の代わりにしない。Python 補助ツールだけの変更では `python3 -m unittest discover -s scripts/tests -q` と文書検証・差分確認を行い、Android の再ビルドは必要としない。

```sh
./gradlew --console=plain check assembleDebug
```

Debug / Release の JVM テスト、Lint、Debug APK を確認する。環境、個別実行、レポートの場所、警告の扱いは[ビルド・検証の手引き](../guides/android.md)を参照する。Git フックとコミットメッセージ検証の導入・手動確認・テストは[Git 運用規約](git.md#自動検証と-git-フック)に従う。文書だけの変更では内容・ローカルリンク・`git diff --check` を確認し、APK の再生成や E2E の再実行を必須にしない。文書内のコマンドや設定値を変えた場合は、対応する実装・定義と照合する。

### 検証結果を再利用する条件

過去の結果を使う場合は、実行者、対象コミットまたは差分ハッシュ、コマンド・対象範囲・入力、環境・ツール・依存の版、比較元、成否と根拠の保存先を確認する。前回から今回までの変更が、対象コード・テスト・設定・入力・依存先や保証範囲へ影響しないことを照合し、今回に有効と判断した理由を記録する。

影響がある、条件が異なる、必要な記録が不足する場合は関係する検証を再実行し、実行できなければ未確認として理由と次の確認方法を残す。別の実行者の結果の参照と、自身の今回の実行を区別する。今回の実行で再生成することを求めるレポートの鮮度要件や、更新後の必須 CI を、過去の成功で代替しない。既読資料の再利用は別の判断であり、過去の検証成功を意味しない。

## 品質の劣化を継続的に検出する

依存関係など、維持する必要がある品質を選び、次の手順で繰り返し確認できる形にする。

1. 対象と実行環境を固定し、変更前の状態と維持する条件を記録する。
2. 許可する依存方向などを検査で確認する。条件に違反した場合に誰が結果を確認し、何を修正・再検査するかを決める。
3. 自動化する場合は、ローカルのタスク・CI・実行手順・結果の保存先を同じ変更で整え、実際に範囲外の変更を検出できることも確かめる。実行時間や環境差のある検証は、高速なテストと分けて実行契機を記録する。
4. 機能・データ量・対象環境が変わったら、基準と測定方法を見直す。失敗が出た場合は原因を調べてから基準を更新し、変更理由を残す。

現行 CI には JVM テストとして依存構造検査を含める。性能計測の導入は当面見送る。性能の自動計測は未導入であり、機能 E2E の所要時間を性能の基準値として扱わない。

### 依存構造を自動検査する

依存構造の検査には [ArchUnit](https://www.archunit.org/userguide/html/000_Index.html) 1.5.1 のコアライブラリを採用し、既存の JUnit 4 の JVM テスト `ArchitectureTest` で実行する。アプリのコンパイル済みクラスの依存関係を検査し、現在の単一モジュール構成を維持する。`check` を通じて既存 CI の実行対象にも含まれる。ローカル検証と GitHub 上での実行結果は区別し、[検証記録](../records/verification/2026-11-03-architecture-checks.md)へ残す。

初期の依存規則は次の3つとする。

| 対象 | 守る依存規則 |
| --- | --- |
| `OrgParser` と `OrgBlock` | Android・画面・ファイルアクセスの実装へ依存しない |
| `DocumentDecoder` | Android・画面・文書プロバイダーへ依存しない。渡されたストリームの読み取りと、JDK の文字コード処理は許可する |
| `ReaderViewModel` | 画面クラスや `ContentDocumentSource` の具体実装へ依存せず、`DocumentSource` を介して読み込む。Android の ViewModel・状態保存機能への依存は許可する |

通常の JVM テストに含め、ローカル・PR・`main` 更新時に実行する。定義した規則への違反が1件でもあればテストを失敗させる。導入時に、正しい依存関係で成功することと、意図的に加えた依存違反を検出して失敗することを確認し、一時的な違反は取り除く。対象クラスを取得できていることも確認し、対象が空のため検査されなかった状態を成功として扱わない。

検査対象はソースファイル単位の import 一覧ではなく、各クラスの依存関係から定める。同じファイルに Android と関わるクラスがあっても、それだけで `DocumentDecoder` 自身の違反とは判断しない。対象に関連する内部クラスなどの扱いも導入時に確認し、実際の依存違反を広い除外で隠さない。

パッケージ・モジュールの境界を設ける際は、その境界に合わせた循環依存の検査を追加する。規則の維持だけを目的にパッケージやモジュールを増やさず、責務や依存方針を変更する場合は、変更理由と規則を合わせて見直す。実行時の失敗・キャンセル・資源解放などは、引き続き機能テストと E2E で検証する。

導入する変更で、採用バージョン、検査対象・除外条件、各規則の実装、実行コマンド、レポートの場所、違反を検出した確認結果を[ビルド・検証の手引き](../guides/android.md)へ記録する。

## 失敗・不具合を調べる

1. 操作、期待結果、実際の結果、対象コミット・成果物、環境を押さえ、公開可能な最小の再現データを用意する。
2. 仮説と予測する結果を一つ立て、条件を変えて確かめる。入力や処理を半分ずつ減らして最小の再現例へ近づけ、必要なら履歴の比較や `git bisect` で原因を絞る。分岐を追加する前に、不要な状態や処理を除く方法も検討する。
3. 可能なら修正前に失敗する回帰テストを追加し、原因を直して成功を確認する。既存 E2E で再現できない場合は、公開可能な入力・環境条件を整理し、自動化の未対応範囲と追加方針を残す。
4. 同じ原因の境界条件と関連する既存動作を確認する。調査用の変更や個人情報を含むログは公開差分へ残さない。

同時実行などで決定的な再現が難しい不具合は、実行時間や回数を決めた反復テストで検証する。高速なテストとは分け、実行条件と結果を記録する。検証中に失敗が出なかったことだけで、不具合がないとは判断しない。

同じ条件で成否が変わるテストは、競合・時刻・共有状態・外部 I/O などを調べる。成功するまで再実行して完了にせず、無効化を修正の代わりにしない。隔離が必要なら理由、失われる保証、代替の確認、復旧条件を記録し、必須検証の条件を満たすまでは統合しない。

調査が進まない場合は、一定時間で仮説・試したこと・分からない点を書き出し、説明や休憩を挟んで前提を見直す。ログは未処理例外、処理の成否、再現に必要な非決定的な条件や副作用へ絞り、個人の文書内容・ファイル名・URI は記録しない。純粋な計算の中間値をすべて残す方法は避ける。

## 5. CI と E2E で変更を確認する

<a id="ci-e2e-workflow"></a>

## CI・E2E の実行手順

短命の作業ブランチで変更を小さく共有し、最新の `main` と組み合わせた状態を検証する。ブランチや PR の扱いは[Git 運用規約](git.md)に従う。CI サーバーの存在に加えて、頻繁な統合と失敗への対応を開発の習慣にする。

半日程度で一貫した変更まで進められない場合は、作業の分割や未完成の経路を隠すフラグを検討する。この目安で分割を見直しつつ、統合に必要な検証とレビューを維持し、Git の操作は依頼された範囲で行う。

レビューでは受け入れ条件、境界条件、依存方向、失敗時の操作を確認し、作者以外が変更理由と処理を追えるかを確かめる。自動検証の成功に加えて、テストが見逃しそうな誤りも検討する。

十分に確認できない大きさの変更には、分割を求める。変更に関係するテストや操作を実行して確かめる。実行できなかった範囲は未確認として共有する。

- 指摘は、修正必須の問題と改善提案を区別する。
- 指摘には理由を添え、必要に応じて具体的な代替案を示す。
- 意見が分かれた場合は、受け入れ条件・検証結果・変更リスクを基準に判断し、採否の理由を残す。

作成者のセルフレビューと、別の担当者によるレビューでは、以下の[レビューチェックリスト](review.md#review-checklist)を使う。PR 作成前に確認し、指摘への修正や対象コミットの更新後には、影響する項目を再確認する。結果は [PR テンプレート](../../.github/pull_request_template.md)へ記録する。PR を作らない段階では、同じ形式を作業メモや完了報告で使ってよい。

1. ローカルの検証後に、依頼された範囲で push・PR 作成を行う。PR には問題、変更後の振る舞い、理由、検証結果と未確認事項を書く。
2. GitHub Actions で対象コミットの結果とレポートを確認する。PR の検証後に `main` や対象コードが更新された場合は、必要な検証をやり直す。
3. UI、ファイルアクセス、状態復元、依存や SDK など利用経路へ影響する変更では、[自動 E2E](../guides/android.md#自動-e2e-テスト)を実行する。対象 SHA・APK SHA-256、エミュレーター・OS、シナリオ別結果とレポートを対応付ける。文書だけの変更では内容・リンク・差分を確認する。
4. 統合後も `main` の CI 結果を確認し、失敗時は修正または取り消しを優先する。

CI の `verify` には、Git フック・メッセージ検証処理のテスト、コミットメッセージと PR タイトルの検証、ビルド・Lint・JVM テストと Debug APK・レポートの保存を定義している。必須チェックとブランチ保護は下記の確定方針に沿って GitHub 側にも設定する。ワークフローを記述したことだけで有効になったとは扱わない。Play ストア配信、Release 署名、本番への自動配信は未整備であり、必要になった時点で版の識別、署名・配布、データ互換性、復旧手順を整える。

E2E は初期運用としてローカルと `Android E2E` の手動起動で実行する。実行時間と安定性を確認するまでは PR の必須ジョブへ追加しない。CI を利用できない場合はローカルの専用エミュレーターで実行し、CI の成功と区別して記録する。

E2E が失敗した場合は、失敗した段階と入力・環境を調べて修正し、アサーションの緩和や無変更リトライで成功扱いにしない。未対応条件はシナリオ追加の課題として残し、実機での手動確認を代替工程にしない。

## 必須 CI とブランチ保護

`main` への統合は、PR と必須 CI の成功を通す。最新の `main` を取り込んで検証し、個人開発では人による必須承認を当面0人としてセルフレビューを行い、レビュー指摘を解決してから Squash merge する。管理者への適用、直接 push・強制 push・削除の禁止、マージキューの扱いなど、GitHub 側の具体的な保護条件は[Git 運用規約](git.md)へ集約する。

必須 CI は、現在の `Android checks` の `verify` ジョブを起点にする。現行の `check assembleDebug` によるビルド・Lint・JVM テストと成果物の保存を維持し、依存構造検査は JVM テストとして必須 CI の実行範囲へ含める。カバレッジ・プロパティベーステストの PR 実行は、それぞれ導入後に必須 CI の実行範囲へ含める。試験段階のミューテーションテスト、未導入の性能自動計測、初期の E2E は各節の実行方針を維持し、一律に PR の必須ジョブへ追加しない。

2026-11-01 に GitHub 側へ保護を適用し、実際のチェック名 `verify` と実行元 GitHub Actions（App ID `15368`）を登録した。REST API で保存された設定を再取得し、GraphQL API でも `main` に適用されるルールを確認済みである。同じ保護設定の一時ブランチで、管理者による条件未達の更新・マージの拒否と、条件を満たす PR の Squash merge を確認した。実際の `main` 向け PR #5 でも `verify` の成功を確認し、設定値・対象コミット・検証用 PR・CI run・保証範囲は[検証記録](../records/verification/2026-11-01-branch-protection.md)へ残している。以後も設定変更時は[Git 運用規約の確認手順](git.md#設定の維持と動作確認)に従い、設定の確認と PR での動作確認を区別する。

## 利用者が目的を達成できるかを評価する

利用者の目的を入力・操作・期待結果へ落とし込み、E2E シナリオで達成可否を検証する。
主要な課題は「保存した文書を開いて読む」「長い文書で閲覧を続ける」「取り消し・エラーから戻る」とする。
操作の見つけやすさや読み上げの自然さなど、現在の自動検証で判断できない品質は未対応として記録する。

実際に得られた利用者からの報告は、期待結果・実際の結果・公開可能な再現条件を整理し、
問題の重要度に応じて E2E の入力やアサーションへ反映する。
自動操作の成功を、人による使いやすさの評価まで実施した結果として扱わない。
利用者の操作や実機での観察を開発完了の必須工程にしない。
