# レビュー手順と判定基準

変更の確認者、R01〜R30、再確認、記録方法の正本。検証の選択は [検証の基準](verification.md)、結果の記入には [レビュー記録の様式](../templates/review-record.md)を使う。

<a id="review-efficiency"></a>

## レビューの負担と待ち時間を減らす

レビューは、一つの目的を入力・操作から結果まで追える大きさで依頼する。機能変更と無関係な整形・構造整理は分け、置き換えは途中でも検証できる単位にする。作者以外が変更理由と保守方法を説明できることを重視する。

日常の作業では[agent の入力と出力](../guides/agent-tools.md#agent-context)、[レビューチェックリスト](#review-checklist)、[agent レビュー手順](#agent-review)を使う。補足は、再レビューでは[確認の重点と根拠](#review-focus)、繰り返す指摘への自動検証の導入では[自動化の進め方](#review-automation)を読む。

<a id="review-focus"></a>

## 補足：確認の重点と根拠をそろえる

1. **依頼に必要な情報をそろえる。** 目的・受け入れ条件、対象版と差分、変更理由、影響する操作・依存先、既存の検証結果と未確認事項を渡す。agent には[依頼文のひな形](#review-request)を使い、今回重点的に確認する経路も添える。版や環境は今回の設定と照合する。
2. **壊れやすい経路へ時間を配分する。** 変更で起こり得る誤りと影響から、詳しく追う経路を選ぶ。例えば読み込みの変更では、連続選択の完了順序、失敗後の表示・保存 URI、権限喪失を優先する。データ・イベント・時間・量の観点を使い、E2E を含む自動テストで保証する範囲と未対応の範囲を分ける。R01〜R30はすべて判定し、重点外という理由だけで対象外にしない。
3. **根拠は一度記録して参照する。** 検証結果には識別子またはリンクを付け、実行者・対象版・環境・コマンド・結果を一か所へ記す。レビュー表ではその根拠を参照し、同じ結果と根拠の ID だけをまとめる。異なる理由の対象外や未確認を一括にしない。レビュー担当は参照先を直接確かめ、自身の実行と他者の結果の参照を区別する。
4. **再確認は更新差分と影響から決める。** 修正前後の版、解消する指摘、更新差分、影響する経路・項目を渡す。前回の記録を保持し、今回再確認した ID と、根拠の有効性を確かめて引き継ぐ ID を明記する。共通設定や依存先、比較元が変われば影響を見直す。初回の全項目判定と必須検証は維持する。

例えば同じ対象版で実行した文書検証を `V1` として一度記録し、R19・R25の根拠に `V1` を参照できる。ただし、差分の検証だけで未実行の CI や E2Eまで確認済みにはしない。

<a id="review-automation"></a>

## 補足：繰り返す指摘を自動検証へ移す

レビュー中に同じ種類の指摘が繰り返されたら、既存の作業メモや Issue に、公開可能な指摘例、対応する R 番号、発生条件、影響、繰り返しの状況を短く記録する。専用台帳や全指摘の転記は必須にしない。

1. **機械判定できる規則を選ぶ。** 合意した書式、確実な不具合、依存方向など、期待結果を説明できるものを候補にする。要求の妥当性、読みやすさ、リスクの受け入れなど判断が必要な確認はレビューで扱う。
2. **既存の検証へ組み込めるか調べる。** 現行の Lint、Git フック・メッセージ検証、テストを先に確認する。依存方向の検査は[検証の基準の「依存構造を自動検査する」](../workflow/verification.md#依存構造を自動検査する)に従い、未導入の検査を実行済みと扱わない。新しいツールは検出できる問題、誤検知、導入・保守の負担を比較して選ぶ。
3. **小さく導入して検出能力を確かめる。** 正しい例が成功し、意図した違反例が失敗することを確認する。既存違反が多い場合は対象範囲や基準値を明記して新しい違反を止め、既存違反の解消を別に進める。広い除外で新規違反を隠さず、例外には理由と再検討条件を残す。実装・検証コマンド・CI の実行契機・文書を同じ変更で更新する。
4. **負担が減ったかを見直す。** 導入前後で同種の指摘の再発、レビューの待ち時間・確認時間、誤検知への対応、検証時間・保守負担を比べる。変更の規模や種類も添え、速度や指摘件数だけを品質の評価にしない。効果が乏しい規則は対象や実装を見直す。

この節は運用手順であり、新しい検査ツールや CI 規則の導入、レビュー時間の短縮を確認した記録ではない。自動化を追加する際は対象版と実行結果を別に残す。

<a id="agent-review"></a>

## agent によるレビュー手順

agent が変更を作成・修正した場合は、完了報告前に本手順でレビューする。「レビューチェックリストを実施して」という依頼にも同じ手順を使う。変更全体を見て、次の基準で確認者を選ぶ。

- 文書の誤字・表記・リンクの修正だけで、意味、参照先の要件、コマンド、設定、権限、受け入れ条件、検証・レビュー基準を変えない場合は、作成 agent によるセルフレビューを認める。リンク修正では意図した参照先の内容も確認する。セルフレビューを選んだ理由を記録し、文書検証と R01〜R30の全件判定は行う。
- それ以外は、別のレビュー agent を利用できる場合は依頼する。利用できない場合は作成 agent が実施し、セルフレビューであることと制約を記録する。上記の条件に当てはまるか不明な変更もこちらに含め、一部だけを取り出してセルフレビューの例外を適用しない。

別 agent への依頼でも、確認範囲は渡した対象と実際に読んだ内容に限る。

AI を利用した変更では、新しい外部サービスの追加がなくても R12を判定する。既存の利用者確認を継承する場合は、今回の共有対象・利用先・環境がその範囲内かを照合し、確認元の記録を参照する。根拠が不足する場合は未確認とし、利用条件の監査済みとは断定しない。個別のアカウント情報・設定や私的資料を根拠へ転載しない。

1. **対象を固定する。** 作成 agent は目的・受け入れ条件・対象範囲・既知の未確認事項を整理する。レビュー agent は `git status --short`、現在のブランチ、対象の履歴を確認する。コミット済みの変更は比較元・先の SHA を記録し、`git diff <base>...<head>` など意図した差分を読む。未コミット変更は `git diff`、`git diff --cached`、`git ls-files --others --exclude-standard` で把握し、対象ファイル一覧と内容ハッシュなど変更を識別できる情報を記録する。無関係な既存変更とローカル専用資料は対象へ含めない。
2. **根拠を直接確かめる。** 公開の開発手順・Git 運用規約、差分、関連コード・テスト・設定を読む。作成 agent の説明は検証の手掛かりとし、参照先や実行結果と照合する。新しい API などが関係する場合は、対象版の公式資料を確認する。
3. **必要な検証を実行する。** 変更に合う既存のコマンドでビルド・Lint・テスト、または文書の内容・リンク・差分を確認する。既存の実行結果を使う場合は、[検証結果の再利用条件](verification.md#検証結果を再利用する条件)を照合し、レビュー agent 自身の実行と区別する。実行できない確認は理由と次の確認方法を記す。E2E の実行結果、利用者からの報告、外部サービスの契約条件、業務上のリスク受け入れなどは、証拠や判断権限がなければ未確認とする。
4. **30項目を判定する。** R01〜R30すべてに結果と根拠または理由を付け、該当しない項目も対象外として残す。同じ結果・根拠の ID だけをまとめてよい。指摘には ID、重要度（修正必須・改善提案）、ファイル・行、問題が起きる条件、影響、修正案を記す。見つからなかった問題を、存在しないと保証しない。
5. **修正と再確認を分ける。** レビュー agent は対象ファイルを変更せず、結果を作成 agent へ返す。必要な修正は作成 agent が行い、修正後の対象版と差分を渡して再確認を依頼する。セルフレビューでは実装と確認の段階を分ける。確認中に対象が更新された場合は更新内容を確認し、影響する項目を再判定する。
6. **結果を保存・報告する。** [PR テンプレート](../../.github/pull_request_template.md)の形式で、確認者、対象版、各 ID の結果、指摘と対応、残るリスク、判定を残す。PR がなければ作業メモや完了報告に残す。公開先への投稿は依頼の範囲に従い、レビューの依頼だけで PR へのコメント投稿、承認、マージを行わない。修正必須があれば「要修正」、必須確認や権限外の判断が残れば「未確認のため保留」とし、完了報告でもその範囲を明記する。

レビュー agent の「採用可」は、記載した対象と範囲についての確認結果である。GitHub の承認、必須 CI の成功、E2E の成功、リスクを受け入れる権限の代わりにはならない。agent が実行・判断できる範囲は、既存の指示と今回の依頼に従う。

<a id="review-request"></a>

## レビュー依頼文のひな形

```text
レビュー担当として、AGENTS.mdと開発手順の「作業に応じた読み方」に従って
共通事項・レビュー手順・対象に関係する節を読み、agentレビューを実施してください。
目的・受け入れ条件：<利用者の操作と期待結果>
対象：<比較元・先のSHA、または未コミット変更の対象ファイル一覧>
変更理由・影響範囲・重点的に確認する経路：<今回のリスクと選んだ理由>
計画がある場合：<計画の参照先、実施した手順、計画を変更した理由>
再レビューの場合：<前回の対象版・記録、修正前後の差分、指摘と影響するID。初回は「初回」>
既知の未確認事項：<理由・不足する環境や判断>
共有範囲・利用条件の根拠：<公開可能な確認記録。既存確認は今回への適用範囲も照合する。なければ「未確認」>
既存の検証結果：<識別子・記録の参照先。実行者・対象版・環境・コマンド・終了コード・結果を参照できること。なければ「なし」>
対象ファイルは変更せず、公開可能な対象だけを確認してください。
R01〜R30すべての結果と根拠、指摘、未確認事項、残るリスク、判定を返してください。
実行していない検証は成功とせず、外部への投稿・承認・マージは行わないでください。
```

返答は PR テンプレートの「レビュー記録」「指摘と残るリスク」に合わせる。未確認が一件もないことより、根拠のある結果と不足が読み取れることを重視する。

<a id="review-checklist"></a>

## レビューチェックリスト

コード、テスト、設定、CI、文書の変更に適用する。AI による提案・生成・調査を使った変更も同じ基準で確認する。AI の説明や検証報告は、差分・参照先・実行結果と照合する。

### 記録と判定

- 各項目の結果を「確認済み」「対象外」「未確認」「要修正」のいずれかで記録する。チェックは確認済みの項目にだけ付ける。対象外には理由、未確認には理由と次の確認方法を残す。
- 確認根拠にはファイル・行、仕様、対象版の公式資料、実行コマンド・環境・結果などを記す。同じ結果と根拠の項目は ID をまとめて記録してよい。異なる結果や根拠は行を分ける。
- 作成者と確認者、対象コミットまたは未コミット差分の範囲を明記する。確認者が人か agent か、作成者と同じか別かを記す。セルフレビューはその旨を記す。修正後は対象の版を更新し、指摘と再確認結果を対応させる。
- 要求と異なる動作、機密情報の露出、重要な処理の理解不足、必須検証の失敗が残る場合は、修正または変更範囲の縮小を行う。必須の確認が未確認なら統合判断を保留する。
- 残るリスクには影響、受け入れる理由、判断者、後続対応の担当と期限または再検討条件を記す。リスクの受け入れを理由に、必須 CI や既存の完了条件を省略しない。

文書のみの変更では内容・リンク・差分を検証し、実装・E2E に関する項目は理由を付けて対象外にできる。全項目の確認だけで、未想定のリスクがなくなるとは判断しない。確認と記録は人または[agent レビュー手順](#agent-review)を使う agent が行う。PR テンプレートの記入や判定を自動検証する CI は導入していない。

### 1. 要求と文脈（R01〜R04）

- [ ] **R01** 利用者の目的、入力・操作・期待結果が明記され、変更が対応している。推測で補った条件は、確認済みの事実と区別した。
- [ ] **R02** 正常時に加え、関係する空入力、不正入力、取り消し、失敗、再試行の動作を定めた。文書を開く変更なら、選択取り消しや読み込み失敗後の表示も対象にした。
- [ ] **R03** 言語・フレームワークの版、規約、依存先、品質の制約を実際の設定と照合した。プロンプトやテンプレートに古い前提を残していない。
- [ ] **R04** 未追跡ファイルも含めて変更対象を確認し、依頼に必要な範囲へ絞った。無関係な整理・設定変更・生成物は除くか、別の変更へ分けた。

### 2. 情報と技術の正確性（R05〜R07）

- [ ] **R05** 新しく使う API、クラス、設定キー、コマンド、依存パッケージが実在し、採用版で利用できることを公式資料と必要なビルド・実行で確認した。
- [ ] **R06** 技術選択や動作説明の出典を読み、主張を裏付けることを確認した。例示、将来予測、未計測の数値を、現在の実測や保証として扱っていない。
- [ ] **R07** 新しい技術や言語間変換では、文字コード、数値の範囲、null、例外、並行処理など、対象固有の意味を検証した。デコードの変更なら不正 UTF-8 の拒否も確認した。

### 3. 理解と設計（R08〜R11）

- [ ] **R08** 作成者と確認者が、変更の動作と採用理由をコードや文書で説明できる。理解できない重要な処理は、調査・簡素化・分割してから判断した。
- [ ] **R09** 既存の責務分担、依存方向、エラーの扱いと整合する。解析・デコード、`DocumentSource`、`ReaderViewModel`、画面の境界を変える場合は、その理由と影響を確認した。
- [ ] **R10** 追加した抽象化、依存、重複処理の必要性を説明できる。標準機能や既存実装で解決できるか検討した。
- [ ] **R11** 状態変更、I/O、非同期処理を入口から結果まで追った。関係する資源の解放、連続選択の完了順序、古い読み込みの遅延した成功・失敗、画面再作成時の状態を確認した。

### 4. 情報の保護と安全な実装（R12〜R15）

- [ ] **R12** AI や外部ツールを使った場合、共有するコード・データ・添付・取得範囲と利用先の保存・入力利用条件を確認した。共有範囲は権限のある必要な内容に絞り、私的な文書や認証情報を渡していない。
- [ ] **R13** 差分、コミット対象、公開予定の履歴・PR・ログ・検証成果物に、認証情報、個人の文書内容・ファイル名・URI、ローカル専用資料が混入していない。問題があれば公開を止め、秘密の実体を記録へ転載せず対処する。
- [ ] **R14** 関係する入力検証、権限、ファイルアクセス、外部送信を確認した。URI 権限の喪失や不正入力で意図しない読み書き・情報露出が起きず、閲覧操作が元の文書を変更しないことを確認した。
- [ ] **R15** 新しい依存や持ち込むコード・素材の提供元、利用条件、必要な表示を確認した。AI 生成であることだけを利用可能とする根拠にしていない。

### 5. 検証の十分性（R16〜R20）

- [ ] **R16** テストの期待値を仕様や利用例から定めた。実装の出力を正解にしたり、同じ誤りを含む二つの経路の一致だけで正しいと判断したりしていない。
- [ ] **R17** 重要な受け入れ条件を適切な層で検証し、関係する境界値、不正入力、失敗後の復帰を確認した。業務上の判断が必要なら、その条件を判断できる担当者と照合した。
- [ ] **R18** 重要な誤りを見逃さないか、入力とアサーションを点検した。実装とテストの同時変更では、見出しレベルの固定、末尾の欠落、エラーの無視などの誤実装でも成功してしまわないか確認した。
- [ ] **R19** コマンド、対象版・環境、実際の結果を確認した。テストの削除・無効化、アサーション・閾値の緩和、成功するまでの再実行で不具合を隠していない。カバレッジだけで十分と判断していない。
- [ ] **R20** 単体、連携、利用経路の検証範囲を区別した。必要な CI・E2E を行い、未実行は理由と次の確認方法を記録した。Robolectric やローカル APK の成功を、E2E や別の CI run の成功へ置き換えていない。

### 6. 利用者への配慮（R21〜R23）

- [ ] **R21** 名前、言語、日時、文字、入力形式などに、不要な文化的・利用者固有の制約がない。日本語や長い文書など、必要な利用者の例で確認した。
- [ ] **R22** UI の変更では、読み上げ、文字拡大、色以外の手掛かり、フォーカス・操作方法について、変更した主要操作を確認した。未実施の支援技術は未確認として記録した。
- [ ] **R23** 利用者向けの説明、エラー文、生成データが、実際の動作と用途に合っている。不当に利用者を排除する表現や仮定がなく、エラー後の次の操作が分かる。

### 7. 変更規模と統合・運用（R24〜R27）

- [ ] **R24** 全体を理解して確認できる変更規模になっている。大きい場合は、途中でもビルド・検証できる単位へ分けた。
- [ ] **R25** 複数ファイルの変更では、呼び出し元、設定、登録箇所、データ形式、文書の整合性を確認した。個々のファイルの確認に加え、必要な連携も検証した。
- [ ] **R26** 性能改善を主張する場合、同じデータ量・環境・計測区間で変更前後を比較した。メモリ、読みやすさ、復旧性などへの影響も確認した。長文の末尾表示の成功だけで応答性を保証していない。
- [ ] **R27** 保存・移行・外部サービス・配布方法に影響する場合、互換性と失敗時の復旧方法を確認した。試作品を実利用へ進める場合も、失敗の影響に応じた保証を確認した。

### 8. 判断と残る課題（R28〜R30）

- [ ] **R28** レビュー担当が採用理由、品質のトレードオフ、未確認の想定を根拠と照合して記録した。AI の推奨や生成できたことだけを採用理由にせず、担当の権限を越える判断は未確認として判断者へ引き継いだ。
- [ ] **R29** 修正必須の指摘と改善提案を区別し、修正後の差分と必要な検証を再確認した。採用の判断者と、残る課題の担当・期限または再検討条件が分かる。
- [ ] **R30** 変更の価値を、利用者の目的や品質の改善で説明できる。生成量や所要時間だけで、理解・レビュー・保守の負担を見落としていない。
