# 実装計画と主担当・レビュー担当の試行

## 目的と受け入れ条件

実装計画を小さな変更と検証記録へ結び付け、主担当が実装・検証し、別の agent が要求・差分・結果をレビューする。

- 開発手順に計画と担当の流れを追加し、公開ファイルだけで使える様式を用意する。
- 文書 A の読取が遅れ、文書 B の成功後に A の読取が成功しても、表示文書・保存 URI・loading・failed が B の結果を保つことを回帰テストで確認する。
- 既存実装が条件を満たす場合は実装を変更しない。新しい回帰テストの初回成功を、未実装による Red と混同しない。
- 受け入れ条件、対象版、検証、レビューを対応付け、未実行・未確認の範囲を残す。

## 判断と未確認事項

既存の `readJob` のキャンセルと結果受取の動作をまずテストする。待機には上限を設け、固定時間の sleep は使わない。通常の TDD による実装変更と、回帰テストの検出能力を調べる一時変更は区別する。

着手前の最初の試行は、Gradle キャッシュの書込制限、続く SDK 未設定によりテスト開始前に停止した。これは機能の失敗や Red の証拠ではない。リポジトリの設定を変更せず、一時環境に JDK・SDK を準備して V1を実行した。

初回実装段階の CI は push・PR 作成前のため未実行だった。追加承認後の CI・統合結果は、この変更の PR の検証記録に対象コミットと run の参照先を残す。端末確認は文書と JVM 回帰テストだけの変更で、アプリ実装・UI・ファイルアクセスの変更を伴わないため対象外とする。Robolectric の結果を実機確認の代わりにはしない。

## 試行で分かったことと次の比較

今回の回帰テストは現行実装で成功したため、本番コードの修正は不要だった。一時変更で古い成功結果の上書きを検出でき、計画の条件と検証結果を対応付けられた。新しい skill を追加する必要性はまだ示していないため、既存3 skills を維持した。

今回の一件だけでは、手戻り・再読・レビュー待ち時間・トークンや費用の削減は実証できない。全担当のトークン数・費用と、比較可能な過去タスクの時間は取得していない。次の同種・同規模の変更でも計画と実行結果を対応付け、修正往復、再読、待ち時間、取得可能な使用量を比較する。主担当と保守担当者が結果を確認し、計画の定型化が繰り返し必要になった場合に入口となる skill を検討する。

### 指摘と残るリスク

修正必須・改善提案ともなし。**対象差分の内容とローカル検証は採用可。統合判断は必須CIが未確認のため保留。** 公開・統合を依頼された段階で主担当が対象コミットの必須CIを確認する。ローカル成功やagentレビューをCI成功へ置き換えない。

主担当とレビュー担当のモデル識別情報・全担当のトークン数・費用は取得していないため、モデル条件をそろえた効果比較も未確認である。次の同種作業での比較と保守担当者による継続判断を後続事項とする。

## 公開・統合への引き継ぎ

利用者の追加承認により、対象4ファイルだけをコミット・push し、PR の必須 CI を確認して Squash merge する。統合後の main の CI も確認する。上記の R20は初回レビュー時点の判定として保持し、CI 確認後の再判定と対象版・実行結果は PR の検証・レビュー記録に残す。計画・テスト・本番実装の内容は変更しない。
