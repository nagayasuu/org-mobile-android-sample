# agent の読取・文書検証・実行結果集約

## 計画と受け入れ条件

基準版：`49783f5bcf67609b7a794a5b87920abc88e21b28`。
作業ブランチ：`chore/agent-context-followup`。主担当は作成 agent、最終確認は別のレビュー agent が行う。

目的は、必要な原文を保持しながら、文書検証コードの作り直し、広すぎる読取、ログの再解析を減らすこと。

| 段階 | 対象と期待結果 | 検証 |
| --- | --- | --- |
| 基準確認 | 既存の Python テストを維持する | `python3 -m unittest discover -s scripts/tests -q` |
| 文書ツール | 公開対象の Markdown の UTF-8・末尾空白・ローカルリンク・アンカーを検査する。指定節を原文・行番号・内容ハッシュ付きで取得する | 正常例、日本語、重複見出し、コード内の偽見出し、リンク切れ、不正 UTF-8、存在しない節を確認 |
| 結果集約 | 任意の検証コマンドを実行し、全文ログと終了コードを保持する。JUnit・Lint の明示したレポートから集約し、欠落・不正・失敗を成功にしない | 合成レポートと実際の子プロセスで成功・失敗・警告・レポート欠落・再実行を確認 |
| 利用手順 | 正本の開発手順・ビルド手引きからツールを利用できる | 新ツールで文書検証、節取得、検証コマンド実行を一巡する |
| 完了確認 | 既存の検証・R01〜R30を維持する | 別 agent レビュー、差分と公開範囲の確認 |

Python 標準ライブラリのみを使う。アプリ・ビルド設定・CI は変更しない。ツールのテストは既存 CI の Python テスト探索対象へ追加する。
レポート集約は既存のビルド・カバレッジ判定を置き換えず、その実行結果の表示を補助する。
ローカルログは公開成果物へ自動登録しない。既存のローカル専用資料と個人設定は変更しない。

総入力30%削減と task success の低下を最大3ポイント以内に抑えることを初期目標とする。現行運用を比較元にし、全 agent・失敗・再試行の入力を含める。キャッシュ入力も総入力に含める。文書修正・コード変更・検証スクリプト変更を分け、同じ課題・対象版・モデル・設定で比較する。少数試行の点推定だけで3ポイント以内を保証しない。今回のツール導入だけでは削減率・成功率の達成を主張しない。

### 未確認事項と対象外

- APK 再生成・Android Lint 再実行・端末 E2E は対象外。アプリ・Gradle・端末利用経路に変更がなく、Python CLI の受け入れテストと実文書・既存 XML の形式確認を行った。
- GitHub CI は未確認。公開操作は今回の依頼に含めず、統合時に対象コミットの必須 CI を確認する。既存 CI の Python テスト探索で新テストも対象になる。
- 総入力30%削減・task success の低下3ポイント以内は未確認。今回の作業で A/B のモデル実行はしていない。保守担当が次の同種作業で全担当の使用量と結果を集計する。reviewer は親会話を継承せず、計画・差分・参照先から起動したが、それだけで削減を実証したとは扱わない。
- レポートの鮮度判定は mtime を用いるため、時刻操作・粗い時刻分解能・別プロセスによる生成を完全には識別しない。対象版・コマンド・元レポートも直接確認する。
- Markdown はリポジトリの現在の ATX・単純リンク形式を対象とする。外部 URL の内容・Setext・複雑な構文は原文確認が必要。
- 外部サービスの保存・入力利用条件の新たな確認はしていない。公開可能なリポジトリ資料と合成データのみを扱い、認証情報や私的資料を新しく共有する実装はない。
