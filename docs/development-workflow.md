# 開発手順

このリポジトリでは、動いている org 閲覧アプリへ小さな変更を加え、テスト・CI・端末での結果から次の変更を決める。人と agent は同じ検証手順を使い、既存の閲覧機能を維持しながら、入力から表示、必要なら保存までを一つの機能として通す。GitHub CLI（`gh`）は必須にしない。

## 1. 現在の動作と変更する範囲を確かめる

最小の閲覧機能、コマンドによるビルド・Lint・自動テスト、GitHub Actions、CI 生成 APK の実機確認は整備済みである。初回の結果は上記の検証記録に残し、以降の変更の成功を保証するものとは扱わない。

現在の利用経路は「Dropbox アプリで UTF-8 の `.org` ファイルを端末へ保存 → 本アプリの『ファイルを開く』 → Android 標準のファイル選択 → 読み込み・org 解析 → 表示」。端末上のコピーを読むため、PC 側の更新後は再度保存する。

維持する基本動作は次のとおり。

- 日本語の見出し・本文・箇条書き・番号付きリストを区別し、長い文書の末尾まで縦にスクロールして読める。
- 表示対象は `*` から始まる見出し、通常の本文、`-`・`+`・インデントした `*` の箇条書き、`1.`・`1)` の番号付きリスト。対応外の構文はテキストとして残す。
- ファイル選択の取り消しで現在の表示を保ち、読み込みに失敗したら再選択できる案内を出す。
- 画面再作成後の文書・閲覧位置の保持と、更新したファイルの再読み込みを維持する。

現在は閲覧専用である。折りたたみ、編集、新規メモの保存、Dropbox との自動同期は、個別に受け入れ条件を決めて追加する。完全な org-mode の描画を前提に機能を広げない。

作業開始時には次を行う。

1. [Git 運用規約](git-workflow.md)に従い、状態、現在のブランチ、差分、関連する履歴を確認する。既存の未コミット変更を保つ。
2. README、対象コード、関連テストと履歴を読み、一つの操作を入口から結果まで追う。既存の実装や Android の標準機能を使えるか調べる。
3. 変更に関係する既存テストを実行し、着手前の状態を把握する。保証が不足する箇所は、必要な範囲で現在の振る舞いをテストにする。
4. 利用できる JDK・SDK、CI、端末と、実行できない検証を確認する。環境構築は[ビルド・検証の手引き](android-build.md)に従う。

## 2. 次の小さな機能と受け入れ条件を決める

利用者の一つの目的を、実装・レビュー・端末確認できる大きさに絞る。画面だけ、保存層だけを先に大量に作らず、利用者の操作と結果がつながる単位で進める。不具合修正、依存更新、構造整理も一つの目的に絞る。

### 利用者の目的と利用環境を確かめる

機能や利用経路を決める際は、利用者への短い聞き取りや実際の操作から、次の点を確認する。このアプリでは「PC の Emacs で使う org ファイルを Android でも読む」という目的を起点にし、開発者自身の知識や操作の慣れを利用者全体の前提にしない。

- 達成したい作業と、現在の方法で困っている点。例えば、移動中に必要な見出しや本文を見つけたいのか、文書全体を読みたいのかを区別する。
- 利用頻度、org や Android のファイル操作への慣れ、Dropbox から保存する手順をどこまで理解しているか。
- 利用する端末・OS、文書の長さや言語、通信の有無、文字サイズ・読み上げ・入力方法など、操作に影響する環境。

確認した事実と未確認の想定を分け、今回優先する使いやすさを受け入れ条件へつなげる。例えば、たまに使う場合は操作を見つけやすいこと、繰り返し使う場合は少ない手間で目的の本文へ戻れることを重視する。小さな修正では既存の確認記録を参照し、影響する点だけを見直す。公開記録には個人を特定する情報や私的な文書内容を含めない。

### 品質要求を見つける

要求された機能に加え、その機能を役立つものにする品質を、利用者の目的・文書の性質・利用環境から探す。例えば閲覧機能には、明示されていなくても、元の文書を変更しないこと、日本語を正しく読めること、私的な内容を外へ出さないことが関係する。既存の基本動作を出発点にし、追加の要求は関係者へ確認する。

1. 主な操作と、失敗すると目的を達成できなくなる条件を挙げる。通常の文書だけでなく、大きな文書、連続したファイル選択、画面再作成、アクセス権の喪失、遅いプロバイダーなど、今回の変更に関係する条件を選ぶ。
2. 「速い」「変更しやすい」などの表現を、対象の操作・部品、入力と環境、期待する結果、確認方法へ分解する。応答性なら文書量と計測区間、変更のしやすさなら「構文追加で Android のファイルアクセスを変更せず解析テストで確認できる」など、判断できる条件にする。
3. 聞き取り、既存の障害、実測などの根拠と、未確認の想定を分ける。平均的な条件に加えて、守る必要のある厳しい条件を確認し、受け入れ条件と品質の優先順位へ反映する。根拠がない目標値は、先に計測・確認する課題として残す。

### データ・操作・時間・量からテスト観点を整理する

変更対象の入力・操作・依存先を、データ・イベント・時間・量の観点とその組み合わせで見直す。目的は、通常の操作だけでは気付きにくい失敗条件を挙げ、優先する受け入れ条件を選ぶことである。

| 観点 | このアプリでの対象 | 組み合わせて調べる例 |
| --- | --- | --- |
| データ | org 文書、文字コード、URI、アクセス権 | 不正 UTF-8 の選択、保存済み URI の権限喪失 |
| イベント | ファイル選択、再読み込み、回転、読み込みの成功・失敗 | 読み込み中の再選択や画面再作成 |
| 時間 | 遅延、操作順序、完了順序、長時間の待機 | 古い読み込みが新しい読み込みより遅れて完了する |
| 量 | 文書のバイト数・行数、見出しの深さ、連続選択の回数 | 大容量文書の読み込み中に複数回選び直す |

1. 利用者の目的と変更対象を定め、必要なら解析・状態管理・ファイルアクセス・表示などの部分問題へ分ける。
2. 各観点に当てはまる対象を挙げ、起こり得る誤りと観測する結果を具体化する。組み合わせは今回の変更とリスクに関係するものを選ぶ。
3. 既存テスト・検証記録と照合し、保証済みの条件と不足を分ける。影響と発生可能性から優先し、まず重要なシナリオを1〜2件選ぶ。
4. 入力、イベントの順序、期待結果、検証する層を受け入れ条件へ反映する。テスト結果から新しい対象や関係が分かったら見直す。

読み込み処理では、古い読み込みの遅延した失敗を扱う既存テストに加え、次を追加候補とする。各候補の実装・実行結果は別に記録し、ここへ方針を記載しただけで検証済みとは扱わない。

- 遅い文書 A の読み込み中に文書 B を選び、B の成功後に A が成功しても、表示文書・保存 URI・読み込み中・エラー状態が B の結果を保つ。
- 文書を3件以上続けて選び、完了順序や成功・失敗を変える。最後の選択が成功すればその文書・URI へ切り替わり、失敗すれば選択前の表示文書・保存 URI を保ってエラーを示す。キャンセル済みの処理が後から完了しても、これらの状態を変えない。

競合の確認ではフェイクや同期手段で完了順序を制御し、待機に上限を設ける。古い結果が状態を上書きしないことと、プロバイダーの処理自体が中断されることは別の保証である。同期読み込みの即時中断やタイムアウトは前提にせず、長時間待機・停止時の動作と必要な対策を確認する課題として残す。

### 受け入れ条件へ落とし込む

着手前に、Issue・PR の草案や作業メモへ以下を記載する。小さな変更では短い箇条書きでよく、専用ファイルは必須にしない。

- 目的、変更前と変更後の振る舞い、今回扱わない範囲。
- 入力・操作・期待結果で表した受け入れ条件。正常系に加え、関係する空入力、取り消し、アクセス権の喪失、失敗と再試行などを選ぶ。
- 影響する画面、解析処理、状態保持、ファイルアクセス、設定・依存先と、互換性への影響。
- 自動テストで確かめる条件、実機で確かめる条件、使用する公開サンプルや合成データ。

例えば見出しの折りたたみなら、「見出しを押す → 配下が隠れる → 再度押すと戻る」という一本から始め、入れ子や画面再作成時の状態は別の具体例で確認する。

品質の条件も変更の範囲に合わせて具体化する。

| 観点 | 条件と確認方法の例 |
| --- | --- |
| 読みやすさ・操作性 | 日本語、長い文書、文字サイズ、明暗設定、回転時に操作と内容を判別できるかに加え、利用者が操作を見つけて目的を達成できるかを確認する |
| アクセシビリティ | 読み上げ、文字拡大、色に依存しない情報、操作対象とフォーカスについて、変更対象の画面・主要操作で確認する |
| データと失敗時の動作 | 対応外構文の保持、読み込み失敗後の再選択を自動テストと実機で確認する。保存機能を追加する場合は元ファイルの保護と再起動後の保持も条件にする |
| 応答性 | 対象端末・OS、文書量、計測区間、許容時間を決めて測る。1 万項目の末尾表示の確認と、読み込み時間・メモリの測定を区別する |
| プライバシー | 文書内容・個人のファイル名・URI・認証情報をログや成果物へ含めず、必要なアクセス権だけを使うことを差分と出力で確認する |

数値の目標は、現在の実測と利用目的から決める。未計測の性能を達成済みとせず、カバレッジやコード量だけを完了条件にしない。

### 品質特性の優先順位を合意する

性能、読みやすさ、データの保護、変更のしやすさなどが衝突する場合は、次の順で判断する。

1. 利用者の目的と制約から、今回必ず守る条件と、特に重視する少数の品質を選ぶ。
2. 各案の利用者への影響、実装・保守の負担、測定結果を比較し、どの品質を優先して何を受け入れるかを利用者・保守担当者など判断に関わる人と合意する。
3. 採用案、理由、受け入れる不利益、確認方法、再検討する条件を Issue・PR または ADR に残す。条件や実測が変わったら判断を見直す。

### 品質を保証する範囲を決める

優先する品質ごとに、どの操作・範囲で保証するかを定める。ファイルやパッケージの分割だけで独立性を判断せず、実行・配布に必要なコード、データ、OS の機能、外部サービスを含めて調べる。

- 対象の操作を入口から結果まで追い、必要な部品とデータ、その所有者を挙げる。個別に変更・配布できる範囲と、一緒に変更・検証する必要がある範囲を区別する。現在のアプリ内の責務は、同じ APK に含めて配布される。
- アプリ側で保証する動作、依存先に求める条件、その条件が崩れた際の動作を記載する。結果を待つ依存先の遅延・停止は、呼び出し元の応答性や利用可能性にも影響するため、処理時間や障害の確認範囲へ含める。
- 部品単体のテスト、部品間の連携確認、実際の利用経路の確認を対応付ける。例えば解析テストは、ファイル選択から表示までの成功や Dropbox での保存の成功までは保証しない。端末へ保存したコピーを読む経路と、通信を必要とする可能性がある文書プロバイダーから読む経路は、条件と確認結果を区別する。

品質の記録には、対象範囲、依存先への前提、確認方法、未確認の範囲を残す。境界や依存先を変更する際は、既存の保証が引き続き成り立つかを見直す。

### アクセシビリティを設計・確認する

画面や操作を変更する場合は、次の観点から受け入れ条件と端末での確認方法を選ぶ。既存画面との一貫性も保ち、確認した環境・範囲と、未対応・未確認の点を記録する。

| 観点 | 確認する内容 |
| --- | --- |
| 読み上げ | TalkBack でボタンの目的、見出しと本文の関係を把握でき、文書を自然な順序で読める。読み込み中・空文書・エラーと次の操作も分かる |
| 文字とレイアウト | 文字サイズや表示サイズを拡大しても、本文・ボタン・案内が欠けず、スクロールして必要な内容を読める |
| 色と見分けやすさ | 明暗設定で文字と背景を判別でき、状態や操作の違いを色だけに頼らず伝えられる |
| 操作対象 | ボタンを見つけて押しやすく、隣接する操作を誤って実行しにくい。取り消しやエラー後に次の操作へ進める |
| フォーカスと操作方法 | 読み上げ時のフォーカスが自然に移り、必要な操作へ到達できる。外付けキーボードなどを対象にする場合は、その方法でも確認する |

自動テストや Lint の結果に加え、端末上で読み上げ・文字拡大などを実際に操作する。確認できなかった支援技術や操作方法は未確認として残す。

#### 初期の確認方法と合否条件

アクセシビリティの確認は次の方針で行う。[Android のアクセシビリティ検証手引き](https://developer.android.com/guide/topics/ui/accessibility/testing)を参照し、既存の Lint と端末での手動確認を組み合わせる。以下の確認結果は今後の端末検証で記録し、方針を定めたことだけで確認済みとは扱わない。

| 項目 | 採用する方針 |
| --- | --- |
| 環境 | Pixel 10a／Android 17。対象 APK、TalkBack の版、文字・表示サイズ、明暗・画面の向きを記録する |
| 入力 | 公開サンプル、複数画面にまたがる文書、空文書、不正 UTF-8 の合成ファイルを使う |
| 実行契機 | 初回導入時と、UI・表示・操作に影響する変更時に実施する |
| 合否判定 | 主要操作が完了できない、必要な内容を読めない、必要な操作へ到達できない問題は修正必須とする |

初期の確認内容は次の4つとする。

1. **TalkBack。** 読み上げとフォーカス操作で標準ファイル選択から文書を開き、見出し・本文を自然な順序で読めること、見出しとして移動できることを確認する。
2. **状態と復帰。** 読み込み中・空文書・エラーを把握でき、取り消しやエラー後も次の操作へ進めることを確認する。
3. **文字・表示サイズ。** 通常と最大の設定で、縦横どちらでも本文・操作・案内が欠けず、必要な内容をスクロールして読めることを確認する。
4. **明暗・フォーカス。** 明暗それぞれで文字・操作・システムバーを判別でき、フォーカス順序が自然で、色だけに依存せず状態が分かることを確認する。

実際の操作順序、端末設定の値、期待結果と実際の結果を[端末確認手順](device-testing.md)と検証記録へ反映する。設定変更前の値を控え、確認後に戻す。修正必須の問題は修正して同じ条件で再確認し、その他の問題も影響と次の対応を記録する。

開発者による確認と、支援機能に慣れた利用者による評価は主体と確認範囲を分けて記録する。未実施の支援機能は未確認とし、Lint の成功を端末操作や利用者評価の完了とみなさない。外付けキーボード・Switch Access・Voice Access は、利用者の目的や対応する操作方法に応じて対象へ追加する。

### 編集・保存・同期を追加する前に

現在は閲覧専用を維持し、編集・保存・同期は今回の導入対象にしない。これらの機能に着手する時点で、次の事項と確認方法を具体化し、実装前に受け入れ条件へ含める。保存先、同期サービス、データベースなどの具体的な方式は、その段階で選定する。

| 項目 | 着手前に決めること |
| --- | --- |
| 追加する機能 | 編集・新規保存・既存ファイル更新・同期のうち、今回扱う範囲 |
| 元データの保護 | 上書き方法、バックアップ、失敗時に元の文書を保持・復旧する方法 |
| 保存の整合性 | 保存途中の失敗・中断・再試行で、破損や二重反映を起こさない方法 |
| 同期の競合 | 複数端末で更新された場合の検知・解決・利用者への案内 |
| データ移行 | 形式の版管理、旧版との互換性、中断後の再開・復旧 |
| 検証 | 正常保存に加え、権限喪失・失敗・中断・再実行を自動テストと実際のプロバイダーで確認する方法 |
| 判断の記録 | 比較した方式、採用理由、制約、復旧方法を ADR に残す |

保存先・文書プロバイダーが提供する保証を調べ、選択した方法が実際の利用経路で成立するかを確認してから方式を決定する。正常時だけでなく失敗時・復旧時の入力、操作、期待結果、確認環境を受け入れ条件に記載する。これらは将来機能の着手条件であり、現時点で方式の選定や保存・同期の検証が完了したとは扱わない。

影響が広く戻しにくい判断は、後述の ADR の記録方法に従って `docs/decisions/NNNN-short-title.md` へ残し、対応する機能の Issue・PR と関連付ける。方式の決定・受け入れ条件の合意、実装、検証結果を区別して記録する。

#### 更新の整合性とデータアクセスの性能

保存層や同期を実装する際は、採用した保存先の保証を調べ、次の点を設計と検証へ含める。データベース・キャッシュを使う場合は、その仕組みに対応する項目も確認する。

- 一度に成功させる更新の範囲と、途中で失敗した場合の取り消し・再試行を決める。中断や重複実行を再現し、部分的な更新や意図しない二重反映が残らないことを確かめる。データベースではトランザクションの範囲を明示し、ファイル保存では実際のプロバイダーで保証を確認する。
- ストリームや接続の取得・解放を対応させ、成功・例外・キャンセルの各経路で解放する。接続プールを使う場合は、接続数と待ち時間の上限を決め、連続実行でも資源が増え続けないか確認する。
- キャッシュはキー、元データの更新を検知する方法、有効期限・無効化条件、古い値を許容する範囲を決める。再読み込み・更新・失敗後に、期待する新しい値へ切り替わることを検証する。
- 想定するデータ量と増加後の量で、取得件数・実行時間・メモリ使用量を比較する。データベースではクエリをパラメーター化し、実行計画と索引の効果を調べ、必要な列・件数やページ分割を選ぶ。変更前後の同じ条件で効果を測る。

#### データ移行の進め方

1. 移行元と移行先の形式、変換規則、対象件数、停止できる時間を整理し、一括移行か段階移行かを選ぶ。新旧アプリ・データの互換性、同期中の更新、復旧に必要なバックアップも決める。
2. スキーマ変更とデータ変換を、版と適用順序が分かるスクリプトなどとして同じリポジトリで管理する。適用済みの版を識別し、再実行時に二重変換しない方法と、中断後の再開方法を用意する。旧形式を扱える期間も明示する。
3. 公開可能な少量のデータで、件数だけでなく内容・関連・欠損値を照合する。対応する旧版からの更新、中断、再実行、復旧を確認してから対象を広げ、実施した版・範囲・照合結果を残す。

### ファイルアクセス・同期のセキュリティを確認する

外部入力・ファイルアクセス・同期を変更する場合は、実装前に次の点を検討する。

- 外部入力・権限・通信・認証情報について、STRIDE の6観点（なりすまし、改ざん、否認、情報漏えい、サービス妨害、権限昇格）を手掛かりに、変更対象に関係する脅威を整理する。
- 必要な対策と確認方法を受け入れ条件に含める。
- 採用した対策と、残るリスク・制約を記録する。

### アーキテクチャ上のリスクを評価する

責務・依存先・データの扱いを変える場合は、優先する品質とその保証範囲に沿ってリスクを評価する。セキュリティに加え、応答性、状態の整合性、復旧、変更の波及などを対象にする。

1. 対象の構成と操作を確認し、リスクごとに原因・発生条件・影響する品質と範囲を挙げる。例えば、遅い読み込みと次の読み込みが重なったとき、古い結果が新しい表示を上書きする可能性を調べる。
2. 影響の大きさと発生可能性を分け、各々を低・中・高などで評価する。データの損失、操作の中断、回復の手間、利用頻度や実測を根拠に評価基準をそろえる。情報不足は低リスクとせず、未確認と次の調査を記す。
3. 複数人で検討する場合は、各自が先にリスクを挙げてから評価をすり合わせ、軽減策を検討する。一人で行う場合も、事実と想定を分け、別の失敗経路や反例から見直す。
4. 優先して対処するリスクを選び、対策、担当、確認方法、残るリスク、再評価する条件を Issue・PR または ADR に残す。受け入れる場合も理由を記す。対策で別の品質が悪化しないかを比較し、変更後の検証結果や新しい依存先・利用条件に応じて評価を更新する。

## 3. 小さく実装し、理解できる構造を保つ

振る舞いを変える場合は、次のサイクルを基本にする。

1. 利用者の操作に近い境界で、受け入れ条件を示す少数のテストを用意する。画面や ViewModel から必要な振る舞いを定め、細かな解析条件は内部の単体テストで補う。
2. テストを実行し、期待した振る舞いが未実装であるためにアサーションで失敗することを確認する（Red）。環境不備やテストの誤りによる失敗は先に切り分ける。
3. 成功に必要な小さな変更を実装する。
4. 関連テストの成功を確認し（Green）、成功を保って構造を整理する（Refactoring）。
5. 別の結果になる具体例や境界条件を追加し、受け入れ条件を満たすまで繰り返す。完了前に共通のビルド・検証を実行する。

一つの例を通す仮実装から始め、異なる例を追加して実装を一般化する（三角測量）。例えば見出しの判定なら、見出しになる行に加え、インデントした `*` の箇条書きやソースブロック内の行を確認する。新しい振る舞いを加える段階と、振る舞いを保って構造を整理する段階を区別し、コンパイルできない大きな変更を長く抱えない。

文書や単純な設定の変更では、その変更に合う内容・リンク・構文の確認を選ぶ。実装を写しただけのテストや、意味のない失敗を作る作業は増やさない。

### 責務と境界を整理する

機能追加や構造変更では、変更に関係する範囲で次を行う。小さな修正では既存の説明を参照し、変わる点だけを記録してよい。

1. 利用者の操作を基に、「文書を読む」「org を解析する」「表示状態を管理する」などの責務を挙げ、入力・出力、保持する状態・データ、失敗を扱う担当を明示する。
2. 正常時と失敗・取り消し時の受け入れ条件を各責務へ割り当て、担当の抜けや重複を調べる。例えば、入力の解釈、読み込み資源の解放、表示するエラーの決定を誰が担うか確認する。
3. 同じ理由で変わる処理とデータがまとまっているか、境界を越えるやり取りが増えすぎていないか、優先する品質を検証できるかを評価する。必要なら責務を分割・統合し、もう一度操作を通して確認する。

責務を表す論理的な構成と、APK・プロセス・文書プロバイダー・外部サービスなど実際の配置を区別する。責務を分けることだけを理由に、モジュールやサービスを増やさない。

### 実行時の依存を確認する

ソース上の参照関係に加え、一つの操作で実際に何を待ち、どの順序や状態に依存するかを追う。文書を開く操作なら、標準ファイル選択、URI の権限、プロバイダーからの読み込み、文字の変換・解析、表示状態の更新を確認する。

- アプリ内の呼び出し、バックグラウンド処理、プロセスを越える呼び出しを区別し、結果を待つ箇所、共有する状態、必要な実行順序を記す。非同期に実行しても、結果への依存や障害の影響は残る。
- 遅延・例外・権限喪失・キャンセル時に誰が処理を終え、資源を解放し、表示を更新するかを確認する。連続選択や画面再作成では、どの要求の結果を採用するかを明確にし、古い処理や重複処理の影響を調べる。
- 依存先の条件を変えたテストで状態遷移と失敗後の操作を確かめ、実際の OS・プロバイダーとの接続は端末で補う。端末内のファイルとクラウド上の文書では通信の要否が異なり得るため、同じ可用性を仮定しない。

### 設計と構造変更

- 解析・判断を、Android の画面やファイル I/O から独立させる。現在の `OrgParser` / `DocumentDecoder`、`DocumentSource`、`ReaderViewModel`、画面の責務を手掛かりに、値を受け渡して処理をつなぐ。同じ入力に同じ結果を返す純粋な判断を中心に置き、I/O・時刻・乱数などは外側で扱う（関数型コア・命令型シェル）。
- 外部入力は境界で一度解釈し、検証結果を後続で使える型付きの値として返す。真偽値だけを返して同じ解析を繰り返さない。有効な状態を生成・更新する操作自身が不変条件を守り、不変の値を優先する。
- 外部データの形式を写す DTO（データ転送オブジェクト）と、意味や不変条件を守る内部モデルの役割を区別する。形式や保証が異なる場合は境界で変換し、外部形式の都合が内部の判断へ広がることを防ぐ。分離する必要がない場合は、同じ内容の型を増やさない。
- 入力に課す制約は必要なものに絞り、出力には明確な保証を持たせる。このアプリでは、対応外の org 構文をテキストとして保持することと、不正な UTF-8 をエラーにすることを区別する。利用者が直せる入力・アクセスの問題には、次の操作が分かる結果を返す。
- 状態を変える操作と、値を問い合わせる操作を区別し、問い合わせに保存や通信などの予想外の副作用を隠さない。ロギング・キャッシュ・再試行が必要なら、解析や判断へ混ぜず、境界の部品や同じインターフェイスで包むデコレーターへ分ける。
- 同じ理由で変わる処理をまとめる。分岐、引数・変数、追跡する状態が増えた箇所は分解を検討し、名前・型・短い処理で意図を伝える。数値に合わせるだけの分割はしない。
- モジュールや外部依存の追加は、変更の局所化や検証のしやすさと、設定・保守の負担を比較して決める。現在の単一アプリを出発点とし、将来の機能のためだけに層やサービスを増やさない。
- 大きな置き換えは、新しい経路の追加、呼び出し元の移行、古い経路の削除へ分け、途中でもビルド・検証可能にする。未完成機能をフラグで隠す場合は既定値、確認方法、削除条件を記録する。
- 本番コードの構造変更とテスト自身の構造変更は分け、相互の保証を保つ。テストの整理では対象の振る舞いと検出能力が変わっていないか確認する。

構造改善に着手する前に、対象の振る舞いをテストで押さえ、次の基準で範囲を選ぶ。

- 実施する目安：今回の機能追加・修正に必要な箇所が理解しにくい、性能の問題が実測されている、または頻繁に変更され手戻りが続いている。改善の効果を説明できる小さな範囲へ絞る。
- 延期する目安：安定していて変更が少ない、検証に必要な時間やテストが足りない、壊すリスクが利益を上回る、または今回の目的を超える大きな変更になる。必要なら先に現在の振る舞いをテストに残す。

延期する場合は対象・理由・再検討する条件を課題へ残す。実施する場合も、無関係な整理は別の変更へ分け、振る舞いを保つ小さな変更ごとに検証する。

分解を検討する際は、次の目安を使う。いずれもレビューで詳しく読むきっかけであり、CI の強制規則としては導入していない。

| 観察するもの | レビューの目安 |
| --- | --- |
| コードの幅と処理の長さ | 幅 80 文字・メソッド 24 行程度を超える場合、抽象度の異なる処理が混ざっていないか確認する |
| 分岐の複雑さ | サイクロマティック複雑度 7 程度を超える場合、判断の分離と必要なテストの観点を見直す |
| 同時に追う値 | ローカル変数・引数・参照するフィールドを合わせて数え、読み手が抱える状態を減らせないか確認する |

数値を満たすだけの細分化を避け、同じデータや同じ変更理由に沿って分ける。上位の処理は少数の操作で流れを示し、詳細へ進んでも追う情報が増えすぎない形にする。モジュール境界を設ける場合は依存方向と循環の有無を確認し、必要に応じて自動検査で維持する。

クラスや関数の API は、型 → 名前 → コメント → テストの利用例 → コミットの理由 → 外部文書の順に、意図を伝えられるか検討する。名前を仮に `X` に置き換えても、引数と戻り値の型から有効な使い方をどれだけ読み取れるかを確認する。判断理由は文書へ残しつつ、型で防げる誤用を説明だけで補わない。

クラスや関数の API は、公開された型・操作・補完候補から、呼び出し側が目的の使い方を見つけられるか確認する。責務に必要な操作を公開し、内部の補助処理や意図しない使い方につながる操作は公開範囲を狭める。

### 設計判断を ADR に記録する

ファイルアクセス方式、状態の永続化、同期、モジュール境界など、影響が広く戻しにくい判断は ADR（設計判断の記録）を `docs/decisions/NNNN-short-title.md` に判断ごとに一件ずつ残す運用を採用する。方式を比較・決定する際に作成し、対応する実装の PR と関連付ける。現時点で実際の ADR は未作成であり、運用方針の確定と個別の判断の記録を区別する。記載項目は以下とする。

- 日付、題名、状態（提案・採用・置換済み）。
- 解決する問題、制約、重視する品質、比較した選択肢。
- 決定と理由、利点、受け入れる不利益・リスク。
- 検証方法、再検討する条件、置き換える場合は新しい記録への参照。

方針を変更する場合は新しい ADR を作り、旧記録の状態を「置換済み」にして、新旧の記録から相互に参照できるようにする。過去の決定とその時点の理由を新しい理由で上書きせず、変更の経緯を追える状態を保つ。

既存の主要な判断も、必要になった時点で根拠を確認して記録する。過去の採用理由を推測して書かず、現在確認できる事実と判断、その根拠、確認できなかった点を明記する。既存の判断が記録済みであるとはみなさない。

局所的な小さな判断理由はコード・コミット・PR の説明に残せばよく、すべてを ADR にしない。

### 構成と操作を図で伝える

文章やコードだけでは境界ややり取りを追いにくい場合に図を使う。図は次のルールで作成・レビューする。

- 誰が何を判断する図かを決め、対象の機能・操作・範囲を題名や説明に記す。責務の関係、実際の配置、操作の時系列など、目的に合う図を選び、異なる観点は必要に応じて分ける。
- 要素には責務や実装と対応する名前を付ける。矢印には呼び出し・データの流れなどの意味と方向を示し、同期・非同期を区別する必要があれば明記する。独自の図形・線・色には凡例を付け、色だけで区別しない。
- アプリと OS・プロバイダー・外部サービスの境界を示し、対象の操作と失敗経路を図から追えるか確認する。関係のない詳細は省き、実装済みの構成と提案中の構成を区別する。
- 必要な図は対応する設計説明や ADR に置き、Mermaid など差分を確認しやすい形式を優先する。実装と同じ変更で更新し、関連する受け入れ条件や判断理由へつなげる。公開可能な名前と例を用い、個人のファイル名・URI・ローカル専用情報を含めない。

## 4. 必要な層でテストし、共通の検証を通す

自動テストは準備・実行・検証（Arrange-Act-Assert）が読み取れ、入力と期待結果から仕様が分かる形にする。内部の呼び出し順やクラスの配置へ過度に依存させず、同じ誤りを重複して検証するより結果を左右する条件を選ぶ。

| 検証の層 | このアプリでの役割 |
| --- | --- |
| 高速な JVM テスト | org 解析、UTF-8、空入力、不正入力、対応外構文などの変換と境界条件を確認する |
| Robolectric のテスト | ViewModel の状態、URI からの読み込み、画面表示・回転・取り消し・再読み込みなど、Android 部品との連携を確認する |
| 端末でのスモークテスト | 標準ファイル選択、実際のプロバイダーや Dropbox からの保存、OS・表示・スクロールの動作を確認する |

フェイクやテスト専用プロバイダーで高速・再現可能なテストを行い、実際の接続は端末で補う。Robolectric の API 35 での成功は、Pixel 10a／Android 17 の動作や Dropbox の経路の成功を保証しない。現時点で自動の実機・エミュレーター E2E テストは導入していない。

### 自動 E2E テストを導入する

標準ファイル選択を含む主要操作を、次の方針で自動化する。現時点で E2E テスト・エミュレーター設定・CI 連携は未導入であり、採用バージョン、API 37 のシステムイメージと実行環境の利用可否・互換性は導入時に確認する。

| 項目 | 採用する方針 |
| --- | --- |
| ツール | 標準ファイル選択の操作に [UI Automator](https://developer.android.com/training/testing/other-components/ui-automator)、アプリ内の操作・検証に [Espresso](https://developer.android.com/training/testing/espresso) を使う |
| 初期環境 | 標準ファイル選択を備えた API 37 のエミュレーターを使い、[Gradle Managed Devices](https://developer.android.com/studio/test/managed-devices) で構成を管理する |
| 入力 | テスト環境の端末へ配置した公開サンプルと合成文書を使う |
| 実行契機 | 初期はローカルと CI の手動実行。安定後に週次実行を追加し、PR の必須化は実行時間・安定性から判断する |
| 合否判定 | 期待する表示・状態と異なる場合と、タイムアウトした場合は失敗とする。成功するまでの再実行で済ませない |

初期シナリオは次の3つとする。

1. **ファイル選択から表示まで。** 標準ファイル選択でサンプルを選び、読み込み後の日本語・見出し・本文・リストの表示と、長文の末尾へのスクロールを確認する。
2. **取り消し・画面回転後の保持。** 文書の途中までスクロールしてから選択を取り消し、文書と閲覧位置が保持されることを確認する。画面回転後も同様に確認する。
3. **読み込みエラーからの復帰。** 不正 UTF-8 の合成ファイルを選んでエラー表示を確認し、正常な文書を再選択して読み込み・表示へ復帰できることを確認する。

この E2E では実際の標準ファイル選択と端末上の文書へのアクセスを通す。導入時に、テストごとのアプリ状態・文書・権限の初期化と後片付け、非同期の読み込み完了を条件で待つ方法、各操作のタイムアウトを定義する。固定時間の待機だけに頼らず、操作・表示のどの段階で失敗したかを追える結果を残す。個人のファイルやアカウントを含まない専用のテスト環境を使う。

Dropbox アプリからの保存と実際のクラウド接続は、引き続き[端末確認手順](device-testing.md)に沿って手動確認する。自動 E2E の成功と Dropbox 経由の利用経路の成功を区別し、既存の Robolectric・実機スモークテストも維持する。

導入する変更では、依存・テスト・端末構成・CI 定義をそろえ、採用バージョン、システムイメージ、入力の配置・初期化方法、実行コマンド、タイムアウト、レポートの場所を[ビルド・検証の手引き](android-build.md)へ記録する。対象コミット・APK・実行環境と各シナリオの成否を残し、エミュレーター上の結果を実機で確認済みとは扱わない。

### テストの十分性と、テスト自身の変更

テストの十分性は、誤りの起こりやすさと影響から判断する。固定値を返す、末尾の項目を落とす、エラーを無視するなど、明らかに誤った実装でも成功できないかを検討する（悪魔の代弁者）。重要な保証やテストの変更では、必要に応じて実装を一時的に変え、意図したアサーションで失敗することを確認する。調査用の変更は取り除き、正しい実装で再実行してから確定する。

このアプリで検出能力を確かめる代表例は次のとおり。

| 一時的に加える誤り | 確認する保証 |
| --- | --- |
| 見出しレベルを常に1にする | 深さの異なる見出しを区別し、正しいレベルを返す |
| 文書の最後のブロックを落とす | 末尾の件数・内容を保持する |
| 不正 UTF-8 を置換文字として受け入れる | 内容を黙って変えず、文字コードの誤りとして拒否する |

テストオラクル（結果の正しさを判定する基準）も点検する。件数だけで内容の欠落を見逃したり、同じ実装を通した二つの結果の比較で共通の誤りを見逃したりしないよう、期待値は仕様に基づき、実装とは独立に定める。誤実装で成功してしまった場合は入力とアサーションを見直し、狙った保証の違反で失敗することを確かめる。コンパイル失敗や環境エラーは検出能力の確認に数えない。

テストのケース・アサーションは、既存の保証を保ちながら追加する。テストのヘルパー抽出などの構造整理では本番コードを固定し、本番コードの整理ではテストを固定する。可能な限り別のコミットに分け、同時変更が避けられない場合は、上記の検出能力の確認を行う。

### カバレッジ計測を導入する

カバレッジ計測を導入し、検証が薄い箇所を探すために使う。以下の計測方法・対象・合否条件を採用する。現時点で計測設定・レポート生成・CI 連携は未導入であり、方針の確定と実装の完了を区別する。プロパティベーステストやミューテーションテストの導入を待たず、既存の具体例テストで基準値を計測できるようにする。

#### 計測方法と対象範囲

[AGP 標準の JaCoCo 連携](https://developer.android.com/studio/test/coverage-report)を採用し、Debug ビルドの JVM テストから始める。`enableUnitTestCoverage` で計測を有効にし、対象 variant のレポート生成タスクを使う構成を導入時に検証する。現在の AGP・Gradle・内蔵 Kotlin・Robolectric と組み合わせて、既存テストの成功と、実際に対象コードの実行がレポートへ反映されることを確認する。Kotlin の表示・フィルターや設定の保守負担に問題がある場合は、[Kover](https://kotlin.github.io/kotlinx-kover/gradle-plugin/) を代替候補として比較し、採用方針を変更する理由と互換性を記録する。

| 項目 | 初期導入の範囲 |
| --- | --- |
| 実行するテスト | Debug の JVM テスト全体。通常の単体テストと Robolectric のテストを含み、プロパティテストの追加後はそれも含める |
| 計測するコード | `app/src/main` のアプリ実装。解析・デコードだけでなく、ViewModel・ファイルアクセス・画面と表示処理も対象にする |
| 指標 | 行カバレッジ・分岐カバレッジ。全体とクラス・ソース別の未実行箇所を確認する |
| レポート | 人が確認する HTML と、CI で集計できる XML。標準タスクで不足する形式や除外設定は、必要なレポートタスクで補う |
| 初期対象外 | 端末上の手動操作、instrumented test、Release のカバレッジ。既存の Release テスト・ビルド・端末確認は維持する |

Android の生成コード（`R`、生成される場合の `BuildConfig` など）、テストコード、依存ライブラリは集計対象から除外する。アプリ自身の判断を含むコードを達成率のために除外せず、除外パターンと理由を記録する。Kotlin の生成コードやインライン処理に由来する表示は実装と照合し、クラス名の広いパターンで実際の処理まで除外しない。

#### レポートの使い方と他のテストとの関係

同じテスト範囲・variant・ツールの版・除外条件で、行・分岐のレポートを比較する。初期は `OrgParser`・`DocumentDecoder` の境界条件と、読み込み失敗・再試行・状態保持に関わる未実行箇所を優先する。入力と期待結果を説明できる不足ケースを追加し、実際に誤りを検出できるかを確かめる。

- カバレッジは実行された範囲を示す。アサーションの正しさや検出能力は、具体例・プロパティテストとミューテーションテストで補う。高い達成率だけを完了条件にしない。
- [JaCoCo の分岐カバレッジ](https://www.jacoco.org/jacoco/trunk/doc/counters.html)は例外処理を分岐として数えない。不正 UTF-8、権限喪失、読み込み例外などは、レポートに加えて対応するテストと期待結果を確認する。
- 部分的なテスト実行のレポートは調査用とし、全テストの基準値と区別する。端末でしか確認していない操作は JVM カバレッジへ含めず、異なる variant の割合を単純に足し合わせない。
- ミューテーションテストは別の実行として扱い、変更された実装の計測結果を通常のカバレッジへ混ぜない。計測エージェントの併用が検証へ影響しないよう、導入時に実行設定を確認する。

#### 合否判定

最低カバレッジと、変更によるカバレッジの低下を CI で判定する。次の両方を合格条件とし、満たさない場合はパイプラインを失敗させ、PR のマージを止める。

- **最低カバレッジは80%とする。** 上記の除外条件を適用した `:app` の Debug 全体について、行カバレッジ・分岐カバレッジのそれぞれが80%以上であることを求める。丸め前の値で判定し、クラスごとの一律80%は初期条件にしない。
- **変更対象のカバレッジを低下させない。** PR ではマージ先ブランチの最新コミット、`main` 更新時は更新前の `main` のコミットを基準にする。比較可能な変更対象の既存ソースファイル群について、変更前後の行・分岐カバレッジをそれぞれ比較し、いずれも低下していないことを求める。基準側と変更側は同じファイル群・variant・ツールの版・除外条件・テスト実行条件で計測する。新規ファイルも全体の80%判定の集計に含める。

初回など比較元がない場合は、低下の判定を未実施と明記し、80%の最低条件は適用する。分岐がないなど指標の分母が0の場合は対象外と明示し、実行データの欠落を対象外や合格として扱わない。閾値割れや低下が見つかったら、意味のある動作を検証するテストを追加する。除外の拡大や閾値の引き下げを改善の代わりにしない。

#### CI と導入の順序

1. 既存テストによる初回の HTML・XML レポートをローカルで生成し、採用ツールの版、対象・除外条件、対象コミット、行・分岐の値、計測による実行時間の増加を記録する。実行済みの処理が未計測になっていないか、ソースとの対応を確認する。
2. ローカルでは専用コマンド、PR と `main` 更新時は CI で Debug の計測・レポート生成・合否判定を実行し、既存の検証レポートとともに成果物として保存する。同じテストを計測用・通常用に重複実行する必要がないかを確認し、共通のビルド・検証を維持した実行順序にする。PR の比較元コミットを記録し、マージ先が更新されたら比較し直す。
3. 当該実行で生成したデータだけを使い、古いレポートを今回の結果として公開しない。テスト失敗で生成されなかった場合は未生成と報告し、テスト結果と原因を確認する。テスト成功後の計測・レポート生成の失敗や成果物の欠落は CI で検出する。
4. 80%未満や変更対象の低下を検出して失敗することと、条件を満たす状態で成功することを確認する。初回計測が80%未満なら、必要なテストを追加してから合否判定を含む変更を統合する。PR では未実行行・分岐とアサーションの内容も確認する。マージを止めるための必須 CI チェックを GitHub 側でも設定し、ワークフローの追加だけで保護が有効になったとは扱わない。

計測設定・レポートタスク・CI を追加する変更で、採用バージョン、対象・除外範囲、実行コマンド、HTML・XML と実行データの場所、確認方法を[ビルド・検証の手引き](android-build.md)へ記録する。具体的なタスク名・出力先は現在のビルドで検証してから実行手順へ載せる。文書へ方針を追加したことだけで計測済みとは扱わない。

### プロパティベーステストとミューテーションテストを段階的に導入する

プロパティベーステスト（property based testing）は org 解析・UTF-8 デコードへ導入し、ミューテーションテスト（mutation testing）は同じ範囲で試験導入する。前者は多数の生成入力で仕様上の性質を確かめ、後者は実装へ小さな誤りを加えて既存テストが検出できるかを調べる。既存の具体例テストを維持し、両手法を補完的に使う。

プロパティベーステストは以下の対象・構成・実行回数・合否条件を採用する。ミューテーションテストは後述の試験導入方針と閾値の決定手順を採用し、固定閾値の具体的な数値は試験導入後に決定する。現時点で両手法のライブラリ・専用タスク・CI は未導入であり、方針の確定と実装の完了を区別する。採用バージョン、入力サイズ上限の具体値、実行設定は導入時に定め、現在のビルド環境との互換性、実行時間、検出能力を確認する。

#### 対象とプロパティの設計

最初は `:app` 内の `OrgParser` と `DocumentDecoder` を対象にし、端末や Android の画面を起動しないローカル JVM テストで実行する。画面、ファイル選択、状態復元、実際のプロバイダーとの連携は、引き続き Robolectric と端末で確認する。モジュール分離は初期導入の前提にせず、Android のビルド設定との接続が保守負担になる場合に純 Kotlin/JVM モジュールへの分離を検討する。

この2つを初期対象にする理由は、多様な入力の組み合わせを生成しやすく、仕様から期待結果を定められ、Android の画面や外部 I/O を使わずに多数のケースを実行できるためである。`OrgParser` では構文・字下げ・改行などの組み合わせ、`DocumentDecoder` では正常な UTF-8 の内容保持と不正なバイト列の拒否を確かめる。これはコード構造と入力の性質に基づく優先順位であり、他の対象との検出効果・実行速度の比較測定による選定ではない。

適用範囲をこの2つへ固定しない。状態管理の検証不足や不具合が見つかった場合は、`ReaderViewModel` の状態遷移へ適用を広げる。成功・失敗・再試行・連続選択などの操作列に対し、表示文書と保存 URI の整合性を確かめる。その際は各ケースの状態初期化、coroutine の実行制御、期待する状態遷移のモデルを用意する。解析・デコードのプロパティテストだけでアプリ全体の入力・状態の組み合わせを十分に検証したとはみなさない。

プロパティベーステストには [Kotest Property](https://kotest.io/docs/proptest/property-based-testing.html) を使い、既存の JUnit 4 を維持する。テスト依存に `kotest-property` を追加し、既存の `@Test` 内で `runTest` と `checkAll` を使う構成から始める。採用バージョンと依存関係の互換性は導入時に検証する。

| 対象 | 生成する入力と前提 | 確認する性質 |
| --- | --- | --- |
| 見出し | 深さ、空でない改行なしのタイトル、日本語・絵文字 | `*` の数がレベルになり、タイトルが保持される |
| 箇条書き | マーカー、空白・タブによる字下げ、改行なしの本文。`*` の箇条書きには字下げを付ける | 種別・本文・インデントが仕様どおりになる |
| 改行・BOM | BOM と CR を含まない文書から CRLF 版、先頭 BOM 付き版を作る | 元の LF 版と解析結果が等しい |
| リテラルブロック | 見出し・リスト風の本文、ブロック名の大小文字。本文には対応する終了行を含めない | ブロック内を構文として解釈せず、終了後は通常解析へ戻る |
| UTF-8 | 孤立サロゲートを含まない Unicode 文字列、既知の不正バイト列を含む入力 | 正常時は UTF-8 経由の結果が直接解析と一致し、不正時は文字コードの例外になる |
| 解析の独立性 | 異なる文書 A・B を作り、A → B → A の順に解析する。未終了のリテラルブロックや空文書も含める | 各文書の仕様から定めた結果と一致し、前回の段落やブロック状態が混ざらない |

入力は仕様から構文を組み立て、完全なランダム文字列だけに偏らせない。空入力、境界値、対応外構文、不正入力も明示的に含め、生成する文字列長・文書量に上限を設ける。本番と同じ正規表現や判定処理で期待値を計算せず、深さとタイトルから `Heading` の期待値を作るなど、仕様から結果を定める。

改行・BOM の変換前後の一致と、UTF-8 経由・直接解析の一致は、既存の具体例テストを多様な入力へ広げる性質として使う。内容の保持については、見出しやリストと解釈されないよう固定の接頭辞を付けた改行なしの合成本文を UTF-8 で読み、元の本文を持つ `Paragraph` が返ることも確認する。両方の経路に共通する欠落を、経路間の一致だけで見逃さないためである。

失敗時は [shrinking](https://kotest.io/docs/proptest/property-test-shrinking.html) で簡単になった反例、[seed](https://kotest.io/docs/proptest/property-test-seeds.html)、生成回数、ツールの版を記録して再現する。見つかった反例は具体例の回帰テストへ追加する。入力は公開可能な合成データを使い、私的な文書を失敗ログや CI 成果物へ含めない。

合否判定は、定義した性質に反する入力が1件でも見つかったら失敗とする。成功するまで再実行して済ませず、記録した条件で原因を調べ、修正後に反例と関連テストを確認する。

#### ミューテーションテストの構成と評価

[PIT](https://pitest.org/) を候補にし、Android モジュールへの接続には [pl.droidsonroids.pitest](https://github.com/koral--/gradle-pitest-plugin) を試す。プラグインは Experimental とされているため、現在の AGP・Gradle・内蔵 Kotlin との互換性を実行して確認する。Kotlin が生成するコードによるノイズを評価し、必要に応じて [Arcmutate Kotlin plugin](https://docs.arcmutate.com/docs/kotlin.html) の利用を検討する。利用条件・ライセンスを確認し、ライセンスファイルなどの秘密情報はコミットや公開成果物へ含めない。

初回は変更対象を `OrgParser` と `DocumentDecoder`、実行テストを対応する具体例・プロパティテストへ絞り、PIT の既定の変更演算子から始める。Android・Kotlin の生成コードや単純なデータ保持を初期対象へ広げない。Robolectric を使うテストへの拡大は、[専用の Android 対応](https://docs.arcmutate.com/docs/android.html)とその利用条件・制約を確認してから判断する。

- 生き残った mutation は、仕様上の誤りを見逃しているもの、元と同じ振る舞いになるもの、生成コードなどによるノイズを区別する。意味のある不足からテストを改善し、除外には理由を残す。
- タイムアウト・実行エラー・未実行は、意図したアサーションによる検出と分けて記録する。変更前の正しい実装でテストが成功することも確認する。
- mutation score の固定閾値は試験導入後に決定する。試験導入中は生き残った変更のレビューで重要な検証不足を修正し、実行時間、意味のある不足の発見数、ノイズ、調査・保守時間を測って継続利用と対象拡大を判断する。
- [既定の変更演算子](https://pitest.org/quickstart/mutators/)が正規表現内の構文を網羅するとはみなさない。高い score だけで構文の検証が十分とは判断せず、「見出しレベルを固定する」「最後の段落を落とす」などの代表的な誤実装を検出できるかも導入時に確認する。一時的な変更は残さない。

#### mutation score の閾値を決める手順

mutation score は、生成した変更のうちテストで検出できた変更の割合を示す。カバレッジで採用した80%をそのまま適用せず、次の手順で維持すべき検出能力を確認してから、固定閾値の数値を決定する。

1. **計測条件を固定する。** 対象コード、変更演算子、ツール・プラグインの版、除外条件、プロパティテストの seed・生成回数・入力サイズ上限を記録する。採用ツールが score の分子・分母へどの状態を含めるかも確認し、異なる集計方法の値を混同しない。
2. **初回結果をレビューする。** score と変更の件数・内訳を確認し、生き残った変更をテスト不足、元と同じ振る舞い、生成コード由来のノイズに分ける。除外する場合は根拠を記録し、計測設定へ反映する。タイムアウト・実行エラーはアサーションによる検出と分け、原因を確認する。
3. **重要な見逃しを修正する。** 不正 UTF-8 を受け入れる、見出しレベルを誤る、文書の末尾を落とすなど、仕様上重要な誤りを見逃している場合は、期待する振る舞いを検証するテストを追加する。
4. **改善後の実測値から最低値を決める。** 同じ条件で再計測し、レビューした結果を維持できる下限を固定閾値にする。余裕を設ける場合も理由を記録する。対象・集計方法・閾値・決定理由を文書と実行設定へ反映し、閾値未満で失敗することを確認する。

閾値の導入後は「score が閾値以上」と「重要な振る舞いを壊す変更を見逃していない」の両方で判断する。score が高くても重要な見逃しは修正対象とし、実行エラーや計測の欠落を合格として扱わない。ツール・変更演算子・対象・除外条件を変える場合は、結果の比較可能性と閾値の根拠を見直し、合格させるためだけに閾値を引き下げない。

#### 実行頻度と導入の順序

プロパティベーステストは早い段階で反例を発見するため、開発中の関連する性質と、PR 作成・更新時の対象の性質を、それぞれ各1,000例検証する。最終受け入れでは、受け入れ対象コミットの CI 成功を確認する。週次・任意の探索専用の実行枠は設けない。失敗調査では記録した seed による再現を行う。

1,000例は実測前の初期値であり、検証の十分性を保証する数値ではない。導入時に実行時間と検出効果を確認し、生成する入力とサイズ上限も評価する。回数や入力サイズ上限を見直す場合は、理由と検出能力への影響を記録する。

| 実行契機 | プロパティベーステスト |
| --- | --- |
| 開発中 | 関連する性質を各1,000例 |
| PR 作成・更新時 | 対象の性質を各1,000例、seed を記録 |
| 最終受け入れ | 受け入れ対象コミットの CI 成功を確認 |

ミューテーションテストの実行頻度は引き続き次の試験導入方針とする。

| 実行契機 | ミューテーションテスト |
| --- | --- |
| 開発中 | 必要なクラスだけ手動実行 |
| PR | 初期は任意。運用が安定したら対象変更時に実行 |
| 定期・手動 | 対象範囲を一通り実行し、レポートを保存 |

通常のプロパティベーステストは seed を変えて探索範囲を広げ、失敗時は記録した seed で再現する。ミューテーションテスト内では seed・生成回数・入力サイズの上限を固定し、mutation ごとに入力が変わって結果や実行時間の比較が難しくなることを避ける。

1. 解析・デコードへ4〜6個のプロパティテストを追加し、既存の具体例テストと共通のビルド・検証を通す。
2. 同じ対象でミューテーションテストを試し、対象コード・変更演算子・seed・生成回数などの条件をそろえて、既存テストだけの場合とプロパティテスト追加後の検出能力・実行時間を比較する。
3. プロパティベーステストは導入時に通常のローカル検証と PR 作成・更新時の CI に組み込み、1件の反例でも失敗することと、記録した seed で再現できることを確認する。最終受け入れでは対象コミットの成功結果と対応付ける。ミューテーションテストは試験導入の効果と保守負担が見合えば CI に組み込む。依存・専用タスク・CI 定義と同じ変更で、採用バージョン、対象・除外範囲、入力サイズ上限、生成回数と seed の指定方法、実行コマンド、レポートの場所を[ビルド・検証の手引き](android-build.md)へ記録する。文書に方針を書いたことだけで、実装・検証済みとは扱わない。

### 共通の検証

実装中は関連テストで早く結果を得て、アプリ・テスト・ビルド設定の変更は完了前に以下を実行する。

```sh
./gradlew --console=plain check assembleDebug
```

Debug / Release の JVM テスト、Lint、Debug APK を確認する。環境、個別実行、レポートの場所、警告の扱いは[ビルド・検証の手引き](android-build.md)を参照する。Git フックとコミットメッセージ検証の導入・手動確認・テストは[Git 運用規約](git-workflow.md#自動検証と-git-フック)に従う。文書だけの変更では内容・ローカルリンク・`git diff --check` を確認し、APK の再生成や端末操作を必須にしない。文書内のコマンドや設定値を変えた場合は、対応する実装・定義と照合する。

### 品質の劣化を継続的に検出する

性能や依存関係など、維持する必要がある品質を選び、次の手順で繰り返し確認できる形にする。

1. 対象の操作・入力・端末や実行環境・計測区間を固定し、変更前の値を記録する。性能は複数回測り、ばらつきも確認して許容範囲を決める。
2. 読み込み時間・メモリ使用量・許可する依存方向などを、測定や検査で確認する。許容範囲を外れた場合に誰が結果を確認し、何を修正・再計測するかを決める。
3. 自動化する場合は、ローカルのタスク・CI・実行手順・結果の保存先を同じ変更で整え、実際に範囲外の変更を検出できることも確かめる。実行時間や環境差のある検証は、高速なテストと分けて実行契機を記録する。
4. 機能・データ量・対象環境が変わったら、基準と測定方法を見直す。失敗が出た場合は原因を調べてから基準を更新し、変更理由を残す。

現行 CI に性能計測や依存構造の専用検査は組み込んでいない。導入前の手動測定も、実施した環境・値・範囲が分かるように残す。

#### 性能計測の対象と方法

性能計測は次の方針で導入する。現時点で計測用ビルド・計測設定・自動実行は未導入であり、読み込み時間・メモリ使用量の基準値と許容値も未確定である。既存の長文の末尾表示テストと、時間・メモリの計測結果は区別する。

| 項目 | 採用する方針 |
| --- | --- |
| 初期対象 | 文書の読み込み・UTF-8 デコード・org 解析・最初の内容表示 |
| 入力 | 公開可能な100・1,000・10,000項目の合成文書。バイト数と構成も固定する |
| 環境 | Pixel 10a／Android 17。同じビルド条件・端末設定・文書プロバイダーで比較する |
| 方法 | Android Studio Profiler とシステムトレースを使う。時間計測には Release 相当の計測用ビルドを使う |
| 指標 | 読み込み開始から最初の内容表示までの時間、解析時間、メモリ使用量 |
| 繰り返し | 各条件を5回測定し、中央値・最大値を記録する。初回の読み込みと同じ文書の再読み込みを分ける |
| 合否基準 | 初回計測と利用上の要求を基に、時間・メモリの許容値を決定する |
| 実行契機 | 初期は手動。性能に影響する変更で再計測し、継続実行が必要になったら自動化する |

計測区間は、アプリが選択された文書の読み込みを開始した時点から、最初の文書内容が画面に描画された時点までとする。利用者がファイルを選ぶ時間は含めず、解析区間も別に測る。初回の基準計測は端末上の合成文書を使い、クラウド経由など条件の異なる読み込みは別の結果として記録する。計測開始・終了をトレース上で識別する方法と、メモリの指標・採取タイミングは、導入時に定義して実装・手順をそろえる。

[Android のプロファイリング手引き](https://developer.android.com/studio/profile)に沿って、時間計測は Release ベースの profileable な計測用ビルドで行う。詳細なメモリ調査に Debug を使う場合は、その結果と計測条件を分けて記録する。比較時は端末設定に加え、アプリの起動状態、温度・負荷、計測ツールの条件もそろえ、各回の値とばらつきを確認する。

初回計測後に、対象の入力・操作に必要な応答性とメモリ使用量を検討し、指標ごとの許容値と合否に使う統計値を決定する。許容値を超えた場合は原因を調べ、修正または条件の見直し後に同じ方法で再計測する。基準値の変更には理由を残し、計測前に性能条件を達成済みとは扱わない。

指標は「長い文書を開き、待ち時間やメモリ不足で閲覧を妨げられない」という利用目的へ結び付ける。現状の全文をメモリへ読む方式では、項目数に加えて本文の長さ・バイト数による影響も調べる。各回の測定値からばらつきを確認し、中央値や平均が許容範囲でも最大値などが受け入れ条件を外れていないかを点検する。1万項目の末尾表示の成功やカバレッジの閾値達成を、快適に読めることの代わりにしない。

スクロールの滑らかさは後続の計測対象とし、必要になった段階で [Macrobenchmark](https://developer.android.com/topic/performance/benchmarking/benchmarking-overview) による自動計測を追加する。初期の読み込み時間・メモリ計測だけでスクロール性能まで検証したとはみなさない。

導入する変更では、計測用ビルド・ツールの設定、合成文書の生成方法、実行手順を[ビルド・検証の手引き](android-build.md)と[端末確認手順](device-testing.md)へ記録する。結果には対象コミット・APK の識別情報、入力条件、計測環境、各回の値、中央値・最大値、許容値と判定を残し、未確定の条件は未確定と明記する。

#### 依存構造を自動検査する

依存構造の検査には [ArchUnit](https://www.archunit.org/userguide/html/000_Index.html) を採用し、既存の JUnit 4 の JVM テストへ追加する。アプリのコンパイル済みクラスの依存関係を検査し、現在の単一モジュール構成を維持して導入する。現時点で検査ライブラリ・規則のテスト・CI での実行は未導入であり、採用バージョンと現在のビルド環境との互換性は導入時に確認する。

初期の依存規則は次の3つとする。

| 対象 | 守る依存規則 |
| --- | --- |
| `OrgParser` と `OrgBlock` | Android・画面・ファイルアクセスの実装へ依存しない |
| `DocumentDecoder` | Android・画面・文書プロバイダーへ依存しない。渡されたストリームの読み取りと、JDK の文字コード処理は許可する |
| `ReaderViewModel` | 画面クラスや `ContentDocumentSource` の具体実装へ依存せず、`DocumentSource` を介して読み込む。Android の ViewModel・状態保存機能への依存は許可する |

通常の JVM テストに含め、ローカル・PR・`main` 更新時に実行する。定義した規則への違反が1件でもあればテストを失敗させる。導入時に、正しい依存関係で成功することと、意図的に加えた依存違反を検出して失敗することを確認し、一時的な違反は取り除く。対象クラスを取得できていることも確認し、対象が空のため検査されなかった状態を成功として扱わない。

検査対象はソースファイル単位の import 一覧ではなく、各クラスの依存関係から定める。同じファイルに Android と関わるクラスがあっても、それだけで `DocumentDecoder` 自身の違反とは判断しない。対象に関連する内部クラスなどの扱いも導入時に確認し、実際の依存違反を広い除外で隠さない。

パッケージ・モジュールの境界を設ける際は、その境界に合わせた循環依存の検査を追加する。規則の維持だけを目的にパッケージやモジュールを増やさず、責務や依存方針を変更する場合は、変更理由と規則を合わせて見直す。実行時の失敗・キャンセル・資源解放などは、引き続き機能テストと端末確認で検証する。

導入する変更で、採用バージョン、検査対象・除外条件、各規則の実装、実行コマンド、レポートの場所、違反を検出した確認結果を[ビルド・検証の手引き](android-build.md)へ記録する。

### 失敗・不具合を調べる

1. 操作、期待結果、実際の結果、対象コミット・成果物、環境を押さえ、公開可能な最小の再現データを用意する。
2. 仮説と予測する結果を一つ立て、条件を変えて確かめる。入力や処理を半分ずつ減らして最小の再現例へ近づけ、必要なら履歴の比較や `git bisect` で原因を絞る。分岐を追加する前に、不要な状態や処理を除く方法も検討する。
3. 可能なら修正前に失敗する回帰テストを追加し、原因を直して成功を確認する。実機でしか再現できない場合は操作と結果を残す。
4. 同じ原因の境界条件と関連する既存動作を確認する。調査用の変更や個人情報を含むログは公開差分へ残さない。

同時実行などで決定的な再現が難しい不具合は、実行時間や回数を決めた反復テストで検証する。高速なテストとは分け、実行条件と結果を記録する。検証中に失敗が出なかったことだけで、不具合がないとは判断しない。

同じ条件で成否が変わるテストは、競合・時刻・共有状態・外部 I/O などを調べる。成功するまで再実行して完了にせず、無効化を修正の代わりにしない。隔離が必要なら理由、失われる保証、代替の確認、復旧条件を記録し、必須検証の条件を満たすまでは統合しない。

調査が進まない場合は、一定時間で仮説・試したこと・分からない点を書き出し、説明や休憩を挟んで前提を見直す。ログは未処理例外、処理の成否、再現に必要な非決定的な条件や副作用へ絞り、個人の文書内容・ファイル名・URI は記録しない。純粋な計算の中間値をすべて残す方法は避ける。

## 5. CI と端末で変更を確認する

短命の作業ブランチで変更を小さく共有し、最新の `main` と組み合わせた状態を検証する。ブランチや PR の扱いは[Git 運用規約](git-workflow.md)に従う。CI サーバーの存在に加えて、頻繁な統合と失敗への対応を開発の習慣にする。

半日程度で一貫した変更まで進められない場合は、作業の分割や未完成の経路を隠すフラグを検討する。この目安で分割を見直しつつ、統合に必要な検証とレビューを維持し、Git の操作は依頼された範囲で行う。

レビューでは受け入れ条件、境界条件、依存方向、失敗時の操作を確認し、作者以外が変更理由と処理を追えるかを確かめる。自動検証の成功に加えて、テストが見逃しそうな誤りも検討する。

十分に確認できない大きさの変更には、分割を求める。変更に関係するテストや操作を実行して確かめる。実行できなかった範囲は未確認として共有する。

- 指摘は、修正必須の問題と改善提案を区別する。
- 指摘には理由を添え、必要に応じて具体的な代替案を示す。
- 意見が分かれた場合は、受け入れ条件・検証結果・変更リスクを基準に判断し、採否の理由を残す。

作成者のセルフレビューと、別の担当者によるレビューでは、以下の[レビューチェックリスト](#review-checklist)を使う。PR 作成前に確認し、指摘への修正や対象コミットの更新後には、影響する項目を再確認する。結果は [PR テンプレート](../.github/pull_request_template.md)へ記録する。PR を作らない段階では、同じ形式を作業メモや完了報告で使ってよい。

1. ローカルの検証後に、依頼された範囲で push・PR 作成を行う。PR には問題、変更後の振る舞い、理由、検証結果と未確認事項を書く。
2. GitHub Actions で対象コミットの結果とレポートを確認する。PR の検証後に `main` や対象コードが更新された場合は、必要な検証をやり直す。
3. 端末確認が必要な変更では、成功した CI run の APK を取得し、[端末確認手順](device-testing.md)で受け入れ条件と既存の基本動作を確認する。同じ APK を使い、取得元と SHA-256 を記録する。
4. 統合後も `main` の CI 結果を確認し、失敗時は修正または取り消しを優先する。

CI の `verify` には、Git フック・メッセージ検証処理のテスト、コミットメッセージと PR タイトルの検証、ビルド・Lint・JVM テストと Debug APK・レポートの保存を定義している。必須チェックとブランチ保護は下記の確定方針に沿って GitHub 側にも設定する。ワークフローを記述したことだけで有効になったとは扱わない。Play ストア配信、Release 署名、本番への自動配信は未整備であり、必要になった時点で版の識別、署名・配布、データ互換性、復旧手順を整える。

UI、ファイルアクセス、状態復元、依存や SDK など実行環境へ影響する変更では端末確認を行う。純粋な解析処理などは変更のリスクに応じて判断し、省略する場合は理由を残す。CI を利用できない段階ではローカル APK で確認を進め、その結果を CI 成果物の確認と区別する。

インストールできたことだけで利用経路を確認済みとしない。Dropbox の保存操作を省略した場合、実機確認を実行できなかった場合、対象と異なる OS で確認した場合は、その範囲を明記する。Debug APK の署名差による入れ替えは状態とアクセス権を失うため、[端末確認手順](device-testing.md)の扱いに従う。

### レビューチェックリスト

コード、テスト、設定、CI、文書の変更に適用する。AI による提案・生成・調査を使った変更も同じ基準で確認する。AI の説明や検証報告は、差分・参照先・実行結果と照合する。

#### 記録と判定

- 各項目の結果を「確認済み」「対象外」「未確認」「要修正」のいずれかで記録する。チェックは確認済みの項目にだけ付ける。対象外には理由、未確認には理由と次の確認方法を残す。
- 確認根拠にはファイル・行、仕様、対象版の公式資料、実行コマンド・環境・結果などを記す。同じ結果と根拠の項目は ID をまとめて記録してよい。異なる結果や根拠は行を分ける。
- 作成者と確認者、対象コミットまたは未コミット差分の範囲を明記する。確認者が人か agent か、作成者と同じか別かを記す。セルフレビューはその旨を記す。修正後は対象の版を更新し、指摘と再確認結果を対応させる。
- 要求と異なる動作、機密情報の露出、重要な処理の理解不足、必須検証の失敗が残る場合は、修正または変更範囲の縮小を行う。必須の確認が未確認なら統合判断を保留する。
- 残るリスクには影響、受け入れる理由、判断者、後続対応の担当と期限または再検討条件を記す。リスクの受け入れを理由に、必須 CI や既存の完了条件を省略しない。

文書のみの変更では内容・リンク・差分を検証し、実装・端末に関する項目は理由を付けて対象外にできる。全項目の確認だけで、未想定のリスクがなくなるとは判断しない。確認と記録は人または以下の手順を使う agent が行う。PR テンプレートの記入や判定を自動検証する CI は導入していない。

<a id="agent-review"></a>

#### agent によるレビュー手順

agent が変更を作成・修正した場合は、完了報告前に本手順でレビューする。「レビューチェックリストを実施して」という依頼にも同じ手順を使う。別のレビュー agent を利用できる場合は、その agent に依頼する。利用できない場合は作成 agent が実施し、セルフレビューであることと制約を記録する。別 agent への依頼でも、確認範囲は渡した対象と実際に読んだ内容に限る。

1. **対象を固定する。** 作成 agent は目的・受け入れ条件・対象範囲・既知の未確認事項を整理する。レビュー agent は `git status --short`、現在のブランチ、対象の履歴を確認する。コミット済みの変更は比較元・先の SHA を記録し、`git diff <base>...<head>` など意図した差分を読む。未コミット変更は `git diff`、`git diff --cached`、`git ls-files --others --exclude-standard` で把握し、対象ファイル一覧と内容ハッシュなど変更を識別できる情報を記録する。無関係な既存変更とローカル専用資料は対象へ含めない。
2. **根拠を直接確かめる。** 公開の開発手順・Git 運用規約、差分、関連コード・テスト・設定を読む。作成 agent の説明は検証の手掛かりとし、参照先や実行結果と照合する。新しい API などが関係する場合は、対象版の公式資料を確認する。
3. **必要な検証を実行する。** 変更に合う既存のコマンドでビルド・Lint・テスト、または文書の内容・リンク・差分を確認する。既存の実行結果を使う場合は、実行者・対象版・環境・結果を明記し、レビュー agent 自身の実行と区別する。実行できない確認は理由と次の確認方法を記す。端末操作や利用者評価、外部サービスの契約条件、業務上のリスク受け入れなどは、証拠や判断権限がなければ未確認とする。
4. **30項目を判定する。** R01〜R30すべてに結果と根拠または理由を付け、該当しない項目も対象外として残す。同じ結果・根拠の ID だけをまとめてよい。指摘には ID、重要度（修正必須・改善提案）、ファイル・行、問題が起きる条件、影響、修正案を記す。見つからなかった問題を、存在しないと保証しない。
5. **修正と再確認を分ける。** レビュー agent は対象ファイルを変更せず、結果を作成 agent へ返す。必要な修正は作成 agent が行い、修正後の対象版と差分を渡して再確認を依頼する。セルフレビューでは実装と確認の段階を分ける。確認中に対象が更新された場合は更新内容を確認し、影響する項目を再判定する。
6. **結果を保存・報告する。** [PR テンプレート](../.github/pull_request_template.md)の形式で、確認者、対象版、各 ID の結果、指摘と対応、残るリスク、判定を残す。PR がなければ作業メモや完了報告に残す。公開先への投稿は依頼の範囲に従い、レビューの依頼だけで PR へのコメント投稿、承認、マージを行わない。修正必須があれば「要修正」、必須確認や権限外の判断が残れば「未確認のため保留」とし、完了報告でもその範囲を明記する。

レビュー agent の「採用可」は、記載した対象と範囲についての確認結果である。GitHub の承認、必須 CI の成功、端末での成功、リスクを受け入れる権限の代わりにはならない。agent が実行・判断できる範囲は、既存の指示と今回の依頼に従う。

**依頼文のひな形**

```text
レビュー担当として、AGENTS.md、docs/development-workflow.md、
docs/git-workflow.mdを読み、開発手順のagentによるレビューを実施してください。
目的・受け入れ条件：<利用者の操作と期待結果>
対象：<比較元・先のSHA、または未コミット変更の対象ファイル一覧>
既知の未確認事項：<理由・不足する環境や判断>
既存の検証結果：<実行者・対象版・コマンド・環境・結果。なければ「なし」>
対象ファイルは変更せず、公開可能な対象だけを確認してください。
R01〜R30すべての結果と根拠、指摘、未確認事項、残るリスク、判定を返してください。
実行していない検証は成功とせず、外部への投稿・承認・マージは行わないでください。
```

返答は PR テンプレートの「レビュー記録」「指摘と残るリスク」に合わせる。未確認が一件もないことより、根拠のある結果と不足が読み取れることを重視する。

#### 1. 要求と文脈（R01〜R04）

- [ ] **R01** 利用者の目的、入力・操作・期待結果が明記され、変更が対応している。推測で補った条件は、確認済みの事実と区別した。
- [ ] **R02** 正常時に加え、関係する空入力、不正入力、取り消し、失敗、再試行の動作を定めた。文書を開く変更なら、選択取り消しや読み込み失敗後の表示も対象にした。
- [ ] **R03** 言語・フレームワークの版、規約、依存先、品質の制約を実際の設定と照合した。プロンプトやテンプレートに古い前提を残していない。
- [ ] **R04** 未追跡ファイルも含めて変更対象を確認し、依頼に必要な範囲へ絞った。無関係な整理・設定変更・生成物は除くか、別の変更へ分けた。

#### 2. 情報と技術の正確性（R05〜R07）

- [ ] **R05** 新しく使う API、クラス、設定キー、コマンド、依存パッケージが実在し、採用版で利用できることを公式資料と必要なビルド・実行で確認した。
- [ ] **R06** 技術選択や動作説明の出典を読み、主張を裏付けることを確認した。例示、将来予測、未計測の数値を、現在の実測や保証として扱っていない。
- [ ] **R07** 新しい技術や言語間変換では、文字コード、数値の範囲、null、例外、並行処理など、対象固有の意味を検証した。デコードの変更なら不正 UTF-8 の拒否も確認した。

#### 3. 理解と設計（R08〜R11）

- [ ] **R08** 作成者と確認者が、変更の動作と採用理由をコードや文書で説明できる。理解できない重要な処理は、調査・簡素化・分割してから判断した。
- [ ] **R09** 既存の責務分担、依存方向、エラーの扱いと整合する。解析・デコード、`DocumentSource`、`ReaderViewModel`、画面の境界を変える場合は、その理由と影響を確認した。
- [ ] **R10** 追加した抽象化、依存、重複処理の必要性を説明できる。標準機能や既存実装で解決できるか検討した。
- [ ] **R11** 状態変更、I/O、非同期処理を入口から結果まで追った。関係する資源の解放、連続選択の完了順序、古い読み込みの遅延した成功・失敗、画面再作成時の状態を確認した。

#### 4. 情報の保護と安全な実装（R12〜R15）

- [ ] **R12** AI や外部ツールを使った場合、共有するコード・データ・添付・取得範囲と利用先の保存・入力利用条件を確認した。共有範囲は権限のある必要な内容に絞り、私的な文書や認証情報を渡していない。
- [ ] **R13** 差分、コミット対象、公開予定の履歴・PR・ログ・検証成果物に、認証情報、個人の文書内容・ファイル名・URI、ローカル専用資料が混入していない。問題があれば公開を止め、秘密の実体を記録へ転載せず対処する。
- [ ] **R14** 関係する入力検証、権限、ファイルアクセス、外部送信を確認した。URI 権限の喪失や不正入力で意図しない読み書き・情報露出が起きず、閲覧操作が元の文書を変更しないことを確認した。
- [ ] **R15** 新しい依存や持ち込むコード・素材の提供元、利用条件、必要な表示を確認した。AI 生成であることだけを利用可能とする根拠にしていない。

#### 5. 検証の十分性（R16〜R20）

- [ ] **R16** テストの期待値を仕様や利用例から定めた。実装の出力を正解にしたり、同じ誤りを含む二つの経路の一致だけで正しいと判断したりしていない。
- [ ] **R17** 重要な受け入れ条件を適切な層で検証し、関係する境界値、不正入力、失敗後の復帰を確認した。業務上の判断が必要なら、その条件を判断できる担当者と照合した。
- [ ] **R18** 重要な誤りを見逃さないか、入力とアサーションを点検した。実装とテストの同時変更では、見出しレベルの固定、末尾の欠落、エラーの無視などの誤実装でも成功してしまわないか確認した。
- [ ] **R19** コマンド、対象版・環境、実際の結果を確認した。テストの削除・無効化、アサーション・閾値の緩和、成功するまでの再実行で不具合を隠していない。カバレッジだけで十分と判断していない。
- [ ] **R20** 単体、連携、利用経路の検証範囲を区別した。必要な CI・端末確認を行い、未実行は理由と次の確認方法を記録した。Robolectric やローカル APK の成功を、対象端末や CI 生成 APK の成功へ置き換えていない。

#### 6. 利用者への配慮（R21〜R23）

- [ ] **R21** 名前、言語、日時、文字、入力形式などに、不要な文化的・利用者固有の制約がない。日本語や長い文書など、必要な利用者の例で確認した。
- [ ] **R22** UI の変更では、読み上げ、文字拡大、色以外の手掛かり、フォーカス・操作方法について、変更した主要操作を確認した。未実施の支援技術は未確認として記録した。
- [ ] **R23** 利用者向けの説明、エラー文、生成データが、実際の動作と用途に合っている。不当に利用者を排除する表現や仮定がなく、エラー後の次の操作が分かる。

#### 7. 変更規模と統合・運用（R24〜R27）

- [ ] **R24** 全体を理解して確認できる変更規模になっている。大きい場合は、途中でもビルド・検証できる単位へ分けた。
- [ ] **R25** 複数ファイルの変更では、呼び出し元、設定、登録箇所、データ形式、文書の整合性を確認した。個々のファイルの確認に加え、必要な連携も検証した。
- [ ] **R26** 性能改善を主張する場合、同じデータ量・環境・計測区間で変更前後を比較した。メモリ、読みやすさ、復旧性などへの影響も確認した。長文の末尾表示の成功だけで応答性を保証していない。
- [ ] **R27** 保存・移行・外部サービス・配布方法に影響する場合、互換性と失敗時の復旧方法を確認した。試作品を実利用へ進める場合も、失敗の影響に応じた保証を確認した。

#### 8. 判断と残る課題（R28〜R30）

- [ ] **R28** レビュー担当が採用理由、品質のトレードオフ、未確認の想定を根拠と照合して記録した。AI の推奨や生成できたことだけを採用理由にせず、担当の権限を越える判断は未確認として判断者へ引き継いだ。
- [ ] **R29** 修正必須の指摘と改善提案を区別し、修正後の差分と必要な検証を再確認した。採用の判断者と、残る課題の担当・期限または再検討条件が分かる。
- [ ] **R30** 変更の価値を、利用者の目的や品質の改善で説明できる。生成量や所要時間だけで、理解・レビュー・保守の負担を見落としていない。

### 必須 CI とブランチ保護

`main` への統合は、PR と必須 CI の成功を通す。最新の `main` を取り込んで検証し、個人開発では人による必須承認を当面0人としてセルフレビューを行い、レビュー指摘を解決してから Squash merge する。管理者への適用、直接 push・強制 push・削除の禁止、マージキューの扱いなど、GitHub 側の具体的な保護条件は[Git 運用規約](git-workflow.md)へ集約する。

必須 CI は、現在の `Android checks` の `verify` ジョブを起点にする。現行の `check assembleDebug` によるビルド・Lint・JVM テストと成果物の保存を維持し、カバレッジ・プロパティベーステストの PR 実行・依存構造検査は、それぞれ導入後に必須 CI の実行範囲へ含める。試験段階のミューテーションテスト、手動の性能計測、初期の E2E は各節の実行方針を維持し、一律に PR の必須ジョブへ追加しない。

2026-11-01 に GitHub 側へ保護を適用し、実際のチェック名 `verify` と実行元 GitHub Actions（App ID `15368`）を登録した。REST API で保存された設定を再取得し、GraphQL API でも `main` に適用されるルールを確認済みである。同じ保護設定の一時ブランチで、管理者による条件未達の更新・マージの拒否と、条件を満たす PR の Squash merge を確認した。実際の `main` 向け PR #5 でも `verify` の成功を確認し、設定値・対象コミット・検証用 PR・CI run・保証範囲は[検証記録](verification/2026-11-01-branch-protection.md)へ残している。以後も設定変更時は[Git 運用規約の確認手順](git-workflow.md#設定の維持と動作確認)に従い、設定の確認と PR での動作確認を区別する。

### 利用者が目的を達成できるかを評価する

初回と、利用経路・UI・操作に影響する変更時に、上記の利用者理解と受け入れ条件に沿って、実際の利用者による操作で使いやすさを確認する。公開サンプルや合成データを使い、対象の APK・端末・OS・表示や支援技術の設定を記録する。以下は採用する評価方針であり、評価の実施結果は別に記録する。

評価者の立場、org・Android のファイル操作への慣れ、アプリへの習熟度を記録する。開発者本人が利用者として評価する場合も、その立場と習熟度を明記する。単に文書を開けたという報告と、操作の見つけやすさ・迷い・手助けの必要性まで確認した結果を区別する。

評価前に[既存の検証記録](verification/2026-11-01-code-review.md)と以降の結果を読み、未確認の条件を今回の対象へ含めるか決める。既存記録に残る最大表示サイズ、TalkBack の読み込み中・空文書・エラー時の案内、見出し移動の詳細などは、評価対象の APK・条件を記録し、目的の操作を完了できたか確認して結果を追記する。手助けなしで再選択できるか、必要な本文へ移動して読めるかを評価し、過去の基本操作の成功を未確認の状態へ一般化しない。

#### 初期の評価課題

1. **保存した文書を開いて読む。** 指定した見出しの本文までたどり着き、内容を読めるかを確認する。
2. **長い文書で閲覧を続ける。** 目的の内容を探し、文書の途中から閲覧を続けられるかを確認する。
3. **取り消し・エラーから戻る。** ファイル選択の取り消しや読み込みエラーから、閲覧へ戻れるかを確認する。

#### 評価方法と判定

各課題について、達成する目的を伝えてから次の手順で評価する。

1. 「保存した org ファイルを開き、指定した見出しの本文を読む」など、達成する目的を伝える。最初から操作の順番を教えず、操作を見つけられるかを見る。
2. 目的を達成できたか、迷った場所、誤操作、説明や手助けが必要だった場面を記録する。効率が受け入れ条件なら所要時間や操作回数も確認する。
3. 操作後に、分かりにくかった点や期待と違った点を聞く。観察した事実、利用者の感想、開発者の解釈を分けて残す。
4. 目的の達成を妨げる問題から優先して小さく修正し、同じ目的と条件で再確認する。残る問題は影響と次の対応を記録する。

主要目的を達成できない問題は修正必須とする。迷いや説明・手助けが必要な箇所も改善対象として影響に応じて優先順位を付け、達成可否だけで評価を終えない。問題がアプリ、Android の標準ファイル選択、Dropbox の保存手順のどこで起きたかを記録し、利用経路全体の改善につなげる。所要時間や操作回数は、効率を受け入れ条件にする場合に測定する。

直接観察できない場合は、利用者自身の操作と報告で確認した範囲を残す。開発者や agent による確認はその主体を明記し、利用者による評価ができていない場合は未確認とする。普段使わない操作方法の確認結果を、その方法に慣れた利用者の評価まで実施したものとして扱わない。

評価結果は、課題ごとの達成可否、迷い・誤操作・手助け、利用者の感想、観察した事実と開発者の解釈、残る問題と次の対応を、上記の環境・評価者の情報とともに PR または検証記録へ残す。アクセシビリティの確認結果は確認範囲を分けて記録し、個人のファイル内容や評価者を特定する情報は公開記録へ含めない。

### 一般配布前に運用を具体化する

当面は検証用 Debug APK の運用を維持し、一般配布の実装と配布先の選定は開始時に行う。一般配布を始める前に、次の事項を決定・検証する方針を採用する。現時点で一般配布用の署名・配布・更新・復旧の仕組みは未整備であり、方針の確定と配布開始の準備完了を区別する。

| 項目 | 配布開始前に決めること |
| --- | --- |
| 配布方法 | 配布先、対象利用者、公開範囲、配布操作の担当 |
| 版と成果物の識別 | バージョン番号・リリースタグの規則、コミット・APK・SHA-256 の対応。Git 上の版・タグの扱いは Git 運用規約と合わせて定める |
| 署名 | 一般配布用の署名方式、鍵の保管・利用権限・バックアップ・復旧方法 |
| 環境別設定 | 開発・テスト・一般配布の設定と認証情報の分離 |
| 更新確認 | 新規インストールと旧版からの更新で、既存の文書・閲覧状態・アクセス権がどう扱われるか |
| 配布停止・復旧 | 問題発生時の停止条件、判断担当、修正版の提供方法、データの復旧方法 |
| 記録 | 採用理由と制約を ADR に、実行方法を開発・配布手順に残す |

配布候補の同じ成果物を使って署名・新規インストール・旧版からの更新を検証し、問題発生時に利用できる復旧手順も確認する。古い APK への入れ替えで復旧できるとは仮定せず、実際の配布経路とデータの扱いに合う方法を決める。不具合報告に必要なバージョン・環境・再現手順と、問題を検出する方法も整理する。

方式の採用理由・制約・検証方法は ADR に残す。配布開始前に、担当者が実行できる公開可能な手順と、対象成果物に対応する検証結果をそろえ、未確認事項が配布の受け入れ条件を妨げないことを確認する。署名鍵や認証情報の実体は文書・PR・ログ・成果物へ含めない。

#### 環境ごとの設定と認証情報

1. 開発・テスト・一般配布の役割を決め、接続先、データの保存先、機能フラグ、ログの詳細度、署名の区分を一覧にする。外部サービスを使う場合は、環境ごとに設定と認証情報を分離する。
2. 共有する設定定義と検証方法は版管理し、秘密情報の実体はローカル専用設定や CI の秘密情報管理などから渡す。配布 APK に含まれる値は利用者が取得できる前提で扱い、サービスの秘密鍵などを埋め込まない。
3. 各環境で、意図した設定が選ばれること、必要な値の不足時に明確に失敗すること、テストが本番データを変更しないことを確認する。検証記録には秘密値を含めず、設定の区分と対象の版を残す。

#### 配信と復旧の手順

1. 配布候補のコミット・バージョン・成果物の SHA-256 を対応させ、署名情報の確認、検証、配布を再実行できるタスクとして定義する。署名鍵は管理する場所と復旧方法を決め、検証済みの同じ成果物を配布する。
2. 配布対象・配布経路・監視できる範囲を確認し、一括配布か段階配布かを選ぶ。段階配布では、対象を広げる条件、観察する期間、中止・復旧する条件と判断する担当を事前に記録する。
3. 新規導入に加え、対応する旧版からの更新とデータの互換性を確認する。既存の文書・閲覧状態・アクセス権の扱いを期待結果と照合し、必要な再選択や復旧の案内も確認する。不具合時は配布を止め、旧版へ戻すか修正版を配布するかを判断する。Android の版番号・署名・データ形式を踏まえ、旧 APK へ戻せると仮定せず、実行可能な復旧方法を検証用環境で確かめる。
4. 配布・中止・復旧の結果を対象の版とともに記録する。自動化は検証済みの手順から進め、失敗時にも結果の保存と必要な後処理が行われることを確認する。

現在の CI は Debug APK の生成までであり、Release 署名・一般配布・復旧の自動化は未整備である。導入時にタスク・CI・実行手順を合わせて更新する。

#### 監視と不具合対応

当面は実際に得た利用者の報告と端末での再現確認を使い、一般配布の開始前に次の運用を具体化する方針を採用する。今回は受付先や監視サービスを選定せず、遠隔での自動収集・通知も追加しない。現在、配布後の自動収集・通知は未導入であり、方針の確定と運用の開始を区別する。

| 項目 | 一般配布前に決めること |
| --- | --- |
| 不具合の受付 | 報告先、受付担当、確認・対応状況の追跡先 |
| 報告内容 | アプリの版、端末・OS、操作、期待結果・実際の結果、公開可能な再現データ |
| 監視する指標 | 読み込み時間・読み込み失敗・クラッシュなどから、利用目的に必要な少数を選び、収集方法と確認頻度を定める |
| 異常の判断 | 通常時の値、異常とする条件、重要度、通知先、判断担当 |
| 対応 | 再現・原因調査・回帰テスト・修正・再確認の進め方と、必要に応じて配布停止や復旧へつなぐ条件 |
| 記録の管理 | 収集項目、保存先、保持期間、容量上限、削除方法 |

文書内容・個人のファイル名・URI・認証情報は収集対象に含めない。ログは時刻、処理の種類、成否、対象のアプリの版など、再現に必要な情報へ絞り、不要になった記録が削除されることを確認する。遠隔での自動収集が必要になった場合は、目的、収集項目、利用者への説明・設定、利用サービスを決めてから導入する。

通常時の値は版・対象環境とともに記録し、絶対値と通常時からの変化を基に異常や通知の条件を定める。自動監視を導入するときは、想定した異常を検知・通知でき、担当者が配布停止・復旧・修正などの対応へ進めることまで確認し、設定内容と確認結果を記録する。

不具合報告と監視結果から、対象の版・環境・期待結果・実際の結果・再現手順を整理する。影響を判断して復旧または修正を行い、回帰テストと必要な端末確認を経て結果を追跡先へ残す。指標・通知・対応手順の有用性は、配布や不具合対応の区切りで見直す。

## 6. 完了条件と報告

完了時には次の短いチェックリストを使う。

- [ ] 合意した受け入れ条件を満たし、変更範囲の既存動作を維持した。
- [ ] 変更に合う自動テスト・静的解析・ビルド、または文書の検証を実行し、結果を確認した。
- [ ] CI と端末確認について、確認済みの結果、該当しない項目、未実行・未確認の項目を区別した。
- [ ] 利用経路や UI の変更では、対象となる利用者・環境、アクセシビリティと使いやすさの評価結果、残る問題・未確認事項を記録した。
- [ ] 責務・境界・依存先を変える場合は、品質を保証する範囲とリスクを見直し、必要な検証・設計説明・図を更新した。
- [ ] 必要な文書と設計判断を更新し、差分・成果物にローカル専用資料、個人のメモ、認証情報を含めていない。
- [ ] [レビューチェックリスト](#review-checklist)の結果と根拠を記録し、修正必須の指摘を解消した。対象外と未確認を区別し、残るリスクの判断と後続対応を記録した。
- [ ] 残る課題と次の作業を明示し、Git の操作を依頼の範囲内で行った。

未実行・未確認の項目は理由と次の確認方法を残す。必須の検証が失敗している変更は統合しない。未確認を含む作業報告はできるが、検証済みとは報告しない。

agent へ依頼するときも、目的・受け入れ条件・変更範囲・検証手段を共有する。生成されたコードやコマンドも差分と実行結果で評価し、理解とレビューを省略しない。コミット・push・PR 作成・マージは[Git 運用規約](git-workflow.md)と依頼の実行範囲に従う。

完了報告は次の項目を基本にする。自動テスト、CI、実機、ユーザーの操作報告は、それぞれ確認した主体と範囲が分かるようにする。

```text
変更: 目的、変更後の振る舞い、主な設計判断
ローカル検証: 実行コマンド、結果、確認したレポート
CI: 対象コミット、run の URL、結果（未実行なら理由）
端末: APK の取得元・SHA-256、端末・OS、操作と期待結果・実際の結果
利用者評価（該当時）: 目的、評価者の立場・確認方法、表示や支援技術の設定、達成結果、迷いや手助け、残る問題
未確認・残る課題: 理由、影響、次の確認方法
Git 操作: コミット・push・PR・統合の実施範囲
```

長期に残す検証記録は `docs/verification/YYYY-MM-DD-short-description.md` に置く。日常の結果は PR へ記載してもよく、同じ記録を複数箇所へ転記しない。端末識別子、個人のファイル名・内容・URI、画面構造・画像などのローカル専用情報は公開記録へ含めない。

## 7. 開発フローを小さく改善する

機能の区切りや不具合修正の後に、発見が遅かった問題、手作業、CI・レビューの待ち時間を振り返り、次の改善を一つ選ぶ。繰り返す確認は、リスクと保守コストに応じて自動化する。

- テストや CI が遅くなったら所要時間を測り、速い検証を先に得る。接続確認の役割を残したうえで、独立した処理の並列化やテストの配置を見直す。
- ビルド・CI・補助スクリプトも本体と同じくレビュー・検証する。入力・出力・失敗箇所を明確にし、ローカルと CI の処理を別々に複製しない。
- 依存と開発環境の更新は、下記の着手前更新確認に従って判断する。更新を小さな変更として、設定・CI・環境手順を合わせ、共通検証と必要な端末確認を行う。
- 証明書・ドメインなど期限のある資産を利用する場合は、更新期限と担当を明確にし、期限前に確認する予定を設ける。バックアップを運用する場合は、実際に復元できることを定期的に確認する。
- 読みづらい箇所に加え、履歴で頻繁に変わる複雑な処理や、一緒に変更されるファイルを調べ、改善先を選ぶ。機能数やコード量の増加だけで開発の成果を判断しない。
- 集中作業と休憩、短い学習と知識共有の時間を確保する。繰り返し調べる手順や判断理由は、次の担当者が見つけられる場所へ残す。
- 例外・暫定対応を設ける前に、規則を守れる別案を検討する。
- 例外・暫定対応には、対象・理由・代替の確認方法・見直し条件・解消条件と、追跡先の Issue や文書を残す。警告の抑制や検証の緩和で失敗を隠さない。

### 依存・開発環境の着手前更新確認

開発着手前に実施記録を確認し、同日（日本時間、`Asia/Tokyo`）の正常完了記録がなければ、更新情報の確認と結果の記録を自動実行する方針を採用する。失敗・未完了の記録は実施済みとして扱わない。記録は月次 Issue 内に日付別で追記し、方針の確定と実際の確認・更新を区別する。現時点で自動実行の起動処理・実施記録の判定・更新情報確認の仕組みは未導入であり、自動通知・更新 PR の設定も未導入である。

| 項目 | 採用する方針 |
| --- | --- |
| 担当 | リポジトリの保守担当者 |
| 時期 | 開発着手前。同日の正常完了記録があれば、その結果を参照する |
| 自動実行の条件 | 同日（日本時間）の正常完了記録がない場合。失敗・未完了は実施済みとして扱わない |
| 対象 | アプリ・テストの依存ライブラリ、JDK、Android SDK、Gradle、AGP、GitHub Actions |
| 確認方法 | 現在の設定と Lint レポートを確認し、公式リリースノート・互換性情報・セキュリティ情報を調べる |
| 追跡先 | 月次の GitHub Issue 内へ日付別に、完了状態・更新候補・判断・延期理由・後続作業を記録する |
| 更新単位 | 小さな PR に分ける。互換性上セットで必要な更新はまとめる |
| 検証 | 共通のビルド・テストと、影響に応じた端末確認を行う。設定・CI・環境手順も同時に更新する |
| 完了条件 | 各候補の採用・延期・対象外が判断され、必要な後続作業を追跡できること |

月次 Issue の題名は `YYYY-MM 依存・開発環境の更新確認` とし、保守担当者を割り当てる。月次は記録の集約単位であり、実施タイミングは開発着手前とする。各日の記録に実施日（日本時間）と正常完了・失敗・未完了の区別を残す。候補ごとに現在の版・候補の版、確認した公式情報、変更の必要性と影響、採用・延期・対象外の判断を記録し、更新するものは対応する PR、延期するものは理由と再確認する時期・条件を残す。更新候補がない場合も正常完了の記録を残し、失敗・未完了では理由と残る確認を記録する。

自動実行を起動する方法と実施記録の判定方法は、導入時に具体化する。自動実行の対象は更新情報の確認と結果の記録とし、依存バージョンの変更は確認結果に基づく別の変更として検証する。更新 PR の自動作成は、その必要性を確認して導入を検討する。

AGP・Gradle・JDK・SDK は組み合わせの互換性を確認し、内蔵 Kotlin も AGP と合わせて扱う。Lint に情報として残る新版通知を確認の入口にし、対象全体の公式情報も調べる。確認の結果、更新しない判断も認め、その理由を残す。更新のためだけにすべてを最新版へそろえず、必要性・互換性・検証結果から採用を決める。

更新した変更では、[ビルド・検証の手引き](android-build.md)と CI・依存設定の整合性を確認し、必要な端末検証の結果と未確認事項を PR へ記載する。採用判断と更新完了を区別し、候補の判断後も未完了の更新があれば、対応する Issue・PR で追跡できるようにする。

測定や自動化の仕組みは、現在の困りごとを解く分だけ追加する。手順自体も、実際の結果に基づいてこの文書と分割先へ反映する。
