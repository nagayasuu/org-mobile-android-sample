# 比較試行の記録と時間計測

CA-001 の保存方式。Python 3.10 以上・Git・POSIX 環境で `scripts/record_trial.py` を使う。既存の[使用量集計](agent-tools.md#成功1件あたりの使用量を集計する)と組み合わせ、専用サービスやアカウント情報の収集は追加しない。モデルを呼ぶ比較の条件・予算・許可は[評価手順](../maintenance/evaluation.md)に従って別途固定する。

## 範囲と識別子を先に決める

試行は課題開始から検証・レビュー判定までとし、作者・失敗担当・再試行・レビュー担当を省略しない。`trial`、`agent`、`attempt` は非機密の英数字・`_`・`-` の ID とする。再開時は同じ試行・担当の新しい attempt と新規ディレクトリを使い、既存の成功した編集・検証を無条件に繰り返さない。対象版・入力ハッシュ・環境・検証結果の再利用可否は台帳で確認する。

`scope=trial` は課題内、`scope=outside` は比較全体の準備・外部検査・最終レビューなど課題外を表す。課題外にも別 ID と担当を付ける。`phase` は `agent`（モデルを含む担当プロセス全体）、`tool`（独立した検証など）、`environment`（環境準備）、`review`（レビュー全体）から選ぶ。準備やレビューの範囲は条件間で固定する。

作者プロセスが内部で実行したツール・レビューは、その全体時間に既に含まれる。親と子を両方独立した attempt として合算しない。内部ツールを分離できない場合は agent の内数・未分離と記録する。レビュー全体の時間にはモデル待ちやツール実行も含まれ、各工程が排他的とは限らない。

## 保存する

まずモデルを使わない動作確認例：

```sh
python3 scripts/record_trial.py run \
  --output-dir .local/measurement/D1-author-01 \
  --trial D1 --agent author --attempt 01 --scope trial --phase agent --timeout 30 -- \
  python3 -c 'print("synthetic run")'

python3 scripts/record_trial.py summarize .local/measurement/D1-author-01 \
  > .local/measurement/summary.json
```

実際の比較では `--` の後を、事前に許可・固定した担当コマンドへ置き換える。使用量を記録する担当は JSONL を標準出力に出す設定にし、`summarize_usage.py` の `agents[].events` に各 attempt の `stdout.log` を重複なく指定する。同じ担当の複数 attempt は `author-01`、`author-02` のように一意な集計 ID で列挙する。別ファイルのコピー・重複区間は実行者が排除する。保存器の終了0は課題成功や usage の完全性を意味しない。開始・終了記録や出力捕捉に欠測があれば `agents_complete=false` とし、末尾に完了 usage があっても全体を完全と扱わない。

| ファイル | 確定する内容 |
| --- | --- |
| `start.json` | 試行・担当・attempt・scope・phase、開始 UTC/Unix 時刻、HEAD と追跡差分ハッシュ |
| `stdout.log` / `stderr.log` | 担当の出力を別々に保存。失敗・途中出力も残す |
| `timeline.jsonl` | stdout の行番号・受信時の単調時計による経過秒。既知イベントには種別・ローカルなターン番号も付記 |
| `process.json` | プロセスの元 returncode・終了コード、終了理由、終了 UTC、単調時計による経過秒、記録エラー |

出力先ディレクトリと JSON は排他的に新規作成し、確定済みの完了を途中状態で上書きしない。開始と終了を別ファイルにするため、終了記録がない中断も開始記録から分かる。受信したチャンクごとにログを flush、開始・終了 JSON は fsync するが、電源断・ディスク障害・強制終了による末尾欠落まで保証しない。壊れた JSON は修復・0補完せず検査エラーとする。未完成ディレクトリは削除せず、新 attempt で再開する。

通常の終了は元コード、シグナル終了は128＋シグナル番号、起動失敗は127、時間上限は124を返す。元の負の returncode も保持する。SIGINT/SIGTERM・時間上限では子プロセス群を終了して回収する。コマンド終了後も同じプロセス群の子孫を終了するため、常駐サービスを起動するコマンドには使わない。別セッションへ離れた子が stdout を保持する場合は、元コマンドの終了後に最大約1秒で読取待ちを打ち切り、`capture_errors` と `capture_complete=false` を残して保存器を終了1にする（元コマンドの非ゼロ終了は優先）。そのログを完全な usage の根拠にせず、残存した別セッションの子は別途終了を確認する。保存器自身への SIGKILL・ホスト中断では終了記録が残らず、子の終了も保証できない。終了を確認してから再開する。

コマンド引数や本文をメタデータに保存しない。生ログには機密情報が含まれ得るので、公開・非機密の入力だけで実行し、`.local/` に保存する。自動マスキング・自動公開はしない。公開記録には内容確認済みの集約値だけを転記する。対象版の差分ハッシュに未追跡ファイルは含まれないため、入力・候補ツール・未追跡対象のハッシュ、CLI/Python 版・モデル・設定・プロンプトは評価台帳に別記する。

## 指標の取得範囲と欠測

| 指標 | 取得方法・範囲 | 取得不能・注意点 |
| --- | --- | --- |
| 担当の時間・終了コード | process.json。失敗・上限終了も対象 | 保存器の強制終了時は null。プロセス時間に起動・記録処理を含むが外側の準備は含まない |
| 試行内外の環境準備・ツール・レビュー | scope/phase を付けた独立コマンドの秒数 | 未記録の手作業や親内部の工程は null。独立コマンドを記録し忘れた場合、台帳で欠測にする |
| ターン・ツールの時系列 | timeline の種別・ターン番号・行番号とローカルの原イベントを照合 | 受信時刻でありサービス内実行時刻ではない。バッファリング・イベント欠如・不明形式を含み、ツール時間を自動推定しない |
| モデル待ち・生成・圧縮自身の時間と usage | 対応する原イベントで開始/終了と内訳を確定できた場合だけ別記 | stdout の無出力時間をモデル待ちと扱わない。本保存器ではモデル待ちは null。圧縮前後の累積差で内訳を推定しない |
| 入力・キャッシュ入力・出力 | 保存した JSONL を既存の summarize_usage.py へ渡す | failed/error/未完了/欠けた担当は観測量だけ。完全総量や成功あたり総量は null。保存器は未返却 usage を生成できない |
| 実費 | 契約と対応付く請求・利用明細を確認できる場合だけ既存マニフェストへ入力 | 時間・トークン単価やアカウント総量で試行費用を代用しない。不明は null |

`summarize` は明示したディレクトリだけを読み、同じ scope・trial ごとに集計する。同一パス・同一 attempt 識別子の重複は拒否する。省略した担当や別名コピーの一部重複は自動検出できないので、台帳の全担当・全 attempt と照合する。集計の `process_time_complete` は列挙された attempt の終了時間だけの完全性を表す。

- `attempt_seconds_sum` は担当・attempt の時間合計。並列中の時間も担当ごとに加算する。
- `recorded_window_seconds` は最初の開始から最後の終了まで。並列時間は一度だけ、記録間の待ち・中断は含む。試行全体を覆ったと台帳で確認できる場合だけ完了時間へ採用する。
- `observed_active_seconds` は記録済み区間の和集合。合計との違いから並列の重なりを確認する。`phase_attempt_seconds` と各 attempt を見て長い工程を調べる。
- 未完了 attempt が一つでもあれば時間合計・経過窓・工程合計は null。観測済み時間は `observed_*` に限定する。未記録の工程も null とし、観測した0と区別する。

担当内の所要時間は単調時計、担当間の窓・和集合は同一ホストの Unix 時刻＋所要時間で計算する。時計補正や別ホストによるずれは検出できないため、その場合は窓・和集合を採否に使わず未確認とする。別ホストは別集計にする。

## 次回比較への適用

比較前に全担当・工程・scope・時間上限・未計測理由を台帳に列挙する。開始記録、完了記録、ログ、usage を別々に照合し、プロセス正常終了で失敗イベントや usage 欠測を消さない。再開は新 attempt、外側の最終レビューも outside として保存する。公開する集約の削減率は完全性と条件一致を確かめた場合だけ算出する。

[保存方式の検証記録](../records/evaluations/2026-11-15-ca001-measurement.md)はモデルを呼ばない合成検証であり、モデル待ちや実費の取得、実作業での削減効果を実証していない。保守担当が次の実比較で使用クライアント・版の stdout 形式を照合し、実環境で保存を確認する。過去の復元不能な null は変更しない。

## 通常のPR統合を工程別に計測する

[統合手順](github-cli.md#統合の各段階を記録して再開する)を担当するたびに、PRまたは作業IDと先端SHAを付けて `.local/measurement/` に下の様式で記録する。同じ先端で依頼をまたぐときは記録へ追記し、先端が変わった場合は別の記録で旧版を参照する。PR側・統合後の CI はそれぞれ run ID・attempt を対応付ける。使用クライアント・版、モデルと推論設定、担当構成も記す。

| 工程 | 記録する範囲 |
| --- | --- |
| 事前確認 | 統合依頼を受けて確認を始めてから、対象版・権限・レビューと検証の根拠をそろえるまで。必要なコミット・push、`prepare` を含む |
| PR準備 | PR本文などの準備開始から、`create` または既存PRの確認が終わるまで |
| CI待機 | PR側・統合後の双方で、対象runの探索開始から必須CIの結果確認まで。`wait` と `main-ci` は別行にし、GitHubのジョブ時間を併記できる場合はrun・attemptと取得範囲も記す |
| 成果物照合 | 検証JSON・APKの取得開始から、対象版・検証結果・ハッシュの照合が終わるまで |
| マージ | マージ根拠と許可の再確認を始めてから、`merge` と統合後のSHA・ツリーの確認が終わるまで |
| 後片付け | `cleanup`、ローカルの切り替え・整理、結果報告の準備。準備完了時点で工程を締める。最終報告そのもののモデル応答は、取得できた場合に別枠で記す |

1. **時刻を残す。** 工程・担当・試行ごとに開始と終了のUTC、結果、根拠を記す。失敗・中断・再開は新しい行にし、待ちや再試行の理由を残す。統合台帳の `done` は成功した段階のコマンド秒数として参照する。失敗や再呼び出しのコマンド時間も必要なら上記の保存器で個別に取る。工程中のコマンド時間やCIのジョブ時間は内訳として併記し、工程時間へ加算しない。
2. **経過時間を集計する。** 同じ時計で比較できる開始・終了から、最初の計測開始から最終計測終了までの経過窓、明示的な依頼間待ちの区間、計測済み工程の区間の和集合、担当別時間の合計を記す。重複区間は和集合で一度だけ数え、担当別の合計と区別する。同じ担当の親工程と内訳コマンドは二重計上しない。工程の間に記録のない時間は未計測区間として残す。依頼間待ちは前の依頼を終了して次の依頼を受けるまでとし、時刻の根拠があるものを記す。未終了・欠測・時計の不一致があれば、完全な集計値は `null` とし、確認できた範囲と理由を記す。
3. **全担当の使用量を照合する。** 主担当、独立レビュー、計測範囲に入る自動承認レビューなどの全担当を列挙する。工程の開始・切替・依頼終了時に、取得できる担当の使用量スナップショットまたはイベントの境界をローカルに記す。実行版で取得形式を確認し、参照権限のある担当ログの対象区間から、一意なモデル応答の件数と、その入力・キャッシュ済み入力・出力を数える。後から取得した分も、対象区間と照合できた応答だけを計上する。たとえば [実CI待機の計測](../records/evaluations/2026-11-18-ci-wait-live.md#待機フェーズのモデル使用量)では、開始・終了の取得結果の差から、一意な応答IDごとの使用量を集計した。工程をまたぐ応答は、実行イベントで紐付く工程へ一度だけ計上し、帰属を確定できない分は工程未割当として別記する。CLIのターン使用量は[既存集計器](agent-tools.md#成功1件あたりの使用量を集計する)で対象区間ごとに集計できる。モデル応答数には応答単位の根拠を使う。取得できない担当・応答・使用量を記し、指標ごとに観測分と全担当の総量を分ける。キャッシュ済み入力は入力の内数で、未キャッシュ入力は両方がそろうときに差を求める。
4. **原因と採否を残す。** 依頼の終了時に取得範囲・欠測と主な原因（CI待ち、承認待ち、再試行など）を確認する。生ログやローカル専用情報は `.local/` に留め、共有する評価記録には確認済みの集約と公開可能な根拠を載せる。保守担当は次の3件の同種作業または月末の早い方で見直し、同じ対象範囲と条件の比較から改善候補の採否を判断する。比較材料が不足する場合は「試行継続」とし、次に確認する条件・担当を記す。 [評価手順](../maintenance/evaluation.md#codex-adoption-evaluation)

### 統合計測の記録様式

統合コマンドに `--record-timing` を付けると、既存の台帳と同じ場所の `*.timing.json` に、呼び出したサブコマンド（`invoked_step`）、実行した工程の開始・終了 UTC、経過秒数と成否を記録する。`verify-pr` では `wait` と `artifacts` の各試行に同じサブコマンド名を残す。過去の記録にサブコマンド名がなければ未計測とする。中断から同じ台帳でやり直した場合は試行を追加し、完了済み工程を再表示するだけの呼び出しは新しい試行に含めない。

```sh
python3 scripts/integrate_pr.py verify-pr --state .local/integration/work.json \
  --head "$gh_sha" --run "$gh_run" --record-timing
python3 scripts/integration_timing.py --state .local/integration/work.json
```

集計は Markdown を標準出力へ返す。`--format json` も利用できる。成功・失敗・中断と、終了時刻が記録されなかった試行を表示する。時刻を記録する前の台帳からは成功した工程の秒数だけを表示する。観測した試行時間の合計と、重複を除いた UTC 区間の和集合を区別する。終了時刻の欠測、時刻と経過秒数の不一致、台帳にのみ存在する成功工程があれば、完全な区間集計は未計測とする。コマンド外の確認・依頼間の待ち時間・モデル使用量は、この集計とは別に記録する。

各行に担当と試行を一つ記す。該当しない工程は「対象外」、予定されているが未実施の工程は「未実施」、取得できない値は `null` とし、理由を添える。取得できたゼロは `0` と記す。

```markdown
対象（作業ID・PR・先端SHA・統合SHA・PR側とmain側のrun/attempt）：
条件（依頼の範囲・クライアント/版・モデル/推論設定・全担当）：

| 工程 | 担当・試行 | 開始UTC | 終了UTC | 秒 | 応答数 | 入力 | キャッシュ済み入力 | 出力 | 結果・根拠・欠測理由 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |

依頼間待ち（開始・終了・秒・根拠）：
経過窓／計測済み区間の和集合／担当時間の合計／重複区間／未計測区間：
工程未割当の使用量（担当・理由）：
全担当の応答数・入力・キャッシュ済み入力・出力（観測分／完全な総量）：
最終報告の使用量（別枠・根拠）：
原因・採否・根拠・判断者・次の確認条件：
```

### 定型工程の改善を計測する

次の同種 PR 3件を目安に、通常の統合に合わせて `verify-pr` の実行経路、CI 時間、計測範囲を既存の `.local/measurement/` の記録へ追記する。ローカル検証・結果整形・再検証も同じ依頼に含まれた場合は、該当する項目を記録する。既存の台帳・ログで取得できる欄は参照で済ませる。

1. **実行経路と LLM なしの完了率。** 着手時に、既存手順で結果確認まで完結可能な工程と完了条件を特定する。各工程の実際の経路（実行したコマンド名、人または agent が担当した操作、途中切替の理由）を残す。分母は着手時に対象とした工程数、分子は結果確認までに当該工程の操作や判断でモデルを呼ばずに完了した工程数。モデルがコマンドを選択・実行指示した場合や結果を判定した場合は分子に含めない。失敗・中断・切替も分母に残す。経路の欠測件数も併記し、分母がゼロか LLM の関与が不明な工程がある場合、完全な率は `null` とする。
2. **結果確認までの時間と追加操作。** コマンド起動・終了・完了条件を確かめた時刻を残す。終了から確認までの秒数、終了後に確認に使った追加コマンド数と一意なモデル応答数を記録する。コマンドが完了条件を機械判定し、終了時点で証拠も確定する場合は同じ時刻を使える。人や agent の確認が必要なら、その完了時刻を使う。`run_check.py` の集約 JSON はレポート処理込みの内訳時間に使える。終了時刻は計測対象のコマンドが戻った時点で別途取得し、取得できなければ `null` とする。最初の起動から最終確認までを測る場合、並行する内訳時間は加算しない。 [ローカル検証](agent-tools.md#local-check-profiles) [結果の整形](agent-tools.md#format-check-results)
3. **CI の時間と応答。** PR 側・main 側の run と attempt ごとに、キューへ入った時刻、`verify` の開始・終了時刻、結果を初めて検知した時刻を記録する。各時刻の差から、キュー待ち、ジョブ実行、検知遅延を求める。`--record-timing` の待機工程終了を検知の近似値に使う場合は、台帳保存までの時間も含むことを記し、通知・目視で検知した時刻とは区別する。`verify` の開始より後、終了時刻までに完了した一意なモデル応答を数える。時刻の根拠がない場合や、GitHub と計測側で時計が照合できない場合は、該当する差分・応答数を `null` とする。
4. **再利用・再実行。** 過去記録の照合結果に、実際に選んだ操作を添える。条件が一致して成功記録を再利用した件数、原因に関係する条件変更後に再実行した件数、変更なしで再実行した件数と秒数を集計する。一時障害と判断した場合は理由を残す。再利用候補の表示だけは再利用の実績に含めない。 [過去の検証記録との照合](agent-tools.md#compare-check-records)と[再試行の判断](../workflow/verification.md#retry-diagnosis)
5. **計測範囲。** 工程ごとに時間と使用量の開始・終了がそれぞれ同じ境界かを確認し、使用量を全区間取得できた担当数と測定対象の担当数を残す。時間と使用量の境界が異なる場合や担当の使用量が欠ける場合は、確認できた値と区間・理由を記録し、その工程の完全な使用量と削減率は `null` とする。LLM 不使用を確認できた場合は `0` と記す。

#### CI 時刻の取得

[CI の状態確認](github-cli.md#ci-の状態失敗箇所の確認)で特定した `gh_repo`、`gh_run`、`gh_attempt` を使い、同じ attempt のジョブを読み取る。`verify` が一つで、台帳の対象と run・attempt が一致する場合に開始と終了を採用する。

```sh
gh api --hostname github.com --paginate \
  "repos/$gh_repo/actions/runs/$gh_run/attempts/$gh_attempt/jobs" \
  --jq '.jobs[] | select(.name == "verify") | {id, run_id, started_at, completed_at}'

# 初回 attempt の近似値に使う場合
gh api --hostname github.com "repos/$gh_repo/actions/runs/$gh_run" \
  --jq '{id, created_at}'
```

初回 attempt でキュー入りの時刻が得られない場合は、run の `created_at` から `verify` 開始までを近似値として、取得元とともに残せる。再実行時は当該 attempt のキュー入りを確認できる場合だけ算出する。初回 run の作成時刻を再実行の始点に使わない。 [GitHub のジョブ API](https://docs.github.com/en/rest/actions/workflow-jobs#list-jobs-for-a-workflow-run-attempt) [GitHub の run API](https://docs.github.com/en/rest/actions/workflow-runs#get-a-workflow-run)
