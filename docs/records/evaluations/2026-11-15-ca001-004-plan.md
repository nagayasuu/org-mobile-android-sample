# CA-001〜CA-004：実環境の保存・入力・再開の確認計画

実行前固定。判断者・実行者は主担当 Codex。基準は `33613a4`。
既存の CA-001 保存器、CA-003 入力照合器、CA-002 の1文削減候補を使い、CA-004 の再開台帳を同じ実行で確認する。

## 条件・予算・成功判定

- 公開 HEAD の隔離コピーで、文書 D1 の `確認しましす` だけを `確認します` に修正する。原文は `# 検証`、当該文、`[作業指示](../AGENTS.md)` の3行。リンク・他の文字を維持する。
- 対照は `Acquire only required public instructions and task sources; retain unchanged reads and avoid unnecessary help calls.`、候補は `Avoid unnecessary help calls.`。この1文以外の役割別入力・ツール・原文・必須規則は同一。候補の元は [CA-002 診断](2026-11-15-ca002-input-diagnosis.md)。文書の英訳や取得方式の強制は行わない。
- 順序は対照1→候補1→候補2→対照2。各枠は作者1回、ホストの完全一致・リンク検証、別プロセスの独立レビュー1回。計4枠・最大8モデル起動、各240秒、累積入力4,000,000・出力100,000トークンまで。各役割終了時に上限を照合し、到達・時間上限・利用上限・usage欠測・規約違反で後続を停止する。認証・課金方式・モデルを変更して継続しない。
- Codex CLI 0.166.0、`gpt-6.1-sol`、high、medium、workspace-write を両条件で固定する。ユーザー設定の追加読込を避ける `--ignore-user-config` と `--ephemeral --json` を用いる。既存の認証経路を使い、認証情報を読取・転載しない。初回ロード・キャッシュ・サービス遅延は未統制とする。
- 各モデル起動の直前に、UTF-8原文と既存のホストアサーションを含むプロンプトを CA-003 で照合する。対象版、原文、プロンプト、候補ツールのハッシュを固定し、照合不合格ならモデルを呼ばない。正常入力に加え、改行を欠いた別入力の拒否も確認する。
- 作者成功後、レビュー開始前にホスト制御の中断点を1回設ける。作者の完了記録・差分・入力・検証のハッシュを台帳に保存し、再開時に不変を照合してレビューだけを新 attempt として実行する。進行中のモデルの強制中断ではない。作者や検証の無条件な再実行をしない。
- 成功は期待する1箇所だけの差分、リンク検証成功、レビューの R01〜R30 全件と修正必須指摘なし、対象外ファイル・検証根拠の不変で判断する。プロセス終了0と課題成功を区別する。
- 運用採用には品質低下なし、全担当・失敗込みの入力/成功10%以上減、完了時間中央値の悪化20%以内、全担当usage取得が必要。少数の文書課題だけで解析・画面や通常開発全体へ一般化しない。条件を満たさない場合は見送り、任意利用を維持する。

## 記録・取得範囲

生ログ・入力計画・固定プロンプト・再開台帳は Git 除外先に保存し、公開するのは確認済みの集約値・非機密ハッシュ・判定だけ。共有は既存環境と公開コード・文書・合成入力に限定し、[既存利用者確認](2026-11-07-instruction-reading.md)の範囲を継承する。私的資料や別サービスへの共有許可には広げない。

CA-001 の `start.json`・`stdout.log`・`stderr.log`・`timeline.jsonl`・`process.json` を担当・attempt別に保存し、`turn.completed.usage` の形式を既存集計器と照合する。作者・レビュー・検証は scope=trial、環境準備・入力生成・最終変更レビューは scope=outside。準備する主担当自身のモデル消費や非計測の手作業時間は null とし、比較枠の消費に混ぜない。

役割別input/cached/output、コマンド分類（通常読取・補助・refresh・その他）、返却文字数と取得補助の原文/メタデータを分ける。複合シェル等で範囲を確定できない読取量・再読は null。要求内部の全文構成、モデル待ち・圧縮自身の時間、実費も確定根拠がなければ null。文字数をトークンに換算しない。

担当プロセス時間合計と開始〜終了窓を区別し、内側のツール時間を親へ再加算しない。失敗・未開始・未完了を台帳から落とさず、完了ファイルの再使用拒否とハッシュ不変を確認する。

## CA ごとの完了判定

1. CA-001：実 CLI の開始・終了・受信イベント・usage の保存を照合。取得不能と失敗を残し、欠測のない値だけを完全とする。
2. CA-002：役割・読取方式・返却メタデータの診断を行い、一要因比較の採否と限界を記録する。欠測や上限で止まれば採否は保留とする。
3. CA-003：正常な実入力の事前照合・不備入力の拒否・準備時間・無効試行数を記録する。過去の8件すべてを防げたとは推定しない。
4. CA-004：中断点→台帳照合→残りの役割だけの再開、完了記録不変、usageの一意集計を確認する。

結果は別の評価記録から本計画と集約JSONを参照する。失敗時は未達条件と再開条件を残す。今回の依頼ではコミット・push・PR・マージを行わない。

## 起動環境の診断後の再開条件

初回 B1 作者の CLI が、状態保存先の read-only エラーにより in-process app-server client 初期化時に終了1となった。stdout は空で usage は取得不能。失敗 attempt は保持し、対照群の完全な総入力は null とする。モデル・認証・料金経路を変えず、同じ CLI が既存の状態保存先を利用できる実行権限だけを調整する。環境診断と権限調整は試行外の作業として記録する。

再開は同一 B1 作者の attempt 02 とし、元の失敗を含め CLI 起動は最大8回のまま。したがって順序の末尾 B2 の独立レビューは開始できなければ未開始として残す。比較の完全性が欠けるため、今回の結果による候補の運用採用は見送る。ここでの目的は実形式の保存確認・役割別診断・正常な作者結果の再利用確認を進めることであり、欠測を除外した改善率は算出しない。次の環境エラーまたは欠測が発生したら再び停止し、同条件での起動を反復しない。
