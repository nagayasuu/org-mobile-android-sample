# PR本文編集によるCI再実行の回避

## 実装前の計画

基準HEADは `28b6d5a`。待機・監視の実装と5提案の未コミット変更を保持する。対象は検証結果コメントの更新補助、そのテスト、Git規約・GitHub CLI手引き・PRテンプレート、残タスク、本記録。

当初の「本文の最終追記を統合後にまとめる」という案だけでは不十分だった。[PR #48の追加run](https://github.com/nagayasuu/org-mobile-android-sample/actions/runs/43689214158)はマージ後本文編集時刻に起動し、失敗していた。マージ済みmainの成功とは別の結果である。`edited` と必須 `verify` はタイトル検証にも使うため維持し、通常の検証結果追記をPR本文から専用コメントへ移す。

受け入れ条件：

1. PR本文を変更せず、対象repo/PRへ専用マーカーを持つ自分のコメントだけを作成・更新する。OPEN/MERGEDのどちらでも同じ経路を使う。
2. 同じ内容なら更新しない。第三者や通常のコメントを編集せず、候補が複数・API不正・失敗時は停止する。自動再試行しない。
3. 日本語・改行を保持し、検証した本文を標準入力で渡す。本文・生APIレスポンス・認証情報を実行結果へ出さない。
4. CLI手引きとPRテンプレートに作成時点の結果・継続更新先を示す。目的・受け入れ条件などの実質変更は通常の本文改訂と必要なCIで扱う。
5. CI設定・必須チェック名・タイトル検証・統合後CI・権限・投稿の許可範囲を維持する。コメントの記載をCI成功の代用にしない。

公開入力とfake ghを使い、既存Git関連テスト→新規Red/Green→全Pythonテスト→文書・差分→独立レビューで確認する。比較用モデル呼出し0回。実GitHubへコメント投稿・PR本文更新・CI起動は行わず、CLI適合は既存APIの読み取りとhelp確認に限定する。実CI実行回数・トークン/時間の削減量は今回計測しない。

## 実装と根拠

`scripts/update_pr_results.py` を追加した。GitHub.comのrepo/PR・公開可能なUTF-8ファイルを明示し、PR存在確認→認証ユーザーID確認→ページ分割を含むコメント取得→自分の固定マーカー付きコメントの作成/更新を行う。同じ本文なら更新しない。予約マーカー・空/不正UTF-8、PR番号やrepoの不備、曖昧な候補・不正応答・API失敗は停止し、本文や生レスポンスを表示しない。検証済みの本文文字列を標準入力で渡す。`--check` は読み取りのみで投稿しない。

[GitHub公式のコメントAPI](https://docs.github.com/en/rest/issues/comments)とgh 2.102.0のhelpでGET/POST/PATCH、ページ取得、標準入力の対応を確認した。PRへの通常コメントは [issue_comment](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#issue_comment) に対応する。現在のandroid.ymlはpull_request/push、e2e.ymlはworkflow_dispatchが対象で、コメントの作成・更新は起動条件に含まれない。両workflowとタイトル/コミット検証器はHEADから不変であることを照合した。

Git規約とCLI手引き・PRテンプレートでは、本文を作成時点の記録として保ち、最新結果をChecks・専用コメント・根拠の参照先に集約する。本文の実質的な訂正やタイトル変更に必要なCIを省略しない。別repoや将来のworkflowがコメントイベントを扱う場合は前提を再確認する。

PR #48のマージ後追加runは `pull_request` / 同じ先端SHAで、失敗stepは `Check commit messages and PR title` だった。これは統合後main CIの成功を否定するものではないが、本文更新を統合後に移すだけでは再実行防止にならない根拠として記録する。今回、新しいrunの起動や再試行は行っていない。
