# Codex のトークン効率を向上させる方法一覧

読み込む情報と再試行を減らし、作業品質を保つ方法を整理した。導入順は、日常運用の改善、キャッシュと履歴の管理、追加ツールの開発を基本とする。以下は導入候補であり、設定やツールの変更は別途行う。

Codex の日常運用、独自 API 実装、ローカル LLM の実験を分けて記載する。削減率・精度・料金は、出典や測定条件を確認できないものを保証値として採用しない。モデルの仕様・料金・設定の対応範囲は、採用時に対象版の公式資料で確認する。

## まず取り入れる運用

### 1. ファイルを読む範囲を絞る

- `rg` や `rg --files` で対象を探してから読む。
- 関係する節・関数と、その依存先を読む。
- 読んだ内容は、ファイルが変わった場合や情報が不足した場合に読み直す。
- 生成物、ロックファイル、圧縮済みコードなどの全文表示を避ける。

### 2. ツールの出力を短くする

- 一覧の絞り込みや集計は、シェルやスクリプトで行う。
- 成功時は結果の要点を返し、失敗時はエラーと必要な周辺情報を返す。
- 長いログは必要に応じてローカルに保存し、追加で読めるようにする。
- 出力を省略したことを明記し、終了コードや重要な警告を残す。
- 編集対象の原文、識別子、行番号、エラーメッセージは正確に残す。
- 文字数だけで切り捨てず、次の判断や編集に必要な情報を残す。

### 3. 差分とテストの対象を絞る

- 差分の概要を確認してから、変更したファイルを読む。
- 実装中は関係するテストで早く結果を確かめる。
- 完了前には、リポジトリで定めた必須検証とレビューを行う。

### 4. AGENTS.md を短く保つ

- 毎回必要な規則、禁止事項、検証方法、参照先を中心に書く。
- 詳しい手順は文書やスキルに分け、必要なときに読む。
- 同じ説明を重複させず、変更時は正本を更新する。
- リポジトリ全体の説明を常に読み込ませず、作業に必要な情報へ案内する。
- AGENTS.md に移した指示も、モデルへ読み込まれる分は入力になる。毎回の手入力を減らすことと、入力トークンを減らすことを区別する。

AGENTS.md とスキルの役割分担は、[OpenAI の運用例](https://developers.openai.com/blog/skills-agents-sdk)も参考になる。

### 5. MCP とツールを必要な範囲に限定する

- 作業に必要なサーバーとツールを選ぶ。
- 対応する環境では、必要なツールだけを有効にし、説明も必要時に読み込む。
- Codex の設定と独自の API 実装を区別し、使用環境で使える方法を確認する。

## キャッシュと長期作業の履歴を管理する

### 6. プロンプトキャッシュを活用する

- 同じ作業中は、指示やツール構成を理由なく変更しない。
- 独自の実行基盤では、固定の指示やツール定義の順序を安定させる。
- キャッシュによる費用削減と、トークン数の削減を分けて評価する。

独自 API 実装では、固定の指示を先頭、変化する依頼や検索結果を後方に置く。キャッシュは共通する接頭部分の一致が前提で、同じセッションでもヒットが保証されるわけではない。割引率はモデルごとに確認する。[OpenAI のキャッシュ仕様](https://developers.openai.com/api/docs/guides/prompt-caching)

### 7. 長い履歴を圧縮し、再開に必要な状態を残す

- 履歴の圧縮は標準機能を基本とし、しきい値を安易に変更しない。
- 長い作業では、目的・決定事項・変更ファイル・検証結果・未解決事項・次の操作を残す。
- 圧縮後に原文の再読込や再試行が増えていないか確認する。
- 独自の履歴管理で直近の会話だけを残す場合も、目的・制約・利用者の訂正・許可された操作の範囲は別途保持する。「最新4〜8ターン」のような固定件数だけで削除を決めない。
- 再開時は短いメモに直近の依頼と次の操作をまとめ、詳細は対象版付きの原文へ案内する。要約を必須手順や受け入れ条件の代わりにしない。

## 追加開発して試す仕組み

### 8. 関数やクラス単位で読み込む

- LSP や AST（コードの構文構造）を使い、名前から対象を探す。
- ファイル全文の代わりに、必要な関数やクラスの原文を読む。
- 型、インポート、呼び出し元など、判断に必要な依存先も取得する。

### 9. リポジトリ構造を使って検索する

- 関数の呼び出し関係やモジュールの依存関係を索引にする。
- 検索結果は候補ファイル・識別子・行範囲を中心に返す。
- 候補だけでは足りない場合は検索範囲を広げ、必要な原文を取得する。

### 10. ファイルの構造化メモリを持つ

- ファイルごとに、内容のハッシュ・識別子・依存先・確認済み範囲を記録する。
- 内容が変わっていなければ、記録を使って再調査を減らす。
- 内容が変わった記録は無効にし、編集前には対象の原文を確認する。
- 私的な文書や認証情報を、共有用の記録へ混ぜない。

### 11. 構文を理解した編集で再試行を減らす

- 関数やクラスを指定して編集し、文字列の一致失敗によるやり直しを減らす。
- 編集前には対象の原文を取得し、編集後に構文と動作を確認する。
- 編集失敗、再読込、再試行の回数を比べて導入効果を判断する。

### 12. 探索と編集の担当を分ける

- 大きなリポジトリでは、探索専用ツールや agent を試す。
- 実装担当へは、候補箇所と根拠を短く渡す。
- 小型モデルへの探索の振り分けは、精度と費用を比較して判断する。
- 別 agent やモデルの消費量も含めて評価する。
- 担当を分けたこと自体をトークン削減とみなさず、受け渡しの負担も測る。
- 探索・編集・検証・レビューの各担当へ、役割に必要な資料・ツールと、対象版付きの結果だけを渡す。作成とレビューの独立性は既存手順に従い、会話全体や各担当の履歴を一律に複製しない。

### 13. 作業内容に応じた圧縮を試す

- 独自の実行基盤では、探索終了などの区切りで履歴を圧縮する方法を比較する。
- 専用の圧縮モデルは、大きな検索結果やツール出力が主な消費源だと確認してから検討する。
- 原文、識別子、行番号、エラーなどを選んで残し、編集に必要な情報を保つ。
- 圧縮処理自体の費用、時間、キャッシュへの影響も含めて比較する。
- 独自基盤では、指示・検索結果・要約・ツール出力に割り当てる入力予算と、推論・出力用の余裕を分けて設計する。予算超過時は重複を除き、必要な原文を追加取得できる状態を保つ。必須指示や編集対象の原文を機械的に切らない。[OpenAI のコンテキスト上限の説明](https://developers.openai.com/api/docs/guides/conversation-state#managing-the-context-window)
- 圧縮文も後続の履歴で繰り返し入力される場合は、1回の圧縮率に加えて作業完了までの累積入力を測る。圧縮・原文取得を仲介する仕組みでは、原文を対象版と識別子で保持し、必要な箇所だけ復元する。復元時の追加入力・時間と、履歴の入れ替えによるキャッシュへの影響も含める。

具体的な実験候補は、重要情報を抽出する要約、長さを保ちながら不足情報を補う [Chain of Density](https://arxiv.org/abs/2309.04269)、専用ライブラリの [LLMLingua](https://github.com/microsoft/LLMLingua) など。原文と圧縮文で同じ課題を実行し、日本語の条件・否定・識別子の欠落と、圧縮自体の呼び出し回数を確認する。要約研究の結果をコード編集の精度保証へ置き換えない。

独自の要約処理と、API が返す圧縮済みの状態は区別する。Responses API の `/responses/compact` を使う場合、返された文脈は一部を独自に削らず、そのまま次の入力に引き継ぐ。[OpenAI の compaction 仕様](https://developers.openai.com/api/docs/guides/compaction#standalone-compact-endpoint)

## プロンプト・設定・検索の補完策

### 14. 指示と構造化データの冗長さを減らす

- 依頼は目的・変更範囲・制約・受け入れ条件・必要な結果に整理し、同じ背景説明や例の繰り返しを減らす。
- 報告の長さと形式を指定し、同じ差分や検証結果の再掲を減らす。失敗・警告・未確認事項は残す。
- JSON などの機械向けデータは、不要な項目・重複・整形用空白を削る案を試す。キー名を短縮する場合は対応表も含む入力全体で比較し、公開 API や保存形式は変更しない。
- 日本語の助詞・否定表現や、コードのインデント・文字列内の空白を一律に削らない。圧縮前後の意味と実際のトークン数を確認する。
- gzip や Base64 は保存・転送とモデル入力を分ける。採用する場合はツール側で復元し、必要な原文だけをモデルへ渡す。符号化した文字列の直接入力を削減策として採用しない。

短い自然言語の出力や構造化出力の簡素化は、[OpenAI のレイテンシ最適化ガイド](https://developers.openai.com/api/docs/guides/latency-optimization)を参考に試す。入力を減らした割合だけ作業時間も短くなるとは仮定しない。

### 15. モデル・推論強度・出力の長さを別々に評価する

- 単純な探索・文書整理と、複雑な設計・不具合解析を分けて比較する。同じ課題で品質を保てるモデルと推論強度を選び、全作業を一律に低くしない。
- 最初は現在の設定を基準にし、対応する強度を一つずつ変える。推論量が減っても再試行が増える場合は、完了までの総費用・時間で判断する。
- 出力は必要な成果物と根拠に絞る。生成上限でコードや報告が途中で切れた場合は未完了として扱う。
- 温度（`temperature`）や `top_p`・`top_k` はサンプリングの調整であり、推論強度とは分ける。低くすればトークンが減るとは仮定せず、モデル・API・推論エンジンの対応範囲を確認する。

| 利用環境 | 設定を検討する際の確認事項 |
| --- | --- |
| Codex CLI | `model_reasoning_effort` の対応値はモデルとクライアントに依存する。`model_verbosity` も対象モデルでの対応を確認する。`project_doc_max_bytes` は AGENTS.md から指示を組み立てる際のバイト上限であり、全コンテキストのトークン予算とは分ける。必須指示を欠落させるために下げない。[公式設定一覧](https://learn.chatgpt.com/docs/config-file/config-reference) |
| 独自 Responses API 実装 | `max_output_tokens` は推論トークンを含む生成上限。小さすぎる上限による `incomplete` を検出し、利用モデルの推論設定と合わせて評価する。ほかの API やローカル推論の `max_tokens`・`max_new_tokens` をそのまま流用しない。[公式の推論モデルガイド](https://developers.openai.com/api/docs/guides/reasoning#controlling-costs) |
| ローカル推論エンジン | モデル固有のテンプレート、生成上限、停止条件、サンプリング設定を確認する。Codex CLI の設定キーと共通とは仮定しない。 |

### 16. BM25・埋め込み検索を必要に応じて比較する

- `rg` を基準に、候補が多すぎる場合や言い換えによる探索漏れが問題になった場合に、BM25 の順位付けや埋め込み検索を試す。
- 検索対象を関数・節などの単位へ分け、パス・識別子・行範囲・内容ハッシュを付ける。重複した結果を除き、原文へ戻れるようにする。
- 検索上位件数と読取量を少なく始め、必要な依存先やテストが見つからなければ範囲を広げる。検索スコアだけで編集対象を確定しない。
- 埋め込み・索引の生成、更新、保存、検索の費用を含めて比較する。索引にも公開可能な対象だけを含め、変更されたファイルの索引を更新する。

RAG の初期実験では既存の検索で足りるかを先に確かめる。ベクトル DB やフレームワークの追加は、索引の規模・更新頻度と保守負担から判断する。BM25 や埋め込み検索の一律の削減率・優劣は設定しない。

### 17. 中間結果とビルド成果物を条件付きで再利用する

- 依存関係の解析や検索索引は、内容ハッシュと解析ツールの版を記録し、不変の部分を再利用する。変更箇所に依存する結果も無効化する。
- ビルド・テストのキャッシュは、ビルドツールの入力・依存関係・設定・環境の判定に従う。過去ログだけを根拠に今回の検証を実行済みとしない。
- 再利用した結果と今回実行した結果を区別する。新しい XML を要求する検証では、[ビルド手引きのログ集約手順](../android-build.md#check-output)に従ってレポートを再生成する。
- 再利用によるツール実行時間の短縮と、モデルへ渡す結果の集約によるトークン削減を別々に測る。

## ローカル LLM を使う場合の追加実験

### 18. 量子化・学習・メモリ配置を比較する

これらは、重みや推論エンジンを管理できる場合の候補である。ホストされた Codex モデルの設定としては扱わず、この Android アプリへモデルを組み込む提案とも分ける。

| 手法 | 試す内容と採用条件 |
| --- | --- |
| 量子化 | 対応する低精度の重みで、同じ課題の成功率・メモリ・速度を比較する。重み以外の KV キャッシュや実行時メモリも測り、「16GB なら必ず動く」「精度低下は一定」とは仮定しない。[Transformers の量子化ガイド](https://huggingface.co/docs/transformers/quantization/overview) |
| 蒸留 | 小型モデルに対象業務を学習させる案を、既存モデルで不足が測定された後に検討する。教師出力の利用条件、学習データ、学習費用と評価データの分離を確認する。 |
| LoRA / Adapter | 対象業務への適応が必要な場合に、全重みの更新と比較する。LoRA は低ランクの更新行列を学習する方法であり、適用しただけで推論トークンが減るとはみなさない。[PEFT の LoRA 解説](https://huggingface.co/docs/peft/main/en/conceptual_guides/lora) |
| プルーニング | 不要な重みを除く案は、対応する実行基盤で実際に速度・メモリが改善するかを確認する実験とする。品質低下と再学習費用も含め、初期導入の優先度は低くする。 |
| CPU・ディスクへのオフロード | メモリに収まらない場合に配置を比較し、ロード時間・転送待ち・生成速度を測る。メモリへの収容と高速化を別に評価する。[Accelerate の Big Model Inference](https://huggingface.co/docs/accelerate/usage_guides/big_modeling) |

推論エンジンや最適化手法は、モデル・ハードウェア・ライセンスの対応を確認して選ぶ。量子化や配置変更によるメモリ・速度の改善と、モデルへ送るトークン数の削減は別の指標として扱う。専用圧縮ツールも含め、提供元・対象版・利用条件を特定し、互換性を確認してから導入する。

## 導入効果の確かめ方

このプロジェクトでの実行手順は[評価と継続改善](../development-workflow.md#codex-adoption-evaluation)、記入用の[評価様式](../templates/codex-adoption-evaluation.md)に集約した。使用量集計には課題ごとの成功判定、任意の時間・再読・再試行・手戻り測定を追加し、欠測を0として集計しない。[対応と測定の記録](../verification/2026-11-12-codex-adoption-evaluation.md)では、実測できた出力量と、未計測のモデル使用量・品質への効果を分けている。

| 観点 | 確認すること |
| --- | --- |
| 比較条件 | 同じ課題群・対象版・モデル・推論設定・環境で導入前後を比較し、可能なら複数回実行する。読む範囲、検索、記憶などを個別に変えた条件と、組み合わせた条件を分ける。 |
| 使用量の収集 | CLI の比較実験では `codex exec --json` の JSONL から `turn.completed` の使用量を集計する。対応する版と取得範囲は[公式資料](https://learn.chatgpt.com/docs/non-interactive-mode)と実際の出力で確認する。生ログはローカルに保存し、共有時は非機密の集約値を使う。 |
| 集計の重複防止 | キャッシュ済み入力が総入力に含まれる場合は再加算せず、未キャッシュ入力は総入力からキャッシュ済み入力を引く。複数ターンや別 agent のイベントも、同じ消費を重複して数えない。 |
| 計測する値 | 総入力、キャッシュ済み入力、出力、取得できる場合の推論トークン、費用、時間、成功率を記録する。推論トークンなどの内訳と総量の関係も利用環境で確認する。 |
| トークンの数え方 | プロンプトや JSON の圧縮は、対応するトークナイザーまたは API の使用量で比較する。文字数・バイト数を代用しない。モデル間で数え方が異なる場合は記録し、トークン数だけで費用や速度の優劣を決めない。 |
| レイテンシ | 最初の応答まで、生成完了まで、検証・再試行を含む作業完了までを分ける。複数回の中央値と、試行数が十分な場合の p95 を記録し、キャッシュ有無や初回ロードの条件を分ける。 |
| 品質の評価 | このプロジェクトの受け入れ条件と必須検証を成功の基準にする。SWE-bench・Terminal-Bench などを使う場合は版・課題・実行基盤も記録し、このアプリの検証を代替しない。要約の類似度だけでコード編集の正しさを判断しない。 |
| 探索と再試行 | 読み込んだソース量、最初の編集までのトークン、ツール呼び出し、再読込、再試行、圧縮の回数を比較する。圧縮後のキャッシュ率も確認する。 |
| 成功1件あたりの消費 | 失敗分と別 agent 分を含む総費用・総入力を、それぞれ成功件数で割って比較する。成功率が同じでも、どの課題が失敗するようになったか確認する。 |
| 測定範囲 | CLI の親スレッドで得た値と全担当の合計を区別する。取得できない項目は未計測とし、全体の削減率を推定で断定しない。 |
| 採否の判断 | 品質低下、再試行増加、費用・時間の増加があれば見直す。 |

API の概算費用は、未キャッシュ入力・キャッシュ済み入力・出力それぞれの「トークン数 × 対応単価」を合計する。単価の単位、モデル、取得日、長文・キャッシュ書込などの適用条件、別途かかるツール料金を確認する。出力に含まれる推論トークンは重複加算しない。[OpenAI の料金表](https://developers.openai.com/api/docs/pricing)

ローカル推論では CPU・GPU・RAM / VRAM、モデルと量子化形式、推論エンジンの版、入力長、同時実行数、電力使用量を記録する。費用比較では電力とハードウェア・保守の負担も区別して示す。API の従量料金による概算と、契約プランでの実際の支払いも混同しない。

`codex exec --json` は計測候補であり、この文書の変更で比較実験を実行したわけではない。`--full-auto` は、現行の[公式資料](https://learn.chatgpt.com/docs/non-interactive-mode)では非対応とされている。実行例を採用するときは、使用版に対応する権限設定を確認する。ストリーミング自体はトークン削減策として数えない。
